현재 성공한 주요 네이티브 검사 네 건을 따로 분석하면 총 132분 중 약 125분(94.8%)이 타입 검사와 테스트 실행 파일 준비다. 진행 요약이 앞선 타입 검사 정보를 반복 출력하므로 phase/start/duration/argv가 같은 기록을 제거한 후 계산했다. 나머지는 실제 테스트와 helper·프로세스·증거 처리 등을 포함하므로 순수 테스트 시간으로 단정하지 않는다. 질문 철회 59.15분(준비 55.44분), app-server 36.67분(34.56분), core 28.45분(27.65분), protocol 7.73분(7.46분)이다.

앞선 오류가 드러나기까지 걸린 시간은 디스크 부족 130.12분, Windows 자식 PATH 문제 43.48분, no-marker fixture의 상위 .git 상속 43.73분, Python SDK 환경 누락 24.42분이다. 이 시간에는 재사용 가능한 컴파일도 포함되어 있어 전부 낭비 또는 절감 가능 시간으로 계산하지 않는다. Chrome 디버그 포트 6666과 Node WebSocket의 포트 제한 충돌은 실패 요약이 생성된 뒤에도 약 24분 34초 동안 브라우저/Node가 종료를 막았다. 해당 복구와 패키지 재시도는 네이티브 컴파일과 겹쳤으므로 같은 길이의 전체 완료 지연을 주장하지 않는다.

전체 빌드과정 개선안은 아래 절에서 소유자·순서·검증 기준과 함께 제시한다. docs/ops/development.md의 Consolidated build preflight와 docs/playbooks/build.md에는 환경·조기 검사 지침을 이미 통합했다. 두 문서 git diff --check는 exit 0이었다. 자동 preflight 및 브라우저 harness 개선은 아직 구현하지 않았으며, 해당 문서 변경을 v11f에 넣지 않았다.

통계 원본: r11/reports/build-timing-analysis.json, build-timing-summary.json, timing-priorities.json, current-native-timing.json, current-native-compile-breakdown.json. 실제 stdout/stderr와 원 실패 receipt는 유지했다.

현재 빌드 차단 원인은 고정본 engine/codex-rs/rmcp-client/src/oauth/store_identity_tests.rs:151의 E0308(expected PathBuf, found AbsolutePathBuf)이다. 기본 작업 폴더에는 find_codex_home()?.to_path_buf() 수정이 이미 있지만 고정본에는 없다. 앞서 승인된 no-marker fixture 이외 변경을 추가하지 말라는 사용자 경계를 지켰으며 이 한 줄을 임의로 포함하지 않았다. 제품/소스/패키지는 통과했으나 최종 호스트 검증과 사용자 프로필 설치는 실행하지 않았다. mandatory native 실패 때문에 작업 커밋도 보류했고 무관한 staged 변경은 유지했다.

현재 R11 producer/브라우저/공유 Cargo lease 종료를 확인했다. R11 및 current-cargo-incremental의 lifecycle을 실제 failure/exit 1로 닫아 실행 참조 6개와 활성 실행 보호를 해제했다. 두 묶음은 membership_complete:true이며 잔여 참조는 없다. 현재 실패 진단과 즉시 이어질 수 있는 수정 빌드의 컴파일 재사용을 위해 명시적으로 보존한다. 수정 빌드 수용 또는 빌드 취소 후 해당 묶음을 다시 검토한다. 종료를 성공으로 바꾸거나 레거시 owner 불명 lease를 제거하지 않았다. evidence: terminal-handoff.json, terminal-processes.json, lifecycle-terminal-close.json.

## 전체 빌드과정 개선 계획

상태: 구현 및 관련 Windows 회귀 검증 완료. 사용자가 4번 브라우저 연결·종료 처리를 제외한 개선 작업을 승인했다. 입력/결과 판정, 실제 사전 검사, 조기 테스트 컴파일, 재개·재사용 및 최종 검증/정리 연결을 구현했다. 새 제품 빌드·설치는 별도 고정 입력으로 이어질 작업이며 이번 개선 실행 중 시작하지 않았다. 기존 2026.0.11 완료 목표와 빌드 시작 이후 변경을 추가하지 않는 사용자 지시는 유지한다.

### 입력 변경과 통과 판정

외부 변경의 존재 자체가 실패 조건은 아니다. 작업 폴더의 후속 변경이 고정본 밖에 남아 있고 소비한 도구·외부 입력도 고정된 정체성을 유지하면 고정본은 계속 검증할 수 있다. 고정본 자체 또는 실제 소비한 입력이 실행 도중 바뀌면 해당 결과의 입력 관계가 깨지므로 영향받는 결과를 수용하지 않는다. 출처가 정상적으로 기록된 로컬 수정은 허용되며, 타입 변경이 의도적이라는 설명은 그 수정의 출처나 테스트 컴파일 성공을 대신하지 않는다. 이번 직접 실패는 v11f의 rmcp-client 테스트 E0308이다.

| 변경 상황 | 목표 동작 |
| --- | --- |
| 작업 폴더만 변경, 현재 고정본과 소비 입력 동일 | 현재 실행을 계속한다. 후속 변경은 다음 입력 후보로 알린다. |
| 고정본 또는 소비 입력이 실행 중 변경 | 영향받는 단계와 소비 결과를 무효화한다. 원래 실패·exit는 보존한다. |
| 수정 사항을 다음 빌드에 선택 포함 | 새 입력 ID와 출처를 만든다. 변경 범위와 의존 관계에 따라 재사용 또는 재실행한다. |
| 영향 범위를 판정할 수 없음 | 판정 불가 이유를 표시하고 현재의 보수적인 범위로 재검증한다. |

현재 한계는 통과 불가능이 아니라 넓은 무효화다. scripts/cargo-verification-cache.cjs의 key는 보수적인 엔진 입력, 선언·규칙, 실행 환경을 포함하며 절대 engineSourceRoot도 포함한다. 현 제품 출처 규약은 SOURCE.json과 비 Rust 파일을 포함한 엔진 소스 전체에 묶인다. 따라서 테스트 한 줄 또는 새 고정본 경로도 결과 재사용에 영향을 줄 수 있다. Cargo 컴파일 캐시와 통과 결과 캐시는 별개이며, 새 결과 키가 실제 의존 라이브러리 전체의 재컴파일을 뜻하지는 않는다.

### 범위와 선택할 정책

입력·결과·실행 수명 계약은 Windows x64, Linux x64, macOS ARM64 공통 대상으로 설계한다. PATH 대소문자, MSVC/ABI, Chrome 종료와 경로 길이는 OS 경계에서 구현한다. 이번 실측은 Windows x64 로컬 데스크톱뿐이다. 공통 변경에는 Windows 회귀를 포함하며 Unix 검증 없이 Unix 지원 수용을 주장하지 않는다. 사용자 데이터, 전역 Python·포트 설정, 배포·게시 권한은 변경하지 않는다.

정책은 고정본을 유지하면서 확인 가능한 의존 범위만 재실행하는 방식이다. 기존의 모든 현재 변경 포함 요청을 다음 실행의 선택 범위로 명시할 수 있지만, 실행 중 발견한 수정을 자동 추가하지 않는다. 새 수정 반영은 새 입력 ID로 한다. 이번 구현은 감사를 마친 소스 기반 검사에서 소비하지 않는 제품 payload만 개별 Cargo 결과 키에서 제외한다. 전체 소스·도구·환경 정체성은 유지한다. 의존 범위 기반 재사용이 아직 구현·검증되지 않은 영역과 제품 바이너리 재사용은 기존 전체 범위를 유지한다.

실행 순서는 입력 선택 → 작은 환경 probe와 변경 테스트 타입 검사 → 준비가 끝난 엔진/검사/패키지 단계 → 최종 바인딩·계정/여섯 호스트 검사 → 설치 → 정리다. Python 오류는 SDK 소비자, 브라우저 오류는 UI 소비자처럼 실패한 의존 경로만 막는다. 독립적인 준비와 검사는 즉시 진행하되 Cargo를 공유하는 무거운 컴파일은 겹치지 않는다. 의존 계약·입력/결과 정체성은 root가 소유하며 현재 별도 실행 담당자를 시작하지 않는다.

### 검증과 성능 평가

먼저 기존 build/preparation, cache lease, feature-preservation 테스트를 재사용해 변경된 경계에 회귀를 추가한다. 반드시 구분해 검사할 경우는 작업 폴더만 변경, 고정본 변경, 테스트 전용 수정, 공통 production 수정, lockfile/features/toolchain/환경 변경, 같은 내용의 경로 이동, 미해결 include/build.rs 입력, 마지막 검사 실패와 비정상 종료, 브라우저 연결·종료 실패다. 테스트 전용 수정이 실제 제품 입력에 영향을 주는 경우에도 재사용하면 안 된다. 타이핑 검사 성공은 OAuth 기능 테스트나 최종 패키지 검증의 대체가 아니다.

현재 Windows 관측값 4시간 3분과 주요 네 검사 준비 비율 94.8%를 기준으로 환경 오류 발견 시점, Cargo 준비 실행 횟수·시간, 결과 cache hit/miss와 이유, CPU/디스크/lease 대기, 종료 지연, 전체 경과 시간을 비교한다. 같은 고정 입력으로 차가운/따뜻한 실행을 구분해 측정하고 겹친 시간을 합산하지 않는다. 목표는 회피 가능한 오류를 긴 소비 단계 전에 검출하고, 일치하는 성공 결과·컴파일 준비를 중복 실행하지 않는 것이다. 실제 축소 시간은 변경 후 측정하며 사전 절감률을 보장하지 않는다.

이번 계획 작성은 docs/ops/development.md와 docs/playbooks/build.md의 기존 preflight 지침을 기반으로 한다. 채택 후 동작 변경은 upstream preservation/build·artifact lifecycle의 해당 architecture owner와 feature inventory에 반영하고 관련 스크립트·검사를 함께 연결한다. 공통 Agent 지침 변경이 필요하면 instructions/README.md 유지 경로를 따라 maintained library와 활성 설치본을 일치시키며, 지침 작성만으로 자동화가 구현됐다고 보고하지 않는다.

### 구현 결과와 수용 범위

실행 기록: `artifacts/tasks/CR-01-build-legacy-cleanup/runs/build-improvements-r1`. Windows x64 로컬에서 관련 검증을 완료했으며 Linux/macOS 실행은 검증하지 않았다. 이번 실행은 제품 전체 빌드, 실제 엔진 테스트 컴파일, 계정·여섯 host 검사 또는 사용자 프로필 설치를 수행하지 않았다. v11f 고정본과 원래 E0308 실패를 수정하거나 성공으로 바꾸지 않았다.

- 입력 판정: 기존에 측정한 전후 snapshot을 비교해 소비 경로의 추가·수정·삭제와 루트 변경을 보고한다. 고정본 밖의 후속 작업 변경은 해당 snapshot을 무효화하지 않는다. 판정 자체가 제품 바이너리 재사용을 허가하지 않는다.
- 사전 검사: 실제 SDK import·생성 모델 경로, Node 자식의 Python/Cargo 실행, 작업 폴더 안의 임시 쓰기·읽기·삭제, 사용 가능 용량을 검사한다. SDK Python 3.10과 `tomllib`이 필요한 빌드 Python 3.11 이상을 분리했다. 실제 Windows에서는 SDK 3.10.21, 빌드 Python 3.13.15, Cargo 1.95.0을 확인했다. 측정된 compiler 증가량이 없으면 안전한 용량이라고 단정하지 않고 unknown으로 남긴다. 공유 module cache 등록부는 긴 컴파일 전에 연다.
- 조기 컴파일 준비: 등록된 wrapper의 검토된 명령과 파일 해시에서 test-type 준비를 계획한다. 실제 inventory 검사에서 준비 32개, 미해결 매핑 0개를 확인했다. 변경 crate 우선순위와 같은 명령의 중복 제거를 적용하며 features 합집합은 만들지 않는다. 미등록·변경 wrapper는 명시적으로 막는다. 타이핑 성공과 실제 테스트 성공은 별개다.
- 재개와 키: 검사가 끝날 때마다 현재 입력·런타임·로그를 다시 확인해 개별 성공 증거를 게시한다. 뒤 단계가 실패해도 앞선 증거를 재사용할 수 있고, 전체 gate는 재사용한 결과까지 최종 재검증한다. 감사를 마친 아홉 source-only wrapper의 Cargo schema 5 키는 소비하지 않는 검증된 제품 payload 필드만 제외한다. wrapper·공통 helper가 바뀌거나 receipt가 불완전하면 보수적인 기존 키로 돌아간다.
- 최종 연결과 보호: package/account/여섯 host/설치 gate를 유지한다. 공통 임시 디렉터리는 자신이 끝낸 execution 참조만 해제한다. 다른 실행·설치·복구·증거 참조와 종료가 불확실한 후속 producer의 보호를 유지한다. 브라우저 연결·종료 관련 4번은 구현 범위에서 제외했다.

중간 재시행 원인은 새 snapshot 확인 단계의 fixture 기대값, fake 공유 cache 소유 경계, 테스트용 helper 파일 누락과 실행 환경의 Python 선택이었다. 실패 기록을 보존하고 해당 원인만 수정했다. 특히 SDK interpreter를 빌드 PATH 전체에 앞세우는 초기 구현이 Python 3.10으로 TOML parser를 실행시키는 문제를 발견해, 두 환경의 실제 child 실행을 각각 검증하도록 수정했다. 현재의 모의 cache 측정은 전체 제품 빌드의 시간 절감 측정이 아니다.

임시 배포 run 네 개는 실행 종료·독립 증거 보존 후 Azrael `project_inventory` → `project_cleanup_review` → `project_cleanup_apply`로 삭제했고 네 경로 모두 remaining:false를 확인했다. 테스트를 위해 일부러 남긴 synthetic 소비 참조도 해당 assertion 종료 뒤 해제했다. 삭제된 JS lifecycle metadata 네 개를 실제 부재 확인 후 정리했다. 최초 snapshot 임시 묶음도 같은 도구 경로로 삭제했다. 결과는 `reports/fixture-cleanup-results.json`, `reports/fixture-lifecycle-finalization.json`에 보존한다. 최종 작업 증거는 향후 새 고정 입력 빌드의 수용 또는 취소 시 다시 검토한다.

이번 작업의 공유 파일 여섯 개는 작업 시작 시점부터 HEAD와 달랐고, 다른 작업의 staged import 33개도 존재한다. 이를 섞거나 기존 index를 바꾸지 않기 위해 작업 커밋은 만들지 않았다. 근거와 파일 목록은 `reports/completion.json`에 남겼다. 남은 배포 작업은 새 입력의 선택·고정과 정상 전체 빌드/필수 gate/설치이며, 이번 구현 수용과 혼동하지 않는다.
