마지막 두 행은 집계이므로 앞의 개별 항목에 더하지 않는다. appserver는 첫 실행보다 30분 07초 짧았지만 warm 출력과 경로·환경 차이를 포함하므로 같은 조건의 개선율은 아니다. 재개한 session-handoff 12분 17초도 첫 하위 Cargo 35.5초와 범위가 다르다. wrapper의 준비·컴파일·소유권 처리 시간을 나누는 추가 계측이 필요하다.

## 6. 시간 최적화 권고

### 우선순위 1: 완료·중단 경계와 결과 재사용

- 하위 프로세스의 실제 종료, 선택 검사 결과, 관리 기록 finalization, 상위 인수 완료를 각각 기록한다. 한 단계의 손실이 전체 검증 재실행으로 번지지 않도록 완료된 검사 단위 증거를 고정 입력·환경·실행 규격에 바인딩한다.
- 이번 건에서 상위 미완료 구간 52분과 후속 native 22분이 조사 대상이다. 이 전부를 제거할 수 있다는 측정은 없다. 실제 중단 원인과 비용을 분리한 뒤 재사용 범위를 결정한다.
- 실제 실행 결과가 없는 unknown을 성공으로 바꾸거나 활성 Cargo/catalog 잠금을 해제하는 방식은 제외한다.

### 우선순위 2: 테스트용 컴파일의 입력 일관성과 타깃 묶기

- 기존 shared Cargo owner·stable source helper를 우선 활용한다. 사전검사와 최종검사가 동일한 source bytes라도 원본/복사본 경로, mtime, target triple, features, profile, RUSTFLAGS가 다르면 재사용이 깨질 수 있다. 실제 선택과 fallback 원인을 영수증에서 확인한다.
- 같은 crate·설정의 선택 테스트는 한 번 준비한 바이너리로 실행 가능한지 검토한다. 다른 lib/bin 또는 target이 필요한 실행까지 합치지는 않는다.
- 최초 appserver의 실제 test 본문 23초와 컴파일 중심 33분의 차이가 근거다. 원래 fingerprint/dirty trace가 없어 특정 원인이 전체 비용을 만들었다고 확정할 수는 없다.
- release 최적화 수준/LTO 또는 제품 기능을 낮추는 변경은 이 분석에서 권하지 않는다.

### 우선순위 3: 비싼 실행 전에 작은 실제 준비 검사

- npm 실행 파일을 단일 경로로 확정하고 중복 PATH에서도 선택 결과가 한 개인지 확인한다.
- 짧은 Windows 소켓 경로를 실제 downstream 도구에 전달하는지, 새 실행·검증 경로가 기존 owner와 충돌하지 않는지 확인한다.
- 선택된 UI 변환이 요구하는 정확한 assets를 고정 버전에서 준비하고 작은 실제 변환을 실행한다. package.json 존재만으로 준비 완료로 보지 않는다.
- tmpdir 소유 영역, 독립 실행 시 필요한 초기화, ready/unready fixture를 각각 실제 조건에 맞춘다.
- 격리 검증의 관찰 제한을 실제 AccountService 시작 규격에 맞춘다. 이미 대상 세션에서 고친 부분은 새 작업으로 중복 구현하지 않는다.
- 환경·경로 수정 구간 약 15분34초, fixture 수정 구간 약 8분06초, 시간 초과 실패 및 수정 약 9분17초가 관측된 재작업 범위다. 전부 제거 가능한 순수 낭비라고 합산하지 않는다. 일부는 필수 검사와 준비를 포함한다.

### 우선순위 4: 입력 전체 준비를 피할 수 있는 경로 선택

- 입력 불변이면 `reuseDeploymentInputs`, 지원되는 최상위 scripts 교체면 script-delta, 제품 조립 완료 후면 `preparePackagingWorkspace`를 먼저 선택한다. 원본 엔진 소스가 달라지는 현재 지원 밖 변경에는 전체 고정 준비를 유지한다.
- 전체 준비를 할 때는 두 사본 capture가 약 7분23초로 가장 크다. 독립 고정본과 변경 가능한 작업본의 계약을 유지하면서 기존 Git materialization·복사 방식을 세분 계측한다. hardlink로 변경을 공유하거나 출처 확인을 생략하는 식으로 줄이지 않는다.
- 이미 완료한 5→4회 검증 재사용은 유지한다. 추가 경로·cache 변경은 같은 입력·부하 조건에서 비교하기 전까지 절감률을 제시하지 않는다.

### 우선순위 5: 정리 작업의 임계 경로 줄이기

- 최종 검증·작은 증거 보존이 끝나면 패키지 준비 상태를 즉시 알리고, 현재 권한에 포함된 설치 후속만 시작한다. 큰 이전 실패 자료 정리가 새 결과의 준비 상태를 가리지 않게 한다.
- 이번 세션은 최종 인수 후 정리·보관 전환에 2시간37분이 걸렸다. archive mapping 자체는 2분40초였다. 다만 archive는 사용자가 선택한 보관이며 디스크 공간을 회수하지 않는다. 일반적인 삭제 대체나 무제한 보관을 기본값으로 도입하지 않는다.
- 기존 owner의 등록·검토 결과를 재사용하고, 현재 보호/참조만 fresh 검토한다. unchanged 등록을 재해시하거나 같은 payload를 중복 스캔하지 않는다. 다른 producer와 공유 catalog가 겹치면 작업별 자원 범위를 보고 조정한다.
- 이번 대화에서 수행한 EW01 약47분 삭제는 별도 작업의 실측이다. 대상 세션 2시간37분과 합산하지 않는다.

### 테스트 유지·축소 기준

테스트 지침의 기준은 이후 작업에서 내가 다시 빼먹거나 잘못 수정할 구체적인 경로다. 빌드 호출 인수, fixture 준비, 경로 전달, 패키지 바인딩과 같은 반복 작업의 최소 검사는 유지한다. 기존 owner 또는 빌드 도구가 같은 누락을 확실히 검출하면 중복 영구 테스트를 더하지 않는다. 구현/설계 수정으로 원인이 제거된 것은 이번 검증과 영구 유지 여부를 나눠 판단한다.

이 지침에 따라 테스트 개수를 먼저 줄이기보다 장시간 컴파일을 동반하는 검사가 실제로 어떤 반복 실수를 방지하는지 검토한다. 실제 IPC·세션 종료 같은 필수 계약은 작은 단위 검사로 대체했다는 이유만으로 제외하지 않는다. 소스 검사 29분의 파일별 순위가 없으므로 특정 테스트를 추가 퇴역시키겠다는 결론은 내리지 않는다.

## 검증과 제한

연속 시간표의 합계는 시작·종료 차이와 밀리초 단위로 대조했다. 직접 영수증과 세션 설명이 다르면 직접 종료·영수증 기록을 우선했다. 세션 중복/재시작 파일 6개를 같은 논리 세션으로 확인했다. 이전 다른 세션에서 이미 쓴 컴파일 시간이나 이후 EW01 개선·정리 시간을 대상 빌드 시간에 더하지 않았다. 코드 수정·실험·테스트·제품 재빌드는 수행하지 않았다.
