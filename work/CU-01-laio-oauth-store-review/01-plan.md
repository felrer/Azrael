# LAIO MCP 인증 저장·선택 결함 검토

## 목표·권한·범위
사용자가 제시한 JSON 필드 순서별 키 차이, 중복 저장 및 오래된 인증 선택 가설을 검토한다. 읽기 전용 코드·실행 정보·인증 메타데이터·SQLite 로그 조회와 메모리 재현만 수행했다. 토큰 값 출력, 외부 인증 요청, 실제 인증 변경, 빌드·설치는 수행하지 않았다. 공통 Rust 저장 의미는 Windows/Linux/macOS 공통 영향 가능성이 있으나 이번 확인 환경은 Windows x64이며 다른 OS 실동작은 미검증이다.

## 확인 근거
- 운영 문서가 지정한 현재 소스는 engine/. 실행 중 u17b/w10e의 build-info.json은 artifacts/n10a/engine을 기록하며 두 패키지의 azrael.exe 기록 해시는 동일하다. 해당 스냅샷 oauth.rs와 현재 engine의 oauth.rs 바이트는 일치한다. 실행 바이너리 자체의 전체 해시 재검증은 하지 않았다.
- oauth.rs:1054 compute_store_key는 일반 MCP 식별자를 serde_json Map 직렬화로 해시한다. enterprise 경로만 명시적 정렬 변환이 있다. tui/Cargo.toml은 serde_json preserve_order를 활성화한다. 서로 다른 feature 집합의 빌드는 필드 순서 차이를 낼 수 있다. 어떤 과거 실행 파일이 각 키를 생성했는지는 미확정이다.
- 실제 .credentials.json에 server_name=laio, server_url=https://api.liampli.com/mcp인 두 항목이 존재한다. type,url,headers 순서는 laio|00a31ac0731c6c13, headers,type,url 순서는 laio|b78268cda0267519을 만든다. SHA-256 앞 16자리 계산이 두 실제 키와 일치했다.
- FallbackFile은 BTreeMap이고 oauth.rs:886 로더는 키 정렬 순서로 순회해 최초 일치를 반환한다. 일반 laio 이름에는 현재 계산 키 일치를 강제하지 않으며 만료 시각 비교도 없다. 선택되는 00a... 항목 만료 시각은 2026-10-16T17:13:21.191Z, b782... 항목은 2026-10-19T13:41:31.966Z다. 만료 시각은 발급·저장 시각을 증명하지 않는다.
- oauth.rs:956 저장은 계산한 키에 insert만 수행한다. 다른 키의 동일 이름/주소 항목은 남는다. 삭제도 지정 키 하나를 제거하므로 중복 마이그레이션과 함께 검토해야 한다.
- Node 메모리 재현: 실제 메타데이터의 키 정렬·일치 조건을 모사하고 b782...에 합성 새 토큰을 저장해도 00a... 선택을 assert로 확인했다. 종료 코드 0. Rust 실함수 실행이나 LAIO 네트워크 재현은 아니다.
- logs_2.sqlite를 mode=ro로 조회했다. 2026-10-20 09:36:53 KST WARN codex_mcp::rmcp_client에 laio, invalid_grant 및 refresh token was rejected가 함께 기록되어 있다. 원문과 비밀 값은 내보내지 않았다.

## 판정과 제한
동일 인증이 서로 다른 키로 남고, 만료 시각이 더 이른 항목을 계속 선택하는 결함이 확인된다. 저장 자체 실패보다는 저장 식별자 불안정성과 중복 선택 결함이라는 설명이 정확하다. 이 결함은 재인증 반복을 설명하는 유력한 원인이지만 해당 로그 요청이 어느 키의 토큰을 사용했는지 직접 추적한 것은 아니다. 두 access token 모두 현재 만료 시각을 지났으며 다른 refresh token의 유효성 및 LAIO 측 폐기 원인은 확인하지 않았다.

## 수정 권고 (미실행)
1. 공통 JSON canonical 직렬화 또는 고정 필드 구조로 키를 빌드 feature와 무관하게 고정한다. 기존 키 호환을 함께 유지한다.
2. 이름·URL·소유권 경계를 지키며 레거시 중복을 해소하고, 재인증 저장 성공 후 같은 인증의 이전 항목이 다시 선택되지 않게 한다. expires_at만으로 최신 인증을 단정하지 않는다.
3. 읽기·저장·삭제·refresh의 identity/lock 계약을 함께 검증한다. local:/executor:/enterprise, file/keyring/secrets 저장소 격리를 보존한다.
4. 서로 다른 JSON feature 순서, 실제 중복 구조, 재로그인 후 재로딩, 재시작, refresh 실패/성공 및 로그아웃을 회귀 검증한다. 공통 변경에는 Windows 회귀가 필요하다.
