# Testing — 한국어 직역

> 검토용 번역이다. 활성 지침이 아니며, 영어 `testing/SKILL.md`와 같은 순서로 작성했다.

**이름:** `testing`

**설명:** 최소한의 충분한 증거와 지속적인 계약 가치를 사용하여 테스트를 선택·작성·실행·검토·통합·폐기한다. 구현 중의 테스트 결정이나 기존 테스트 묶음의 허가된 유지보수에 사용한다.

## 1. 범위와 소유권

- 합의된 작업 안에서 테스트 선택, 추가 판단, 단언, 실행 증거, 통합과 폐기를 담당한다. 기존 작업 기록을 사용하고 별도 테스트 계획이나 승인 단계를 만들지 않는다. 검토 요청은 수정이나 실행을 허가하지 않으며, 일반적인 기능 작업은 광범위한 테스트 묶음 정리를 허가하지 않는다.

- 작업 진입 및 implementation 스킬은 범위, 권한, 전체 수락과 산출물 정리를 계속 담당한다. 프로젝트 playbook은 필수 검사, 명령, 지원 플랫폼과 빌드·패키징 절차를 계속 담당한다. 해당 제약을 적용한다. 이 스킬은 이를 면제하거나 삭제 권한을 부여하지 않는다.

## 2. 최소한의 충분한 증거 선택

- 변경된 계약, 의미 있는 실패, 그리고 이를 탐지해야 하는 경계와 조건을 명시한다. 현재 수정의 입증과 지속적인 회귀 보호를 구분한다. 테스트를 생성하기 전에 기존 검사를 살펴보고, 충분한 기존 테스트는 변경 없이 재사용한다. 새로운 테스트 파일·사례·단언을 추가하지 않는 것도 유효한 결과다.

- 주장을 포괄하는 가장 작은 검사들과 프로젝트 필수 관문을 선택한다. 고정된 테스트 피라미드 대신 동작과 위험을 기준으로 선택한다. 수동 검증, 정적 분석 또는 일회용 탐침은 한정된 주장을 입증하기에 충분할 수 있다. 그러나 드물거나 중요한 결함에 필요한 반복 탐지를 대체하지는 않는다.

- 그곳에 위험이 있다면 허가된 환경에서 실제 진입점, 백엔드 또는 영속성 경계를 우선한다. 운영 환경 접근이 요구되는 것은 아니다. 실제 실행이 불가능하면 그 공백을 보고한다. 실행하지 않은 통합에 대한 대체 증거로 대규모 모의 객체 테스트 묶음을 만들지 않는다.

- 테스트 수, 커버리지 비율, 테스트와 제품의 크기 비율은 진단 신호이며 생성·유지·삭제 할당량이 아니다. 이미 요구되는 임계값과 검사를 유지한다. 중요한 권한 부여·금융·동시성·마이그레이션·프로토콜·패키징·플랫폼 위험은 이전 사고가 없어도 선제적인 보호를 정당화할 수 있다.

## 3. 지속적으로 유지할 테스트의 추가 판단과 작성

- 지속적인 결함 탐지에서 고유한 가치가 있고 그 가치가 실행·진단·검토·유지 비용을 정당화하는, 확인된 공백에 대해서만 유지할 테스트를 추가한다. 먼저 기존 사례를 확장하는 방법을 검토한다. 기존 작업 기록이나 변경 설명에 이유를 간단히 적고, 추가 판단 양식이나 별도 승인 의식을 요구하지 않는다.

- 버그 수정에 자동으로 새 테스트 파일이 필요한 것은 아니며, 성공한 일회성 탐침이 자동으로 영구 테스트가 되는 것도 아니다. 같은 지속 가치 기준을 충족할 때만 탐침을 유지한다. 일회용 자료에는 implementation의 정리·보관 규칙을 따른다.

- 기대 결과를 검사 대상 구현과 독립적으로 합의된 계약에서 도출한다. 관련 경계에서 관찰 가능한 동작을 단언한다. 해당 세부 사항 자체가 요구되는 계약인 경우를 제외하고, 자기 비교, 모의 객체 결과의 되풀이, 소스 문구·내부 호출 순서·스냅샷·목록 개수에 대한 검사를 피한다.

- 공개 동작·보안·금융·프로토콜 동작이 정확한 값, 순서 또는 직렬화에 의존한다면 이를 유지한다. 취약한 테스트를 피한다는 이유로 유효한 기대값을 약화하지 않는다. 모의 객체나 보조 코드가 커지는 것은 경계·픽스처·탐침을 재검토할 이유이며, 또 다른 보조 코드 테스트 계열을 생성할 이유가 아니다.

## 4. 실행과 증거 재사용

- 비용이 큰 실행 전에 선행 조건을 확인한다. 입력 식별 정보, 환경, 출처와 주장에 대한 검증 범위가 여전히 충분할 때만 이전 결과를 재사용한다. 입력 변경, 상충하는 증거, 불확실성 또는 필수 관문이 있으면 영향을 받는 검사를 다시 실행한다. 테스트 준비는 의존성을 컴파일할 수 있지만 별도의 제품 빌드를 허가하지는 않는다.

- 선택한 테스트가 실제로 실행되었는지 확인하고 실제 종료 코드와 최종 결과를 살펴본다. 일치 항목 없음, 테스트 0건 성공, 건너뛴 대상, 진행 중인 세션 또는 성공한 도구 호출은 동작 검사 통과가 아니다. 수정 방법을 선택하기 전에 실패를 제품·기대값·테스트·환경 문제로 조사한다.

- 단언이 결함을 탐지하는지에 대한 구체적인 불확실성을 해소할 때 집중된 통제 결함이나 실패·성공 검사를 사용한다. 일괄 변이 테스트 캠페인이나 유용한 기존 테스트에 대한 의례적인 재입증을 요구하지 않는다. 지침이나 스킬의 문구 검사는 에이전트 동작의 변화를 입증하지 않는다. 그 효과를 주장하기 전에 관련 대화를 검증한다.

- 의도한 지원과 실제 검증을 구분한다. 필요한 플랫폼 회귀 검증을 유지하고, 호스트 결과를 다른 OS·CPU·ABI·로컬/원격 환경으로 확대 해석하지 않는다. 필요한 환경을 이용할 수 없으면 계약을 약화하는 대신 공백으로 보고한다.

## 5. 유지·통합·폐기

- 현재 계약과 수명주기 비용 대비 고유한 보호를 기준으로 기존 테스트를 판단한다. 유지, 통합, 재작성 또는 이동, 폐기된 계약의 퇴역, 중복되거나 보호하지 않는 테스트의 제거, 불확실한 결정의 보류 중에서 선택한다. 이름, 연식, 최근 실패 또는 비슷한 커버리지로 그 결정을 확정할 수는 없다.

- 중복이라고 주장하려면 남길 검사를 명시하고 필요한 입력·경계·실행 조건에서 동등한 결함 탐지를 입증한다. 통합은 의미 있는 사례·단언·격리·진단을 유지해야 한다. 일회성 실행 성공은 동등한 반복 보호의 충분한 증거가 아니다.

- 계약의 제거 또는 대체가 합의된 범위 안에 있고 호출자·호환성·복구·필수 검사가 더 이상 그 계약을 필요로 하지 않을 때만 폐기한다. 오래된 테스트만을 위해 폐기된 동작을 복원하거나, 실패를 잠재우기 위해 유효한 계약을 삭제하지 않는다. 불확실한 보호는 유지하고 재검토에 필요한 증거나 소유자 결정을 명시한다.

- 실제 사용 주체를 확인한 뒤에만 테스트 전용 보조 코드·픽스처·등록을 제거한다. 남은 검사가 계속 연결되어 의미 있는 사례를 실행하는지 검증한다. 유지되는 테스트 소스에는 소스 변경 권한을 적용하고, 일회용 실행 출력에는 해당 산출물 소유자의 절차를 적용한다. 유지되는 소스를 생성된 정리 자료로 취급하지 않는다.

## 6. 보고와 종료

- 기존 작업 기록에 영향을 받는 계약, 선택한 증거, 테스트 유지 또는 폐기 이유, 실제 실행 범위와 종료 코드, 남은 보호, 확인한 환경과 공백을 기록한다. 필요하면 상세 로그를 연결한다. 제안한 발견 사항과 적용한 변경을 구분하고, 측정한 절감과 예상 절감을 구분한다.

- 일회용 탐침이나 증거를 해제하기 전에 결과를 검토하고 실패를 진단하며 필요한 재검사를 수행한다. 그런 다음 기존 정리 소유자와 보관 규칙을 사용하고 실제 제거를 확인한다. 테스트 통과만으로 보호된 자료의 삭제가 허가되는 것은 아니다. 전체 완료는 기존 작업 소유자가 계속 담당한다.
