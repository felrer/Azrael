# VS Code 멈춤 및 종료 원인 조사

## 승인된 개선 범위

- 후속 요청으로 저장 경로 개선 실행 승인. ResizeObserver 수정, 빌드·설치·배포는 이번 범위에서 제외.
- Node 표준 SQLite를 재사용하여 atom별 JSON 행으로 분리한다. MCP 캐시뿐 아니라 다른 큰 atom도 작은 설정 갱신에서 제외한다. 실제 VS Code Node 24.22.1 / SQLite 3.53.4의 node:sqlite 사용 가능 확인(exit 0).
- 10ms 모음, commit 후 저장 응답, 동일 값 무기록·무통지, 다중 프로세스 트랜잭션, 이전 후 legacy 제거, reset marker 보존을 구현. 프롬프트/캐시 내용은 진단에 포함하지 않음.
- 루트는 구현/호스트 접합/통합 검증, 위임한 테스트 담당자는 실제 SQLite 독립 검증 파일을 소유. 공통 Node 호스트 경로이며 Windows를 검증; Linux/macOS 실제 실행과 설치 후 migration은 미검증.
- 유지 테스트 이유: 향후 pinned upstream 교체 시 migration·commit 대기·행 분리·초안 필터·패키지 payload 접합을 누락하는 반복 실수 방지.

## 구현·검증 결과

- 구현: atom별 JSON SQLite 행, 10ms 트랜잭션 병합, 동일 값 무기록, 조건부 record 갱신의 화면 조정 응답 보존, generic set-global-state 연결, 종료 시 drain 및 동시 close 안전성. 원래 계정 등 비-atom Memento 항목은 변경하지 않음.
- 이전: commit 후에만 legacy Memento 제거. 이전 실패·cleanup 실패·reset 뒤 재실행·다중 프로세스 갱신·실패한 batch 롤백을 실제 SQLite로 확인.

- 잠금 대기: 다른 세션의 EU01 primary-batch가 project maintenance OS lock을 점유하여 run/register가 처음 거부됨. NodePID45072 종료 observer workId04ff3837-3d71-450c-82dd-df1b716336ba가 실제 exit0을 관측한 뒤 다시 보호 검사 수행. observer 대기는 약30분이었으며, 대기 중 원인 소유자의 요청/프로세스/잠금은 변경하지 않음. 전체 UI 입력 해시 지연은 실제 소비 host/2개 자산으로 plan을 좁혀 해결.
- 결과 범위: Windows에서 공통 Node 소스를 검증. Linux/macOS 실제 실행, 새 package/build/설치 및 실제 사용자 상태 migration은 수행하지 않음. 현재 실행중 설치본은 그대로이며, 갑작스러운 종료 원인은 여전히 미확정.
- 기존 staged engine/instruction 변경을 보존하고 이번 변경만 별도 index로 분리 검토하여 작업별 commit을 수행했다. 원래 staged diff의 동일성을 확인했으며, task 제어 요청·분리 index·commit 상태 파일을 삭제하고 부재를 확인했다.

## 최초 조사 범위
- 사용자가 보고한 최근 멈춤/종료의 근거 조사. 기존 로그, 설치 코드와 SQLite 전역 상태를 읽기 전용으로 확인.
- 대상은 Windows x64 로컬 VS Code 및 설치된 Azrael 2026.0.13. 다른 OS의 증상은 검증하지 않음.
- 최초 조사에서는 제품 코드, 설정, 확장, 사용자 저장 데이터를 변경하거나 재시작하지 않았음. 후속 구현 범위는 위 승인된 개선 범위에 따름.

## 확인된 사실
- 세 창에서 실행된 확장 버전은 Azrael 2026.0.13. 설치 호스트 receipt의 sourceVersion은 26.1007.21434. 현재 checkout을 설치 코드와 동일하다고 가정하지 않고 설치 파일을 직접 확인함.
- 2026-11-01 15:27:47.846~15:28:05.863(window1), 15:28:50.933~15:29:07.246(window3)에 확장 호스트 응답 중단 후 회복.
- 이전 세션 renderer 로그는 15:52:22까지 유지되고 새 main 실행은 15:52:50. 두 멈춤과 종료 사이의 인과는 미확정.
- 전역 상태 크기 경고는 세 창에 각각 1376/1605/1561회. 합계 4542회는 경고 발생 수이며 독립 저장 횟수나 원인 증거로 해석하지 않음.
- 현재 SQLite를 node:sqlite readOnly 모드로 조회. persisted-atom-state는 UTF-8 JSON 1,250,200바이트이며 MCP 도구 캐시 686,104바이트, prompt-history 330,855바이트가 주요 구성. 이 값은 조사 시점 값이며 장애 시점 snapshot이 아님. 내용은 출력하지 않고 키와 크기만 확인.
- 설치 out/extension.js: updatePersistedAtomValue는 atom 하나 변경 시 전체 persisted-atom-state 객체를 복사하여 storage.update로 전달. 동일 값 비교/건너뛰기 없음. enqueueUpdate는 키별 직렬화이며 영속화 전 병합/디바운스가 아님. UI 통지는 변경 atom 단위이며 모든 UI 통지가 전체 1.25MB를 보낸다고 해석하지 않음.
- 같은 세션 Azrael.log의 global-error는 ResizeObserver loop completed with undelivered notifications. 창별 83/127/46회. 렌더러 native crash 증거가 아님.
- 최근 Windows Application 충돌/응답중단 이벤트, 이번 시점 Crashpad 덤프, OOM/fatal/GPU 종료 로그와 해당 세션 CPU profile을 찾지 못함. 조회한 System 전원/메모리/디스플레이 이벤트에도 해당 구간 항목 없음. 기록 부재는 해당 원인을 배제하지 않음.

## 최초 조사 판단
- 대형 전역 상태 전체 갱신은 성능 개선 후보이나 16~18초 멈춤이나 프로세스 종료의 확정 원인은 아님. 실제 hot path와 갱신 주기는 기존 로그로 귀속할 수 없음.
- ResizeObserver 오류도 별도 화면 문제 후보. 종료 원인으로 단정할 수 없음.
- 직접 원인 확정에는 재발 시 같은 창/프로세스의 CPU profile, 프로세스별 메모리, 종료 이벤트/덤프가 필요. 상태 갱신 atom별 크기/빈도/대기시간을 내용 없이 계측하면 저장 부하 가설을 검증할 수 있음.
- 우선 권고는 재현 계측이며, 저장 분리/동일 값 생략/갱신 병합과 UI 레이아웃 수정은 후속 수정 승인 후 별도 검증 필요. 현재 진단만으로 캐시나 대화 데이터를 삭제하지 않음.
