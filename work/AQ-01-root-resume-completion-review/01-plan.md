# 세션 재개 요청의 완료 플래그 설명 검토

## 목적·범위·권한

대상: `azrael://threads/01a13379-dd79-7fa3-9515-9bf6dae83765`. 완료 플래그 없이 30분씩 기다렸는지 확인하고, 재개 도구 설명의 부족한 부분을 검토한다. 조사와 작업 기록 작성만 수행한다. 코드·공유 지침·설치·대상 세션 상태 변경은 요청 범위에 포함하지 않는다. 미결 요구사항은 없다.

대기 계약은 플랫폼 공통 의미를 가지며, 이번 증거는 Windows의 로컬 OpenAI 세션이다. 원격 신호 전달이나 다른 OS의 수용 여부는 검증하지 않는다. 요구 대상, 소스 설명 검토, 실제 실행 증거를 구분한다.

## 결론과 실제 세션 근거

완료 플래그를 연결하지 않은 30분 대기라는 가정은 이 세션의 실제 호출 기록과 일치하지 않는다. 총 9회의 `defer_root` 호출 모두 `wake_on`을 포함했다. 4회는 필요한 자식 에이전트 종료, 5회는 등록된 외부 작업 종료를 선택했다. 30분 예약 3회 모두 `wake_on.work_ids`가 있었다. 에이전트만 선택한 예약은 다음 실행을 여는 출처 조사 결과를 기다렸으므로 외부 작업 ID를 함께 넣지 않았다는 사실만으로 누락이라고 판단할 수 없다.

## 설명 평가와 제안

현재 `engine/codex-rs/core/src/tools/handlers/multi_agents_spec.rs:16`의 `AZRAEL_ROOT_DEFER_GUIDANCE`는 외부 작업 시작 전 등록, producer의 terminal signal, `wake_on.work_ids` 선택, timer fallback, 실패·중단도 종료라는 의미를 설명한다. `work_completion.rs:56`도 실제 종료 신호·재개 후 상태 확인·기한 도달 시 실제 결과와 신호 누락 확인을 명시한다. 핵심 계약이 없는 상태는 아니다. 실제 세션의 개발자 조정 지침에도 완료 이벤트 대기, 다음 단계에 필요한 대상 선택, 재개 후 상태 확인이 있었다.

다만 설명의 실행 예시는 개선할 수 있다.

1. `defer_root`의 구체적 JSON 예시는 에이전트만 다룬다. 외부 작업에도 `create` 응답의 `workId`/`signalPath`를 받아 producer가 실제 종료 시 성공·실패 신호를 기록하고 `wake_on.work_ids`로 선택하는 연결 예시를 추가하는 것이 좋다. 기록 생성만으로 프로세스에 자동 연결되지 않는다는 점을 한 문장으로 명시한다.
2. `instructions/examples/delegation.md:42`도 에이전트 예약만 보여준다. 동일한 외부 작업 예시를 연결하고, 상세 producer helper 사용법은 기존 `docs/ops/development.md:392`에 맡긴다. 설명과 예제의 중복 확장은 피한다.
3. `resume_after_ms`는 완료까지 강제로 기다리는 시간이 아니라 신호가 없을 때 다시 점검하는 상한이다. 이 의미를 긴 본문뿐 아니라 해당 인자 설명에도 넣으면 호출 시 오해를 줄인다.
4. 재개된 작업이 `running`이면 실제 producer 생존·진행·신호 실패를 필요한 범위에서 확인하고, 다음 점검 간격의 근거를 기록하도록 설명한다. 이 세션은 그런 확인을 수행했지만 반복되는 30분의 적절성까지 입증하지는 않는다.
5. 단계 종료가 다음 작업을 열 때에는 해당 단계의 독립 완료 기록을 선택할 수 있는지 판단한다. 전체 pipeline 종료만 필요한 경우 기존 단일 신호가 적절하다. 단계 진행 메시지가 자동으로 root를 깨우는 것으로 설명해서는 안 된다.

예시 형태: `work_completion.create` → 반환된 `signalPath`에 producer의 실제 종료 신호 기록 → `defer_root`에 `{"resume_after_ms":1800000,"reason":"검증 종료 결과가 후속 확인에 필요함","wake_on":{"work_ids":["<반환된 workId>"],"condition":"all_terminal"}}` → 재개 후 `work_completion.status`. producer 구현은 기존 `scripts/complete-work.cjs`와 운영 문서 절차를 재사용하는 것이 좋다.
