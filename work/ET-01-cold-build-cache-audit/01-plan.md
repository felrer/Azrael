# 전체 캐시 재생성과 사용자 프로필 설치

## 승인된 전체 캐시 정리와 실행 순서

- 추가 승인 범위: 같은 물리 경로를 서로 다른 generic native 그룹이 중복 주장하는 경우, 완결 구성·각 소유자·현재 identity·생성 근거·참조/보호/예약·외부 증거와 fresh token을 검증한 뒤 하나의 소유 그룹으로 원자 통합한다. 원래 그룹/항목 기록은 독립 증거와 durable 감사 이력에 보존한다. 통합 자체는 파일을 삭제하지 않으며 이후 일반 검토·명시적 삭제를 사용한다.
- 작업 분담: root는 계약·문서·feature inventory·실제 삭제 및 최종 수용을 맡고, duplicate_claims_fix는 native 모듈/최소 dispatch/관련 회귀/고정 도구 빌드, cache_consumer_owner는 현재 캐시와 교차 프로젝트 소비자 조사를 맡는다. 새 native 도구가 준비되는 동안 독립 캐시 정리 준비를 진행한다. 무거운 Rust 검증은 한 실행만 사용한다.
- 플랫폼: 정책과 native 통합은 공통 로직이며 실제 검증·삭제 대상은 Windows x64 로컬 NTFS다. Linux/macOS의 실행 수용은 별도다. 설치된 도구·실행 중 런타임·계정/사용자 데이터·고정 upstream 원본은 재생성 빌드 캐시로 분류하지 않는다.

- C: 가용 공간은 조사 시 약18GB다. 주 작업 사본의 `engine/codex-rs/target`은 250,065개 파일까지만 집계해도 196,563,699,304 logical bytes이며, 상한에서 조사를 멈췄다. 이는 현재 물리 점유·새 빌드의 최소 필요량·삭제 승인량이 아니다. 집계 중 다른 Rust 검사도 실행 중이었으므로 그 실행 경로를 삭제하지 않았다.
- 기존 target을 남기고 새 전체 캐시를 만들려면 양쪽을 동시에 저장할 여유가 필요하다. 현재 여유만으로 전체 빌드와 native 검사·추적의 성공을 기대해 시작하지 않는다.
- 사용자가 공용 `engine/codex-rs/target` 초기화를 승인했다. 다른 세션의 다음 Rust 검사도 재컴파일하는 영향은 설명했다. 현재 중복 소유권 등록이 기존 owner의 삭제 가드에 차단된다. 원본 소스, 설치 런타임, 계정과 사용자 상태는 해당 target 범위에 포함되지 않는다. 활성/불명확한 참조를 승인만으로 우회하지 않는다.
- 대안: 공용 target을 유지하고 C:의 다른 공간을 먼저 확보한다. 이 작업의 기존 캐시 정리 권한을 사용자 데이터나 무관한 경로 삭제로 확장하지 않는다.

- 목표/권한: 최신 선택 입력을 Windows x64 로컬 환경에서 빌드하고 일반 사용자 VS Code 프로필에 설치한다. 사용자는 기존 캐시 재활용 없이 전체 캐시 재생성, 빌드 전부터 세밀한 감시, 미사용 캐시 부분 정리를 승인했다. 원격 게시·기능 제거는 제외한다.
- 재빌드 방지: 실제 소비자 환경·경로·의존성·출처·검사 선택과 공간을 먼저 확인하고 입력을 고정한다. 이후 변경은 섞지 않는다. 제품 컴파일은 한 번만 시작하며 실패 없는 실행을 보장한다고 주장하지 않는다.
- 감시: 프로세스 계보와 캐시별 파일 열기/읽기/쓰기, owner의 hit/miss·영수증을 결합한다. 변경 이벤트만으로 읽기나 미사용을 판단하지 않는다. 도구 권한·이벤트 손실·관측 범위를 사전 실증한다.
- 캐시 범위: Cargo 산출물/registry/git, 모듈, WindowControl, namespace/asset, 검사 결과, npm/Bun, 준비 중간물을 조사해 실제 선택 경로를 기록한다. 설치된 도구와 고정 외부 원본은 캐시 재사용과 구분한다.
- 정리: 묶음 내 일부 보호를 전체 영구 보관 이유로 삼지 않는다. 실제 소비 범위와 owner를 확인해 지원되는 분리/참조 해제를 거친 뒤 미사용 부분을 검토·삭제한다. OS 잠금·불명확한 소유·실행 중 소비자를 우회하지 않는다. 한 빌드의 미접근은 전역 불필요의 증거가 아니다.
- 순서: 감시/용량 사전 검사 → 소유 출력 등록 및 새 캐시 경로 확정 → immutable 입력 및 소스 도구 준비 → 영향 범위 검사와 제품 빌드 → 정확한 패키지·필수 host 수용 → 사용자 프로필 설치·영수증 확인 → 미사용 생성물 owner 정리.
- 검증: 실제 종료 코드, 전체 경과 시간과 중복 실행 여부, 캐시별 관측/불확실성, 설치·원본 Codex/설정 보존, 삭제 실제 부재를 남긴다. Linux/macOS 수용은 주장하지 않는다.
- 초기 관측: C: 여유 19,077,877,760 bytes. WPR FileIO 설치, 현재 프로세스 비승격, 기존 WPR 기록 없음. 관리자 권한을 추정하거나 권한 경계를 우회하지 않는다.
- 기존 경로/운영을 재사용하는 작업이며 제품 설계 변경은 현재 없다. 구현이 필요해지면 기존 owner 경계와 필수 검사를 따른다.

## 캐시 무효화 진행 상태

- p/q의 완성된 패키지를 검증한 뒤 companion-tool 참조만 해제했다. p의 실패와 q의 종료 미확인 결과는 유지했다([21](21-module-cache-invalidation.json)). 레거시 모듈 구성원의 생략된 생성물 표시는 실제 출력 해시 검증 뒤 지원 writer로 보완했다. 첫 writer 오류가 부분 commit 뒤 발생했음을 현재 revision으로 확인하고 재적용하지 않았다([24](24-module-metadata-upgrade.json)).
- 검증 캐시 lease의 정확한 생성 시각이 현재 Windows kernel boot보다 이전임을 CIM으로 확인해 전체 이전 프로세스 트리 종료를 증명했다. 기존 recoverLease로 해제하고 기존 prune으로 결과 슬롯 1개를 삭제했다. 잔여 슬롯 0, deferred 0이다([29](29-verification-lease-retirement.json), [30](30-verification-cache-prune.json)). 이전 배포의 unknown 결과는 변경하지 않았다.
