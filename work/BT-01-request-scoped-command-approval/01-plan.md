# 전체 액세스의 위험 명령 사용자 승인 검토

상태: draft. 설계 검토만 승인된 작업이다. 제품 코드·설정·설치 상태는 변경하지 않는다.

## 목표와 범위

전체 액세스에서 승인 불가 정책 때문에 차단되는 명령을 사용자 승인으로 연결한다. 승인 유효기간은 사용자의 한 요청 동안으로 제한한다. 검토 산출물은 원인, 재사용 경로, 구현 제안, 미결정 사항과 검증 조건이다.

요구사항의 의미는 공통 플랫폼 범위다. 명령 판별은 실행 대상 OS·셸 의미에 종속된다. Windows PowerShell/CMD와 POSIX 셸을 구분하고, 로컬·원격 환경의 승인을 공유하지 않는다. 현재 소스 검토와 제품·설치 검증은 별개이며, 이 작업에서 어느 플랫폼의 새 동작도 실행 검증하지 않았다. 현재 지원 수용 범위는 프로젝트의 Windows 한정을 유지한다.

## 현재 소스에서 확인한 동작

- `docs/ops/development.md#source-and-state`에 따라 검토 대상은 `engine/`이다. 실행 중인 창의 릴리스는 확인하지 않았다.
- `docs/architecture/auto-review.md`는 전체 액세스의 승인 정책을 `never`로 규정한다. `scripts/test-auto-review.cjs`도 원본 UI의 전체 액세스 매핑을 `never`로 검사한다.
- `engine/codex-rs/core/src/exec_policy.rs::render_decision_for_unmatched_command_for_platform`은 위험 명령에 대해 `Never`이면 Forbidden, `OnRequest`이면 Prompt를 반환한다. 샌드박스가 비활성화되어 있어도 동일하다. 일반 명령은 unrestricted + OnRequest에서 Allow다.
- `exec_policy_tests.rs`에는 danger-full-access + OnRequest의 위험 명령 승인 요구와 Never의 차단을 구분하는 기존 테스트가 있다. 이번 검토에서 테스트를 실행하지 않았다.
- `shell-command/src/command_safety/`에 기존 위험 명령 판별기가 있다. POSIX 강제 rm, Windows PowerShell 강제 Remove-Item 및 별칭, CMD 강제 del과 재귀 rmdir 등을 다룬다. 모든 삭제·스크립트를 완전하게 판별하는 시스템이라는 근거는 없다.
- 명시적 forbidden 규칙과 승인 불가에 따른 차단은 구분된다. 모든 Forbidden을 Prompt로 바꾸면 정책 의미가 달라진다.
- `core/src/tools/approvals.rs`와 `sandboxing.rs`는 사용자 승인과 세션 승인 캐시를 제공한다. 명령 캐시 키는 환경, 명령, 작업 경로, tty, 추가 권한 등을 포함하고 호출부는 정책 fingerprint도 반영한다. `ReviewDecision`에는 Approved와 ApprovedForSession이 있지만 ApprovedForTurn은 없다.
- `app-server-protocol/src/protocol/v2/item.rs`와 `app-server/src/bespoke_event_handling.rs`에도 acceptForSession이 연결되어 있다. 새 요청 범위 승인은 프로토콜과 UI의 표시·전달까지 연결해야 한다.
- `extensions/azrael-ex/src/chatSession.ts`의 별도 채팅 호스트 후보는 Full access를 never로 고정하고 검증한다. 검증된 전체 액세스 턴에서는 들어온 명령·파일 승인 요청을 자동 수락한다. 이 후보를 지원 대상으로 포함하면 고정값·readback과 자동 수락을 함께 수정해야 한다. 이를 현재 설치 UI의 동작으로 단정하지 않는다.
- `core/src/session/root_resume.rs`는 새 재개 turnId와 기존 root_turn_id를 구분한다. 단일 실행 턴이 사용자 질문의 전체 수명과 일치한다고 가정할 수 없다.

## 구현 제안

1. 전체 액세스의 샌드박스 해제는 유지하고 승인 정책을 `on-request`, 위험 명령 리뷰어를 사용자로 연결한다. 기존 execpolicy 판별·승인 경로를 재사용한다. 단순히 exec_policy의 Forbidden 반환을 모두 완화하지 않는다. 조직 요구사항·명시적 forbidden·실행 환경 제한은 별도 제약으로 유지한다. 허용 정책이 never로 제한된 환경은 충돌을 표시하며 묵시적으로 변경하지 않는다.
2. 현재 요청 범위 승인 결정을 추가한다. 예: 내부 `ApprovedForRequest`, app-server `acceptForRequest`. 이는 제안 이름이며 기존 세션 승인 의미를 바꾸지 않는다. 위험 명령 카드에는 한 번 허용 / 이 요청 동안 허용 / 거절을 제안한다. 이 흐름에서 영구 prefix 규칙 저장이나 세션 전체 승인을 기본 대안으로 제시하지 않는다.
3. 엔진이 사용자 요청의 승인 범위를 소유한다. threadId와 요청 식별자 및 기존 명령·환경·권한·정책 키를 결합해 캐시한다. 에이전트나 UI가 임의로 승인 범위를 지정해 확장하지 못하게 한다. 완료·취소·새 요청·권한 또는 환경 변경 때 만료한다. 취소 뒤 도착한 오래된 승인 응답은 실행에 사용하지 않는다. 초기 구현은 재시작 후 재승인을 제안한다.
4. 승인 재사용 범위는 같은 사용자 요청 안에서 승인한 명령과 대상에 한정한다. 다른 경로 삭제는 새로 승인받는다. 명령 문자열이 같더라도 변수·glob·외부 스크립트 등으로 대상이 바뀔 수 있으면 문자열 일치만으로 재사용하지 않는다. 안정적으로 범위를 고정하지 못하는 호출은 매번 승인한다. 단순 `rm`/`Remove-Item` prefix 승인을 사용하지 않는다.
5. 위험 명령의 사용자 승인에는 현재 hooks·Guardian 우선순위와의 관계를 명시해야 한다. 일반 승인에서 기존 경로를 유지하되 이 기능이 요구하는 실제 사용자 승인을 자동 hook allow나 Guardian 판정이 대체하지 않도록 구현한다. 기존 Auto-Review 거절을 사용자 승인으로 자동 전환하는 기능은 이 제안에 포함하지 않는다.
6. 공통 엔진의 승인 판단과 실제 실행 직전 확인을 소유 경계로 삼는다. UI는 요청과 선택을 전달하며 캐시만으로 권한을 결정하지 않는다. 셸·unified exec와 대화형 stdin 등 실제 진입 경로의 적용 범위를 조사해 일치시킨다. MCP·Python 등 모든 도구의 삭제 감지를 보장하는 범용 기능으로 확대하지 않는다.

## 합의된 범위

- 승인 재사용은 같은 요청의 승인한 명령·대상에만 적용한다. 같은 요청의 모든 삭제를 일괄 허용하지 않는다. 이 합의는 설계 범위이며 구현 실행 승인을 뜻하지 않는다.
- 자동 재개·압축은 같은 사용자 요청의 연속으로 취급해 승인을 유지한다. 새 사용자 작업 요청·작업 완료·취소에서는 만료한다. 내부 turnId 변경이나 압축만으로 승인을 만료시키지 않으며, 자동 재개 대기를 작업 완료로 취급하지 않는다.

## 구현 준비에서 구체화할 사항

- 작업 중 추가 메시지가 기존 작업의 보충인지 새 작업 요청인지와 별도 질문의 격리는 기존 요청 수명 계약과 대조해 구체화한다. 자식 세션으로의 승인 자동 상속은 최초 구현에서 하지 않는 안을 제안한다. 이 세부 제안은 아직 합의된 범위와 구분한다.
- 강제 삭제 명령 사용을 원한다면 현재 AGENTS.md의 강제 삭제 금지와 모델에 주입되는 안내도 함께 정합성을 검토해야 한다. 실행 승인과 에이전트의 명령 제안 허용은 별개다. 이번 검토에서는 공유 지침을 수정하지 않는다.

## 구현 시 보존과 검증

일반 명령 무승인 실행, 기존 세션 승인과 정책 변경 의미, 조직 제한, Auto-Review의 제공자 범위, Computer Use 앱 승인과 분리, 거절 후 미실행을 보존한다. 동작 합의 후 `docs/architecture/auto-review.md`의 전체 액세스 계약과 관련 feature inventory를 변경한다. UI 구현 전 프로젝트 UI 지침을 적용한다.

최소 검증은 전체 액세스의 일반 명령 실행 / 위험 명령 사용자 승인 전 미실행 / 승인 후 실행 / 거절·취소·시간 초과 미실행 / 같은 요청의 범위 일치 재사용 / 다른 대상·환경·다음 요청 재승인 / 오래된 승인 응답 무효 / 영구 규칙 미저장이다. 병렬 승인 응답이 다른 요청을 허용하지 않는지도 확인한다. Windows PowerShell·CMD를 필수 회귀에 포함하고 POSIX 판별·승인 계약도 대상에 맞게 검증한다. 소스 테스트, 프로토콜 왕복, 밝은·어두운 UI, 패키지·설치 수용을 구분한다.

## 이번 검토의 근거와 한계

현재 엔진·프로토콜·호스트 후보·기존 테스트 정의를 읽어 경로를 비교했다. 위험 명령 실행, 테스트 실행, 빌드·설치·설정 변경을 수행하지 않았다. 새로운 구현·지원 플랫폼 수용을 선언하지 않는다. 미결정 사항은 제안 상태다.
