## 원인과 한계

확인된 원인은 답변 본문과 엔진의 영속 질문 해결 상태 사이의 불일치다. 복원은 일반 사용자 본문을 답변으로 추론하지 않고 `answered_async_question_ids`만 신뢰한다. 따라서 과거에 답변한 두 질문이 복원 후 미해결로 계산되어 자동 큐 전송을 막는다. UI 표시는 그 계산 결과를 따른다.

소스는 `core/src/session/mod.rs::record_user_prompt_and_emit_turn_item`에서 입력 acceptance_order가 있을 때 해결 ID를 저장하도록 되어 있다. 따라서 메타데이터가 최초 기록에서 누락됐는지, 다른 기록 경로/구버전 구성 요소를 거쳤는지, 후속 재작성에서 사라졌는지는 이번 기록만으로 확정하지 않는다. 재시작/복원이 실제 어느 시점에 발생했는지도 미확인이다. 현재 원본 세션을 변경해 재현하지 않았다.

관련 소스:

- `scripts/inject-question-queue.cjs`: `pendingQuestionCount > 0` 표시 및 자동 전송 보류.
- `artifacts/build/b13/engine/codex-rs/core/src/session/user_questions.rs:152`: from_history는 메타데이터만으로 answered 집합 복원.
- 같은 파일 `restore_user_questions`: 전체 rollout과 아직 pending인 수락 입력으로 복원.
- `artifacts/build/b13/engine/codex-rs/core/src/session/mod.rs:5183`: 답변 해결 ID 기록 생성.
- `docs/architecture/queued-compaction.md`: 자동 큐는 질문에 보류되며 명시적 send-now는 별도 경로.

## 권장 후속 조치

제품 수정 시 질문 답변 수락 → 기록 → 재시작/재연결 → 큐 조회의 통합 검증으로 메타데이터 누락 경계를 특정하고 보존해야 한다. 기존 세션은 신뢰 가능한 수락 기록에 근거한 별도 복구가 필요할 수 있다. 일반 본문을 무조건 답변으로 추론하는 변경은 현행 계약을 바꾸므로 피한다. 실제 사용자 큐의 전송·질문 철회·DB 편집은 이번 요청에서 실행하지 않는다.

분석 문서 외 제품 코드 및 영속 세션 상태 변경이 없어 아키텍처/기능 인벤토리 변경, 제품 빌드, 플랫폼 회귀 실행은 해당하지 않는다. 원본 로그와 세션은 보존하며 별도 원문 사본을 만들지 않았다.
