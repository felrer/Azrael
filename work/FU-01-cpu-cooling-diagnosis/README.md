# 실시간 멈춤 진단 모니터

Windows x64에서 Python 3 표준 라이브러리로 실행한다. 시스템 설정, 팬 속도, 전력 제한, 실행 중인 빌드에는 개입하지 않는다. 현재 체크아웃의 산출물 소유 절차를 사용하는 실행기는 다음과 같다.

직접 CPU 센서를 포함하려면 기존 `cpuz165` 서비스가 실행 중이어야 하며 관리자 PowerShell에서 실행해야 한다. 런처는 이 PC에 설치된 Python 3.13의 절대 경로를 사용한다. 일반 권한에서는 시스템 지표만 기록되고 센서 수집은 실패할 수 있다.

```powershell
node work/FU-01-cpu-cooling-diagnosis/start-monitor.cjs 1800
```

실행기가 출력한 `logs` 폴더에 2초 간격 `system.jsonl`, 임계값을 넘은 샘플의 `alerts.jsonl`, 시작·종료 상태 `status.json`이 생긴다. UTC 시각과 경과 시간, 실제 수집 간격을 함께 기록한다. `STOP`이라는 파일을 같은 폴더에 만들면 다음 수집 간격에 종료한다. 각 레코드의 flush/fsync는 마지막 기록 손실을 줄이지만 저장장치·OS 전체가 멈추면 기록 성공을 보장하지 않는다. 자동 시작이나 재부팅 후 자동 재개는 등록하지 않는다.

독립 프로세스 `watchdog.py`는 0.25초마다 스케줄링 간격을 확인하고 `heartbeat.jsonl`에 1초마다 생존 기록을 남긴다. 1초 이상 지연은 `watchdog_gap`으로 기록하며, sleep 가능성과 직전 디스크 flush 지연을 함께 남긴다. 수집기만 지연됐는지 양쪽 기록이 함께 끊겼는지 비교할 수 있지만, 양쪽 공백만으로 OS 전체 정지를 확정하지 않는다. 강제 재부팅 때는 마지막 정상 시각 이후의 값이 없는 것이며, 정상 종료 `stop` 기록도 남지 않을 수 있다. 활성 실행의 stop 부재는 정상이다.

```powershell
& 'C:\Users\felre\AppData\Local\Programs\Python\Python313\python.exe' -B work/FU-01-cpu-cooling-diagnosis/analyze.py <system.jsonl 절대경로> --heartbeat-log <heartbeat.jsonl 절대경로>
```

분석기는 각 끊김의 실제 직전/직후 샘플과 앞뒤 10초 관측값을 연결한다. 손상·미완성 행은 별도 집계하고, 공백 내부 값을 보간하지 않는다. 현재 세션에서 나중에 추가한 독립 감시는 별도 `FU-01-live-watchdog` run에 있으며, 이후 `start-monitor.cjs` 실행은 같은 로그 폴더에 함께 생성한다.

## CPUID 드라이버 직접 접근

`cpuid-sensors.py`는 설치된 CPUID 165 드라이버 바이너리를 읽기 전용으로 분석해 확인한 인터페이스를 호출한다. 새 커널 드라이버를 구현하거나 교체하지 않는다. 분석한 SHA-256과 CPU 모델(i7-10700K)이 일치할 때만 장치를 연다. MSR 읽기 IOCTL은 `0x9C402440`, 입력은 레지스터 번호 DWORD 4바이트, 출력은 low/high DWORD 8바이트다. 쓰기 IOCTL은 구현하지 않았다.

CPU 온도·패키지 전력 계산에 필요한 다섯 MSR만 읽으며, DTS validity bit가 없는 값은 온도로 표시하지 않는다. 코어별 읽기는 이 수집기 스레드의 affinity만 잠시 지정하고 복원한다. 논리 프로세서별 값은 물리 코어별 값과 구분한다. 팬·펌프 레지스터 조회는 이 CPU 수집기에 아직 구현되지 않았다.

드라이버 서비스 `cpuz165`가 실행되고 관리자 프로세스에 `SeLoadDriverPrivilege`가 부여되어 있어야 한다. 드라이버의 장치 열기 검사를 위해 이미 부여된 이 특권만 Windows API로 잠시 활성화하고 장치 열기 직후 복원한다. 특권이 없는 토큰에서는 실패하며, 계정 권한·ACL·보안 설정을 변경하지 않는다. 프로그램 자체는 서비스 시작/중지·설치도 수행하지 않는다. `--output <소유권 등록된 기존 폴더> --duration 1800`으로 실행하면 `hardware.jsonl`과 통합 수집용 `sensors.json`을 남긴다. 분석기의 `--hardware-log <hardware.jsonl>` 옵션으로 같은 시각의 시스템/독립 감시 기록과 연결할 수 있다. 2026-11-04 23:55에 실제 온도·전력 및 통합 스냅샷 수집을 검증했다. 팬·펌프 RPM은 미구현이다.

## 수집 범위와 해석

- Windows API: CPU 사용률, 물리 메모리 available/total, 시스템 commit/limit, 비페이지 커널 메모리, 프로세스 수.
- 접근 가능한 프로세스: private bytes 상위 10개와 CPU 상위 5개. 이름/PID/부모 PID와 사용량만 기록하고 명령줄·파일 내용은 수집하지 않는다. 접근 거부 프로세스 수를 명시한다. 프로세스 CPU는 전체 논리 CPU 용량 기준이다.
- 영어 PDH 성능 카운터: 물리 디스크별 queue, 평균 읽기/쓰기 지연(초), bytes/sec. 첫 샘플은 카운터 준비 상태일 수 있으며 errors를 확인한다.
- 직접 하드웨어 센서: 현재 런처는 `cpuid-sensors.py`를 사용한다. HWiNFO/HWMonitor 앱이나 공유 메모리를 사용하지 않는다. 같은 폴더의 `sensors.json`에서 센서 이름·종류·단위와 현재값을 기록한다. 접근 거부/손상된 스냅샷은 unavailable, 정상 데이터가 10초 이상 미갱신되면 stale로 구분한다. 이전 `hardware-sensors.cs`/LibreHardwareMonitorLib 경로는 PawnIO 미설치로 수집에 실패했으며 현재 런처에서는 사용하지 않는다. RPM만으로 실제 유량·정상 순환을 판정하지 않는다.
- 경보 기준: CPU 이름을 가진 온도 센서 85°C 초과, available RAM 2GiB 미만, commit 90% 이상, 디스크 평균 지연 1초 이상, 샘플 간격 6초 이상, 센서 데이터 미갱신. 일반 모니터의 경보는 원인 확정이나 다른 프로그램의 종료 명령이 아니다. 시험 부하는 아래 별도 감독기가 종료한다. 이전 진단 원본은 당시 90°C 기준으로 수집됐다.

### 85°C 초과 중지 설정

`node work/FU-01-cpu-cooling-diagnosis/start-monitor.cjs --stress`는 사용자 실행 승인 및 관리자 권한이 필요한 별도 시험이다. 현재 Windows x64 / i7-10700K / 16논리 CPU만 대상으로 한다. 이 명령은 설정만 하는 명령이 아니라 실제 부하를 생성하므로 준비가 끝난 뒤에만 실행한다.

`guarded-stress.py`는 기존 직접 센서 Reader를 재사용하며 패키지 또는 논리 CPU 중 어느 온도라도 **85°C를 초과**하면 시험용 자식 프로세스만 중지한다. 85°C 자체는 허용, 86°C는 중지한다. 다른 빌드·앱·컴퓨터 전원에는 개입하지 않는다. 경계값과 무부하 자식 종료를 검증했으며 실제 고온 부하에서의 중지는 아직 검증하지 않았다.

- 0.25초 목표 간격으로 센서를 읽고, 센서 오류·유효 온도 누락·센서 읽기 1초 이상 지연 시 시험을 중지한다.
- 시험 프로세스는 감독기의 1초 유효 기한 갱신이 끊기면 스스로 종료한다. 온도 초과 시 로그 저장보다 부하 중지를 먼저 수행한다. CPU가 실행 가능한 상태에서 적용되는 보호이며 OS 전체 정지 중의 즉시 중지는 보장하지 않는다.
- 각 단계는 유휴 60초, 최대 작업자 수로 10초/휴식 20초를 3회, 4개 작업자 60초, 8개 60초, 16개 180초, 냉각 120초다. 총 570초이며 목표 작업자 수와 실제 CPU 사용률·전력은 다를 수 있다. Python 연산 부하이므로 AVX 등 모든 종류의 최대 발열을 재현하는 시험은 아니다.
- 하드웨어 값과 단계는 `hardware.jsonl`, 일반 시스템과 독립 감시는 기존 파일에 기록한다. 제어된 중지는 센서/시험 프로세스 exit 3으로 구분하고 원인과 모든 시험 작업자의 종료 증거를 남긴다. 작업자 종료 증거가 없으면 실행 소유권을 정상 종료 처리하지 않고 보호 상태로 남긴다.
- `test_guarded_stress.py`는 온도 경계·센서 실패·실제 유휴 작업자의 종료 및 감독 갱신 만료를 검증하며, 센서 장치 읽기나 실제 부하를 만들지 않는다.

30분 실행의 JSONL은 현재 요청한 진단 결과로 수집한다. 경보 전후의 CPU/메모리/디스크/센서 변화와 빌드 시각을 함께 분석한다. 마지막 레코드 이후의 상태를 추정값으로 채우지 않는다. 센서 데이터가 unavailable이면 냉각 원인 판단은 미검증이다.

Windows 스냅샷 교체가 일시적으로 거부되면 보통 rename을 최대 10회, 20ms 간격으로 재시도한다. 계속 실패하면 `snapshot_unavailable`을 남기고 독립 `hardware.jsonl` 측정을 계속한다. 권한·속성 변경이나 강제 파일 삭제는 하지 않는다. 하드웨어 없이 실행하는 회귀 검사는 Python 실행 파일로 `-B work/FU-01-cpu-cooling-diagnosis/test_cpuid_sensors.py`를 호출한다.
