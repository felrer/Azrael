## 공용 Azrael 실행기 개편

### 요구사항과 현재 결정
앞선 비용 분석에서 공용 엔진은 후순위 조사 후보였지만 사용자는 여러 VS Code 창의 Codex 엔진을 하나로 합치고, 창이 하나라도 남으면 닫힌 창의 작업도 백그라운드에서 계속 실행하며, 혼동 방지를 위해 실행기를 Azrael로 개편·명명하는 방향을 요청했다. 현재 분석을 이 개편 설계로 이어간다. 합의된 목표는 docs/architecture/azrael-runtime.md의 공용 실행기·제품 이름 절에 target으로 반영했다. 설계 동의와 실제 구현/설치 수용은 구분한다.
- 같은 사용자·로컬 호스트·Azrael 상태 홈의 창들은 공용 엔진 하나에 연결한다. MCP·provider·code-mode 등 필요한 worker는 엔진 수와 구별한다.
- 창이 하나라도 남으면 닫힌 창의 기존 작업을 유지한다. 마지막 창까지 닫으면 상태를 저장하고 실행을 중단한 뒤 종료한다. 재실행 시 의도적으로 중단된 작업을 표시하고 수동으로 재개한다.
- 계정·모델 선택은 창별로 유지한다. 실행 중 대화의 선택은 다른 창의 계정 전환에 의해 바뀌지 않는다.
- 제품 실행기는 azrael/azrael.exe, 보조 실행기는 azrael-bridge와 azrael-code-mode-host로 명명하는 설계다. 기존 .azrael-ex 저장소와 Codex 원본 출처·라이선스·protocol/provider ID는 보존한다. 저장소 이동과 전체 Rust crate 개명은 필요조건이 아니다.
- 닫힌 창의 작업은 원래 작업 창을 다시 열어 확인·승인한다. 다른 창의 백그라운드 작업 목록으로 자동 노출하거나 승인 소유권을 넘기지 않는다. 새 승인 요청은 원래 대화 재연결을 기다리고, 기한 만료·취소·도구 연결 상실은 실제 상태로 표시한다. 같은 workspace의 창 여러 개를 구별할 수 있는 대화 ID와 durable owner context가 필요하다. 재연결이 작업을 새로 제출하거나 부작용을 재실행하지 않아야 한다. 일반 workspace 최근 대화 필터는 유지한다.
- 요청 의미는 로컬 플랫폼 공통이다. Windows x64, glibc Linux x64, macOS ARM64의 제품 계약을 유지하되 이번 실제 코드 관찰과 호스트 실측은 Windows뿐이다. 별도 사용자·원격 호스트·SSH·컨테이너 실행기를 합치지 않는다.

### 재사용 근거와 필요한 변경
현재 ordinary-runtime.cjs의 공유 registry는 extension-host 프로세스 안에서만 공유된다. 창마다 무작위 management socket과 engine process가 생긴다. 계정 선택 파일은 integrated-azrael-entry.cjs:122에서 runtime.env에 주입되며 native account processor는 공통 AuthManager를 갖는다. 한 daemon에 기존 env를 합치는 것으로 창별 독립 계정을 보존할 수 없다. 창 등록·connection context와 account runtime registry를 설계하고 thread/turn에 계정 참조를 전달해야 한다. 공용 토큰 저장소·동일 계정 refresh 잠금은 재사용한다.
Codex app-server-daemon은 사용자 홈 기반 상태·시작 잠금·PID 신원과 Windows DETACHED_PROCESS/CREATE_BREAKAWAY_FROM_JOB 실행 기반을 제공한다. app-server의 connection_closed는 연결 구독을 제거하며 바로 모든 작업을 취소하는 코드는 아니다. 실제 detached 시작·창 close 시 실행 연속성은 시험하지 않았다. upstream daemon의 update loop·remote control·graceful drain 동작을 Azrael 요구사항으로 그대로 받아들이지 않는다. 마지막 창 닫기에 필요한 저장·중단·종료와 수동 재개 marker를 별도로 연결한다.
managed daemon recovery snapshot은 성공적으로 persist된 root thread를 선택하고 일부 child/ephemeral thread를 제외한다. 이것을 전체 큐·예약·자식 실행·외부 도구 결과의 완전한 checkpoint로 해석하지 않는다. 의도적인 중단과 crash recovery를 구별하고 기존 결과 불명·중복 실행 보호를 재사용한다.

### 구현 인계와 검증
2026-10-15 실행 시작: root는 공통 계약·통합·수용을 소유한다. engine_contract는 native connection/account/daemon 경계, host_contract는 host transport/window/recovery 경계를 읽기 조사한다. runtime_identity는 platform/build/provenance의 제품 바이너리 이름과 직접 검사를 소유하며 다른 변경을 보존한다. 계정·창 계약 확정에 의존하는 공용 연결 구현은 조사 산출물을 이어받고, 이름 변경은 독립 진행한다. 무거운 Cargo 컴파일은 공유 캐시와 호스트 자원을 확인해 하나씩 실행한다. 기존 미커밋 변경 목록은 시작 시 git status로 확인했으며 이번 변경에 섞거나 되돌리지 않는다.

실행기 단일 소유: private endpoint + 시작 잠금 + PID/creation identity + protocol/version 검증. 창 lease는 실제 등록된 extension host에 묶고 management bridge·RPC·worker는 창으로 세지 않는다. 마지막 창 종료와 새 연결 경쟁은 admission에서 직렬화한다. 서로 다른 배포 버전의 동시 창은 호환 확인 없이 별도 엔진을 띄우거나 실행 중 엔진을 교체하지 않는다. 업데이트·실패 시 동작은 구현 준비에서 구체화할 항목이다.

1. 엔진과 웹뷰의 완료·유휴 대화 유지 수를 줄인다. 기존 unsubscribe/idle unload 및 webview idle 보호를 재사용한다. 세션 기록은 보존하고 재표시 때 resume한다. 큐, 예약 root resume, goals, approval, 진행 중 turn, 다른 연결 subscriber가 있는 대화는 보호해야 한다. 자동 재개 계약을 검토한 후 idle LRU나 지연을 정한다. 현재 1시간 renderer 정책의 실제 설치 수용도 남아 있다. RAM 목적의 최우선 후보이며 절감량은 미측정이다.
2. Azrael 전용 app-server 진입점을 만든다. 기존 binary를 출발점으로 CLI TUI/클라우드 전용 명령을 빌드 그래프에서 분리한다. host가 호출하는 login/features 등 관리 명령, account bridge, provenance, 기존 app-server startup 인자·arg0 sandbox 실행을 확인해 필요 기능을 유지한다. 별도 binary의 단순 이름 변경은 충분하지 않다. 가장 명확한 빌드 비용 축소 후보이며 초기 cargo 비용·재빌드 시간·binary 크기 비교가 필요하다. RAM 큰 폭 절감은 보장하지 않는다.
3. 선택적인 경량 프로필을 검토한다. 음성 미사용 확인 후 realtime/voice, 불필요한 plugin/server, analytics를 개별 비교한다. 개인별 선택으로 시작하고 현재 사용하는 Google Drive/GitHub/브라우저·MCP·skills 기능 상실을 명시한다. tool catalog의 deferred 노출과 MCP 프로세스 수명은 다르므로 도구를 숨기는 것만으로 RAM 절감을 인정하지 않는다. compile-time feature gate는 실제 공통 의존성이 분리되는지 확인한 후 제안한다.
4. 동시에 켠 VS Code 창·활성 agent 수 제한은 메모리 peak를 줄일 후보이나 대화/도구의 실제 활동 수와 함께 측정한다. configured max_concurrent_threads_per_session=120은 제한값이며 120개를 미리 실행한다는 증거가 아니다. 값을 낮추는 것만으로 현재 idle RAM이 줄었다고 주장하지 않는다. 공용 daemon의 상태·계정·보안·창별 연결·crash 범위 변경은 위 개편 설계에서 다룬다.

### 보존·후속 검증
검색/도구 실행, provider/accounts/usage, queue·compaction·root resume, approval·sandbox, reload recovery는 현재 제품 계약으로 보존한다. 장문 context와 이미지·도구 결과 복제는 heap profile 결과에 따라 제한한다. 무작정 context cap 축소는 작업 기억·정확성에 영향이 있어 현재 추천하지 않는다.
후속 승인이 있으면 먼저 동일 대화 수/입력/캐시 상태로 cold idle→긴 대화→완료/해제→재개를 측정한다. codex/renderer/MCP/Node별 Private Bytes·WorkingSet·peak·CPU·재개 latency를 기록하고 기능별 A/B를 한 항목씩 수행한다. app-server 전용 빌드는 원본 대비 cargo package graph·fresh/incremental 전체 경과·peak·binary 크기와 필수 runtime acceptance를 비교한다. release profile 비교는 별도 실험이다. 분석 과정의 실패한 path glob/조회는 좁힌 정확한 파일로 대체했고 build/test는 실행하지 않았다. 필요한 근거의 조회·소스 동일성 검사는 종료 코드 0이다.
OpenAI 공식 문서도 app-server를 thread/turn/tool/approval lifecycle을 통합하는 제품용 진입점으로 설명한다: https://developers.openai.com/blog/codex-as-a-platform . 이 문서는 현재 Azrael의 절감량 증거가 아니다.

# 빌드 CPU·메모리 부담 완화

## 목표·권한·추천
후속 요청: Windows 소스 수정까지 고려한 다른 사용자들의 개선 사례를 조사한다. 조사 권한이며 추가 OS 설정 변경·도구 설치·커널/시스템 파일 패치는 수행하지 않는다.
빌드 중 Defender CPU 부담과 메모리 부담을 조사하고 기능 축소도 고려한다. 조사와 제안을 요청받았으며 기능 삭제·비활성화, 보안 제외 설정 변경, 전체 앱 빌드·설치 권한은 별도다.
추천 순서는 기능 유지 상태의 빌드 동시 실행 제한 → 다음 허용된 빌드의 Defender 경로 분석 → 기존 웹뷰 메모리 해제 구현의 실제 수용 → 측정으로 효과가 확인된 기능 축소다.

## 선택과 영향
- Cargo의 기존 CARGO_BUILD_JOBS로 동시 컴파일 4개를 시험한다. 빌드가 느려질 수 있으며 RAM 절감량은 아직 미측정이다. 16 논리 CPU인 현재 Windows 호스트에서 시험할 값이며 다른 플랫폼 기본값 변경을 의미하지 않는다.
- Defender 성능 분석기로 검사 부담이 큰 경로를 찾는다. 생성물·캐시 제외는 측정과 사용자 결정 후 좁게 적용한다. 실시간 보호와 기존 제외 설정은 변경하지 않았다.
- 기존 숨김 웹뷰 해제 정책은 숨김 1시간, 플래그 없음, 실행/큐/재개/승인 대기 없음이다. 실제 설치본 수용이 남아 있다. 시간 단축과 동시 유지 화면 수 제한은 복원 지연·초안/스크롤 복원·작업 연속성을 검증할 추가 선택이다.
- 기능 축소 후보: 동시에 유지하는 대화 화면 수 제한, 미사용 제공자 모듈의 선택적 패키징. 전자는 재표시 지연, 후자는 해당 제공자 사용 불가가 따른다. 제공자 제외의 RAM 절감량은 입증되지 않았다. 기존 IncludeDevinNative/IncludeProviderAccounts 옵션만으로 최종 제품 동작을 보장하지 않는다.

## 확인한 증거와 한계
Windows 로컬 호스트 RAM 약 32GB, 논리 CPU 16개. 순간 조회에서 Code 25개 프로세스 WorkingSet 합계 4016MiB, codex 2개 1004MiB, MsMpEng 601MiB였고 다른 순간 MsMpEng 757MiB였다. 공유 페이지 중복 가능성이 있는 WorkingSet 합계이며 전용 메모리·빌드 최대치가 아니다. 조회 시 rustc/cargo가 없어 빌드 메모리 원인은 미확정이다.
Defender 실시간 보호는 활성이고 마지막 빠른 검사 기록은 10월 5일이다. 검사 부담 경로는 미측정이고 기존 제외 목록은 관리자 권한이 없어 조회되지 않았다.
현재 셸 CARGO_BUILD_JOBS는 없고 engine/codex-rs/.cargo/config.toml에 jobs 제한이 없다. 실제 빌드 셸·사용자/전역 Cargo 설정의 override는 미확인이다.
[기존 웹뷰 조사](../vscode-webview-memory/01-plan.md): 6개 웹뷰 renderer 전용 RAM 평균 1287.9MiB, 모두 숨긴 뒤 1283.3MiB. 해제 소스 구현·fixture 통과와 실제 설치 RAM 절감 수용은 구분한다.
[기존 빌드 최적화](../AU-01-session-build-timing/02-plan.md): 재사용·조기 실패 소스 구현과 검증 기록이 있으나 실제 전체 빌드 속도 개선은 미측정이다.

## 범위·소유·후속 검증
Defender 진단은 Windows 로컬에 한정한다. 자원 절감의 의도는 공통이나 OS·CPU별 값은 따로 측정한다. 실제 확인 환경은 Windows뿐이다. 제품 변경이 없으므로 architecture와 feature inventory 변경도 없다.
root가 조사·계약·최종 판단을 소유한다. 후속 순서: 적용 범위 선택 → 허용된 빌드 입력 고정 → 제한된 동시 컴파일·단계별 CPU/RAM·경과 시간·Defender 경로 측정 → 기능 유지 수용 → 필요한 기능 축소 설계. 기존 캐시·검증 기록을 재사용하고 필수 검사를 생략하지 않는다.
동일 입력·캐시 조건의 peak RAM/CPU·전체 경과 시간 비교, 필수 기능 검사, 웹뷰 복원·작업 연속성이 후속 성공 기준이다. 이번 조회 최종 종료 코드 0. 제품 빌드·테스트·설치·프로세스 종료·보안 설정 변경은 수행하지 않았다.
참고: https://doc.rust-lang.org/cargo/reference/config.html 및 https://learn.microsoft.com/en-us/defender-endpoint/performance-analyzer-reference

AI 자동 시작 해제는 WSAIFabricSvc Start=3(수동) 레지스트리 변경이다. Phone Link 시작 메뉴 통합 숨김은 YourPhone 제거·전체 서비스 종료와 다르다. 적용 효과는 Home edition의 실제 정책 반영을 확인해야 한다.
복원: 적용되는 registry feature가 있고 SkipRegistryBackup이 없을 때 원래 설정 백업을 수행하며 백업 실패는 적용 전에 오류로 중단한다. 시스템 복원점은 CreateRestorePoint 선택에 따른 별도 기능이다. registry 백업은 제거 앱을 복원하지 않는다. Widgets 복원은 관련 Store 앱 재설치가 필요하다. 제거 기본 대상은 모든 사용자이므로 후속 계획은 AppRemovalTarget CurrentUser를 명시하고 제거 앱 목록을 고정한다. Default/DefaultLite도 Modern Standby 네트워크·AI·검색·Widgets 등을 묶어 바꾸므로 현재 목적에는 사용하지 않는다.
후속 적용 제안: 고정 release ZIP·해시와 개별 옵션 → WhatIf 변경 미리보기 및 원래 상태/registry 백업 확인 → 합의된 항목만 적용 → 필요 시 사용자 재시작 후 동일 유휴·빌드 측정. preview와 registry 값 변경만으로 기능 수용이나 RAM 개선을 인정하지 않는다. 현재는 읽기 확인만 종료 코드 0으로 완료했다.

상태: 공개 프로젝트 문서·사용자 보고 검토 완료. 현재 PC 적용 효과는 미검증이다.

- Windows 커널 수정: 현재 개인 사용자가 Windows 11 전체 소스를 받아 수정·재빌드하는 공개 지원 경로를 확인하지 못했다. Microsoft GSP는 적격 정부 대상이며 선택된 Windows 소스의 읽기 전용 접근을 제공한다. 이를 일반 사용자 수정 권한으로 해석하지 않는다. https://www.microsoft.com/en-us/securityengineering/gsp
- 소스가 공개된 Windows 호환 OS인 ReactOS는 별도 구현이며 현재 alpha, Windows Server 2003 호환 중심이다. 현재 개발 PC의 Windows 11 대체 수용 근거는 없다. https://github.com/reactos/reactos
- AtlasOS/ReviOS: 공개 playbook으로 구성 요소·서비스·정책 등을 조정한다. Windows 소스 자체의 공개나 커널 재빌드를 뜻하지 않는다. ReviOS는 깨끗한 설치에서 시작하기를 권장한다. Atlas는 Defender·보안 격리 등 선택도 포함하므로 개별 옵션 검토가 필요하다. https://github.com/Atlas-OS/Atlas/blob/main/README.md ; https://github.com/meetrevision/playbook
- 사용자 실측: Hyper-V에서 Windows 11 Pro 24H2 155프로세스/1.8GB, IoT Enterprise LTSC 136/1.7GB, privacy.sexy 모든 옵션 적용 Pro 109/1.1GB라는 보고가 있다. 단일 사용자·VM 측정이고 기능 보존 및 실제 빌드 성능은 입증하지 않는다. 약 700MB 차이를 현재 PC 예상 절감으로 환산하지 않는다. https://www.reddit.com/r/WindowsLTSC/comments/1q3rhij/comparison_of_the_number_of_background_processes/
- Atlas 사용자 보고는 ReviOS 약 1.5GB, Atlas 약 1.3GB idle이라고 주장한다. 원본 baseline·상세 측정 조건이 부족하고 토론에서도 신뢰성에 이견이 있어 성능 보장 근거로 사용하지 않는다. https://github.com/orgs/Atlas-OS/discussions/1699
- Win11Debloat: 선택적 앱 제거, Widgets, Phone Link, 검색 통합, AI 서비스 자동 시작 등의 조정이 가능하다. 현재 PC에는 실제 해당 기능 실행·자원 측정 후 필요한 옵션만 추리는 접근을 권장한다. 앱 제거만으로 RAM 절감을 보장하지 않는다. https://github.com/Raphire/Win11Debloat
- Tiny11 Builder: 일반 모드는 업데이트·Defender·복구를 유지하며 앱·기능을 제거한 설치 이미지를 만든다. Core는 servicing/recovery를 제거하고 Defender를 비활성화해 업데이트 불가라고 프로젝트가 명시한다. 기존 개발 환경에 바로 적용하는 수단으로 권장하지 않는다. https://github.com/ntdevlabs/tiny11builder
- Windhawk: C++ mod를 프로세스에 주입하여 개별 동작을 바꾼다. 전체 RAM 절감이 입증된 도구로 취급하지 않고 확인된 Explorer 문제 등 특정 결함에 한정해 검토한다. https://github.com/ramensoftware/windhawk/wiki/Injection-targets-and-critical-system-processes
- RAM 정리 도구: WorkingSet 비우기는 할당 해제와 다르고 이후 접근 시 soft/hard page fault가 생길 수 있다. 사용량 숫자 감소만으로 빌드 성능 개선을 판정하지 않는다. https://learn.microsoft.com/windows/win32/memory/working-set
