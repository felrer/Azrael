# 선택적 구조 설명을 포함한 Serena 비교 측정

## 목표·범위

기존 FI-01 후속이다. 사용자는 Serena에 개선 개요·일괄 읽기를 보완한 경우를 측정하도록 요청했다. 최신 선택적 구조 설명 버전과 stock Serena를 동일한 새 고정 scripts 입력·질문에서 비교한다. 기존 두 질문을 사용하고 조건별 신규 cold 모델 세션 2회, 총 4회 실행한다. 모델 역할은 이전과 같은 luna_explorer다. 조건 순서는 기존/확장/확장/기존으로 균형화하고 공유 worker를 사용한다. 모델 세션은 신규지만 언어 서버/cache는 cold가 아니므로 latency의 인과 비교를 주장하지 않는다.

실험 harness·격리 환경·결과 기록만 허용 범위다. 제품 코드·사용자 설정·기본 도구·공유 지침·배포를 변경하지 않는다. root는 환경·계측·근거 평가·정리를 소유한다. 하위 모델은 고정 입력에서 정답을 찾아 보고하는 읽기 전용 평가만 수행한다. 공통 검색·파일 fallback을 허용하며 정답 파일/함수명은 알려주지 않는다. 파일 밖 문맥을 읽거나 선택적 펼침을 사용하는지 강제하지 않는다.

검증 환경은 Windows x64 로컬, JS/TS 계열 scripts다. 다른 OS·언어·실제 수정 성공률·주 모델 동작으로 일반화하지 않는다. 제품 동작 변경이 없어 architecture/feature inventory는 변경하지 않는다. development-workflow·implementation·testing과 기존 work/build/artifact/delegation 경로를 적용한다.

## 성공 기준·검증

Serena-agent 2.1.0 실제 API 실행, 동일 고정 입력, 조회별 원시 출력과 모델 전달 출력·호출·컨텍스트 증가·시간 계측, 질문별 핵심 근거 정확성, 배치 선택/펼침 사용의 적절성을 확인한다. 입력/확장 hash를 전후 확인하고 반환 본문은 원문과 대조한다. 실패를 포함한 모든 실행을 기록하며 임의 재시도하지 않는다. 실제 환경/인코딩 장애로 제외해야 하면 최초 결과와 이유를 보존한다. 모델 요청/출력 계측에 접근할 수 없으면 그 제한을 명시한다.

일회성 snapshot·venv·캐시·worker·로그·분석은 생성 전에 등록한 lifecycle `run:serena-read-eval:20261102:r4`, owner `work:serena-read-eval`, `artifacts/verification/sr04`에 한정한다. 결과를 이 문서에 독립 요약하고 소유 process tree 종료 확인 후 현재 검증된 maintenance owner의 register/review/apply/finalize로 삭제한다. 기존 extension 소스·테스트는 바꾸지 않는다. 작업 보고서만 로컬 커밋하며 unrelated index를 보존한다.

## 준비와 실행 경계

실제 입력은 541파일·7,468,615바이트다. 이전 평가 이후 checkout 변경을 포함하므로 과거 숫자를 합쳐 평균내지 않는다. Serena-agent 2.1.0 설치 exit 0, 실제 stock overview/find_symbol 및 확장 compact overview/선택적 펼침/본문 2개 일괄 읽기 preflight exit 0을 확인했다. SERENA_HOME·npm/uv/XDG cache와 TEMP는 해당 run에 고정했다. worker ready 응답에서 home/npm cache 경로를 확인했다. agent version은 작업 checkout HEAD를 반영한 `2.1.0-0048f552-dirty`였으며 vendor 소스는 수정하지 않았다.

첫 base1 세션은 안내 파일의 첫 PowerShell 읽기에서 기본 인코딩을 사용해 mojibake가 반환된 것을 확인하고 interrupt했다. 이 실행은 제외하고 최초 명령에 `Get-Content -Encoding UTF8`을 명시한 새 base1r 세션으로 한 번 교체했다. 제외 세션의 raw 조회와 rollout은 삭제 전 따로 집계하고, 나머지 모든 조건도 같은 UTF-8 명령을 명시한다. 출력이나 성능이 불리하다는 이유로 재시도하지 않는다.

세션은 모델만 신규이며 backend는 하나다. 실행 순서는 base1r/enhanced1/enhanced2/base2다. 첫 세션 준비는 UTC 2026-11-02 12:56경 시작했다. root는 다음 평가 전 환경/계측/본문 대조/종료 검증을 준비하며, 다음 세션이 앞선 조건의 결과를 보지 않도록 분리한다.

## 평가 해석 경계

확장 첫 실행은 `overview`와 `read_symbols`가 안내 전체에 정상 표시됐음에도 두 도구를 사용하지 않았다. guide의 실제 모델 전달 출력에서 두 API가 모두 존재하고 잘림이 없음을 확인했다. 원래 계획대로 자연스러운 선택을 측정한 결과이며 이 실행을 제외하거나 사용 지침을 중간에 바꾸지 않는다. 도구가 사용되지 않은 실행의 출력/시간 차이를 확장 기능 자체의 효과라고 해석하지 않는다.

두 번째 확장 실행에서도 두 도구를 사용하지 않았다. 원래 두 세션은 모두 유지한다. 실제 개선 API 사용 시의 결과를 구분하기 위해 동일 질문/입력에서 두 개의 별도 `enhancedguided` 신규 세션을 추가한다. 이 조건만 파일 발견 후 개선 overview, 알려진 함수는 read_symbols, 이미 확인된 관련 함수는 한 배치를 우선하도록 안내한다. 불필요한 함수 채우기나 구조 설명 펼침은 강제하지 않고 일반 파일 fallback도 유지한다. 이는 결과를 교체하는 재시도가 아니라 안내 방식이 다른 제3조건이며, 안내 효과와 기능 효과를 분리해 해석한다. 원래 4회 이후 두 번을 순차 실행하므로 순서/cache 효과가 통제됐다고 주장하지 않는다.

기존 도구 조건의 base2도 stock 심볼 도구를 사용하지 않고 검색과 파일 읽기만 선택했다. 따라서 자연 선택 표의 조건명은 도구를 제공한 조건을 뜻하며, 모든 실행에서 Serena 방식을 실제 사용했다는 뜻은 아니다. 개선 API 우선 안내 조건과 자연 선택 조건의 차이에는 지침 차이도 포함된다. stock 우선 사용을 강제한 대칭 조건은 이번 실험 범위에 없으므로 기능 자체의 순수 효과를 분리했다고 주장하지 않는다.

## 실제 도구 채택과 선택 적절성

자유 선택 확장 2회는 새 overview/read_symbols 모두 0회였다. 안내를 통해 새 도구를 우선 사용한 두 세션은 overview 각각 7/5회, read_symbols 각각 4/4회였다. 모델의 선택적 구조 설명 펼침은 두 세션 모두 0회였고 기본 구조 설명이 생략된 상태로 작업했다. 펼침 API 자체는 preflight에서 실제 성공했지만 자연 채택/효과를 검증한 것은 아니다.

본문 읽기 8회 중 6회가 다중 선택이었다. 선택 목록 크기는 guided1에서 7/6/2/1, guided2에서 6/5/1/2였다. 총 30개 선택 중 29개 본문을 성공 반환했고, 그중 27개가 다중 선택 호출에 포함됐다. 모두 원문과 일치했다. 질문의 구현 함수와 테스트 callback을 파일을 넘나들며 묶는 사용은 실제로 수행됐다.

- guided1은 Q1의 gaugeProgress/decorateGauge/policyDescription과 관련 테스트 4개를 한 번에 읽었다. Q2의 plainFile을 `plainFile[0]`로 잘못 지정해 0건 오류가 났고, 정확한 이름으로 validateCapabilities와 함께 다시 읽었다. 이는 batch 내부 부분 오류 1건이다. 별도로 PowerShell 인용 오류와 client JSON 오류도 있었고 전달 출력/컨텍스트에는 포함된다.
- guided2는 Q1 함수 2개와 테스트 4개, Q2 함수·테스트 5개를 각각 묶었다. Q2에서 선택한 `installationReceipt[1]`는 19문자 Property로, 실제 경로 선택 함수 installationPath가 아니었다. 이후 installationPath를 별도로 읽어 보완했다. ID가 정확한 노드를 읽어도 모델이 목적에 맞는 노드를 선택하는 문제는 남는다.
- 두 세션 모두 인접한 verifyInstalledCommand를 추가로 읽었다. 최종 답변의 필수 근거는 주로 resolver와 plainFile/validateCapabilities 및 전용 테스트였으므로, 모든 선택이 최소·필수였다고 주장하지 않는다.
- stock base1r의 잘못된 정규식 1건도 제외하지 않았다. 제외한 최초 base1은 인코딩 장애가 확인된 별도 실행이며 중단 전 조회 16회·원시 470,883문자였다.

## 출력 증가 원인과 판단

guided1의 넓은 receipt/override/identity/legacy 검색 한 건은 484,452문자, guided2의 유사한 넓은 검색은 192,243문자였다. 두 경우 모두 이후 범위를 좁혀 근거를 확인했다. 전체 scripts 목록도 약 19,990문자를 반환했다. 함수 본문 일괄 읽기보다 발견 단계의 과대 검색이 원시 출력에 큰 영향을 줬다.

guided1은 depth 1로 inject-provider-context 개요 312행·54,654문자, test-provider-context 개요 414행·106,330문자를 받았다. 이때 구조 설명은 모두 생략됐는데도 중첩 심볼 수 때문에 출력이 커졌다. test-provider-context를 depth 0으로 다시 읽은 결과는 37행·10,257문자였다. 최신 기본 depth 0을 유지해도 모델이 불필요하게 depth를 늘리면 재조회·출력 문제가 생긴다. 깊은 개요 두 건의 전체 문자량을 실제 컨텍스트에 전부 들어간 양으로 간주하지 않으며 wrapper 잘림을 구분한다.

현재 권고는 제품 기본 연결보다 발견 검색 범위와 개요 계층 선택을 먼저 개선하는 것이다. 구조 설명 접기만으로는 부족하며, API를 새 이름으로 추가하기만 해서는 모델이 채택하지 않을 수 있다. 향후 기본 심볼 메뉴/개요 계약을 교체하는 실제 통합 방식과 검색 요약/단계적 확장을 별도 검토할 수 있다. 이번 측정 요청에서는 해당 구현이나 기본 지침을 변경하지 않았다.

## 정확성·입력 보존·종료 확인

여섯 세션 모두 Q1의 구간 계산/수치 표시/경계·강조와 Q2의 override/손상 시 거부/legacy 경계 및 관련 테스트 assertion을 찾았다. 테스트 소스를 읽은 결과이며 제품 실행·테스트 통과 증거는 아니다. 잘못된 capacity·NaN/Infinity tooltip·추가 용량 문자열의 직접 assertion 등 확인하지 못한 항목을 구분했다. 실제 버그 수정 성공률이나 모든 모델의 정확성이 보존됐다고 일반화하지 않는다.

## 정리 완료

현재 선택기가 검증한 standalone `maintenance-owner-ff01-group-win-x64-20261102/payload/maintenance_owner.exe`로 등록·registered review·apply를 수행했고 각각 exit 0이었다. 등록 전 optimistic catalog 관측은 다른 작업의 목록 변경으로 한 번 실패했다. 삭제나 종료 상태를 가정하지 않고 동일 owner의 catalog lock 안에서 새 관측을 얻어 해당 run의 revision 1을 확인한 뒤 producer를 닫았다. 이후 보호/참조가 없는 complete group으로 등록해 fresh token의 명시적 delete를 적용했다. 잠금을 해제하거나 우회하지 않았다.
