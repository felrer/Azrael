상태: 조사 중 — 엔진 캐시의 소유·사용·정리 경계를 확인하고 안전한 개선을 진행한다.

## 목표와 범위
엔진 Cargo 캐시의 비정상적 용량 증가를 분석하고, 사용 중인 데이터와 불필요한 생성물을 안전하게 구분해 정리한다. 필요한 경우 기존 캐시 소유·생성·정리 로직을 개선한다. 보호된 데이터, 활성 작업과 기존 사용자 변경을 보존한다.

## 조사 및 접근
기존 관리 도구의 등록·보호·참조와 Cargo 소유자 및 정리 경로를 확인하고, 현재 캐시의 사용과 재생성 비용을 평가한다. 파일 단위 사용 여부는 Cargo가 제공하지 않을 수 있으므로 확인된 경계에 따라 결정한다. 발견한 계약 차이와 선택지를 기록한다.

## 검증
관련 소유자 테스트와 Windows 회귀를 적용하고, 정리 시 검토·실제 결과와 경로 부재를 확인한다. 다른 플랫폼의 실제 실행 여부를 구분한다.

## 확인된 사실과 미해결 사항
- `engine/codex-rs/target`의 두 debug 캐시에서 `incremental` 합계 335,881,285,376 bytes, `deps` 합계 147,470,306,859 bytes를 관측했다. 논리 크기이며 심볼 파일의 하드 링크 중복을 확인했다.
- `target/.azrael-cargo-owner/owner.json`은 2026-10-28 `codex-shell-command` 검사에서 `unknown`으로 남은 소유 기록이다. `coordinatorPid` 77152의 현재 부재와 Cargo 프로세스 부재만으로 원래 producer tree의 종료는 증명되지 않는다. 원래 결과와 lease는 보존한다.
- pending producer catalog의 동일 경로 항목은 `pending`, 미완결, 다른 generation으로 남아 있다. 기존 generation의 종료 증거 및 신규 소유 기록의 실제 시작 여부는 미확인이다.
- native inventory에서 `target/debug/deps`의 일부 실행 파일과 PDB가 DO-01, DO-02 두 그룹에 동시에 등록되고 보류된 상태를 확인했다. 등록된 그룹과 보호 검토를 우회하여 삭제하지 않는다.
- `cargo-target-owner.cjs`는 `recordPending`이 spawn 이전에 실패해도 일반 예외로 처리하고 unknown 소유 기록을 남길 수 있다. 이는 코드 경로의 가능성이며 현재 lease의 실제 원인이나 producer 미시작 증거가 아니다.
- 기본 배포는 호환성별 공유 Cargo 캐시를 선택한다. 이전 source-tree target을 파일 이름·수정 시각만으로 미사용이라고 판정할 근거는 없다. 전체 또는 부분 삭제와 정책 변경 전에 종료 증거, 모든 참조 및 캐시 단위 계약 검토가 필요하다.
