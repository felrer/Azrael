# Stage 3 — Isolated execution

Use only the authenticated host’s same-user Windows child-session route and advertised app operations. The host must admit connection, rendering, independent input and data access on this environment; a configured backend is not acceptance evidence. App approval and task-stage authority bind the isolated execution context. Never silently fall back to parent-session input. Do not extract browser profiles or cookies.

Use returned session and target identities, fresh observations and the managed input owner. Other task input queues or reports occupancy. The current child viewer is read-only; do not offer user takeover through it. User activity in the parent session does not cancel child execution. Changing execution contexts requires a newly bound target and discarding previous observations. Stop on cancellation, uncertain mutation or unsupported capability; teardown only owned sessions and processes without discarding unsaved data.

After an admitted stage transition, `launch_isolated` accepts the observed parent app target and returns a new opaque child target; it does not transfer the live window. Use `capture_isolated`, then `input_isolated` with its fresh observation. Input consumes that observation. Coordinates are pixels inside the returned image, and key events use scan codes with explicit down/up. Task-switch and Windows-key shortcuts are unavailable. Treat `admissionReady: false` or `available: false` as an unmet platform gate; do not infer support from a connected transport. `contentVerified: false` means the transport has not validated app rendering: examine the returned image before input, stop on blank or unexpected content, and verify actual app behavior. The platform fixture does not establish an app’s login, data concurrency or GPU compatibility. Use `resource_status` and `cleanup` for owned resources; Stop releases held input and task leases, while unknown or unsaved work defers logoff.
