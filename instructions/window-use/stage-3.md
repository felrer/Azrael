# Stage 3 — Isolated execution

Use only the authenticated host’s same-user Windows child-session route and advertised app operations. The host must admit connection, rendering, independent input and data access on this environment; a configured backend is not acceptance evidence. App approval and task-stage authority bind the isolated execution context. Never silently fall back to parent-session input. Do not extract browser profiles or cookies.

Use returned session and target identities, fresh observations and the managed input owner. Other task input queues or reports occupancy. The current child viewer is read-only; do not offer user takeover through it. User activity in the parent session does not cancel child execution. Changing execution contexts requires a newly bound target and discarding previous observations. Stop the current action sequence on cancellation, uncertain mutation or unsupported capability; teardown only owned sessions and processes without discarding unsaved data.

After an admitted stage transition, `launch_isolated` accepts either an observed parent app `targetId` or an exact current-user installed Windows MSIX `packageName` with an optional manifest `applicationId`. Installed-package launch does not require opening the app in the parent session. The host resolves a registered full-trust executable, requests app consent, revalidates its registration and pins its hash before the child launches it. Paths, shell commands, arguments and URI activation are not accepted. For example, installed Paint uses `packageName: "Microsoft.Paint"`; package availability and actual launch/render compatibility must still be verified. Both routes return a new opaque child target and do not transfer a live window. Use `capture_isolated`, then `input_isolated` with its fresh observation. Input consumes that observation. Coordinates are pixels inside the returned image, and key events use scan codes with explicit down/up. Task-switch and Windows-key shortcuts are unavailable. Treat `admissionReady: false` or `available: false` as an unmet platform gate; do not infer support from a connected transport. `contentVerified: false` means the transport has not validated app rendering: examine the returned image before input, stop on blank or unexpected content, and verify actual app behavior. The platform fixture does not establish an app’s login, data concurrency or GPU compatibility. Use `resource_status` and `cleanup` for owned resources; Stop releases held input and task leases, while unknown or unsaved work defers logoff.

When `isolated_viewer_minimized` reports `actionExecuted: false`, ask the user once to restore the exact `Azrael isolated session (model control)` viewer from minimization, then wait for their confirmation without imposing a timeout. `restore_window` controls the selected parent window and cannot restore this viewer. After confirmation, obtain a fresh `capture_isolated`, examine it, and use its new observation before further input. Keep existing cancellation, user Stop and revoked authority in force.

A failure describes the individual operation. `mutationOutcome: "unknown"` with `recovery: "observe_again"` and `observationRequired: true` stops the current sequence: never replay the uncertain action. A previous unknown outcome alone does not permanently prohibit read-only capture. Capture still requires current identity, authority, connection and rendering checks, but may run while input release remains unconfirmed. A capture with `inputReady: false` is usable for observation; it does not authorize new input. `inputReleaseConfirmed` describes release evidence when known. Inspect the new state to decide the next authorized action, without assuming whether the failed action ran. Viewer restoration or a successful capture does not prove the uncertain mutation's outcome. A `state_changed` response with `nativeCode: "child_input_revalidated"` and `actionExecuted: false` means the next input was not delivered because release and revalidation invalidated its old observation; capture again before planning new input.

The authenticated host can automatically repair a lost child connection or take over an idle compatible host's connection after native ownership, same-user identity and admission checks. Recovery may request Windows administrator approval. An active input owner blocks handoff. `connectionRecovered: true` means the connection was repaired; it does not confirm the failed action. Old targets and observations are invalid after reconnection: select or launch the approved application through the managed route and capture it again before further input. Never replay the uncertain mutation or implement a separate reconnect, process-kill, session-creation or logoff workaround.
