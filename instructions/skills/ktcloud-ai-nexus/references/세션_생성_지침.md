# kt cloud AI Nexus 세션 생성·접속·기록 지침

이 문서는 Backend.AI CLI로 AI Nexus 세션을 조회·생성·검증하고 세션 기록을 관리하는 단일 운영 기준입니다. 조회와 검증은 v2를 우선하고, 생성은 아래의 서버 호환성 계약을 따릅니다. 로그인은 [다중 계정 자동 로그인 지침](ktcloud_CLI_자동로그인_지침.md), 저장 위치는 [데이터 폴더 이용 지침](data_folder_usage_guide.md)을 함께 따릅니다.

## 1. 계정 선택

| 계정 | GPU 한도 | 새 세션 기본 선택 |
|---|---:|---|
| `trinity` | 최대 4개 | 사용자가 명시적으로 요청한 경우만 |
| `abydos` | 최대 1개 | 계정 언급이 없는 모든 요청 |

- 사용자가 계정을 언급하지 않으면 새 세션은 항상 `abydos`에서 생성합니다.
- `trinity`는 사용자가 `trinity`를 명시적으로 요청한 경우에만 선택합니다.
- 요청한 작업에 GPU 2개 이상이 필요하더라도 Agent가 `trinity`로 자동 전환하지 않습니다. `abydos` 한도로 수행할 수 없음을 알리고 사용자의 명시적 선택을 요청합니다.
- 기존 세션은 자원 수가 아니라 private state root의 `sessions/active` 또는 `sessions/archive`에서 직접 찾은 세션 문서의 `소유 계정`으로 로그인합니다.
- 사용자가 계정을 명시했거나 프로젝트 문서가 기존 세션의 소유 계정을 지정하면 그 값을 우선합니다.
- 소유 계정이 불명확한 기존 세션은 양쪽 계정의 전체 세션 목록에서 UUID를 조회해 확정합니다.
- 계정을 확정하지 못한 상태에서는 세션 생성·종료·SSH 접속을 실행하지 않습니다.

## 2. 로그인과 생성 전 조회

먼저 활성 스킬의 resolver로 Azrael 코드 원본을 확인합니다. 이 단계가 실패하면 프로젝트 로컬 경로로 대체하지 않습니다.

```powershell
$SkillRoot = & "<loaded-skill-root>\scripts\resolve_canonical_root.ps1"
$StateRoot = & (Join-Path $SkillRoot "scripts\resolve_state_root.ps1")
```

선택한 계정을 명시해 로그인합니다. 아래는 기본 계정 `abydos`의 예시입니다.

```powershell
& (Join-Path $SkillRoot 'scripts\ktcloud_login.ps1') -Account abydos
& (Join-Path $SkillRoot 'scripts\ktcloud_login.ps1') -Status -Account abydos
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 config show
```

`Authenticated`가 `True`인 것을 확인한 뒤 다음을 조회합니다. 계정별 wrapper를 사용하면 다른 계정 작업과 병렬 실행할 수 있습니다.

```powershell
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 my resource-allocation keypair-usage
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 resource-allocation resource-group-usage H200-141G
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 my session search --limit 100
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 runtime-variant-preset search --limit 100
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 vfolder my-search --limit 100
```

공식 Linux client 26.7.0과 API `v9.20250722` 조합에서는 일부 목록 응답의 필드가 서버에서
누락되어 client DTO validation이 실패할 수 있다. 현재 확인된 것은 runtime preset의 `required`와
vfolder의 `quota`이다. 이 경우 인증 또는 Linux dependency 실패로 분류하지 않고, client DTO를
shim/patch하지도 않는다. `v2 config`, 사용자 자원, resource-group, session search/get은 그대로
사용하고 image/vfolder 확인은 검증된 legacy 조회로 보완한다. 생성 계약은 5.1의 legacy 경로를
계속 사용하며 이 예외는 `v2 session enqueue` 재시도 권한이 아니다.

legacy `admin keypair info`는 access key나 기타 민감한 keypair 재료를 반환할 수 있으므로 사용하지 않습니다. PowerShell wrapper와 Python runner가 이 명령을 실행 전에 차단합니다. 사용자 자원 한도와 사용량은 위의 `v2 my resource-allocation keypair-usage`로만 조회합니다.

확인 항목:

- 선택 계정의 사용자 한도, 현재 사용량과 `assignable`
- 실행·대기·종료 세션 전체 이력
- 대기 중 세션까지 반영한 실제 CPU·RAM·GPU 잔여량
- 환경 이미지, 프로젝트, 자원 그룹과 데이터 폴더 UUID

`assignable`이 0인 자원은 양수로 요청하지 않습니다. CPU 또는 RAM이 부족하면 세션 생성을 중단하고 자원 확보가 필요하다고 보고합니다. `resource-group-usage`의 `free`는 자원 그룹 전체 여유량이며 사용자 잔여량이 아닙니다.

## 3. 세션 이름

기본 이름은 다음 형식을 사용합니다.

```text
<계열><번호>-<YYMMDD>
```

- CPU 또는 GPU 1개: `kei`
- GPU 2~4개: `azusa`
- 번호는 선택한 계정의 전체 세션 이력에서 같은 계열의 가장 큰 번호에 1을 더합니다.
- `TERMINATED`, `CANCELLED`, `ERROR`도 번호 계산에 포함하고 사용한 이름을 재사용하지 않습니다.
- 날짜는 실제 생성일의 한국 시간 기준입니다.
- 프로젝트가 이미 별도 명명 규칙을 승인한 경우 그 규칙을 따르되 계정별 전체 이력에서 중복을 확인합니다.

세션 이름은 계정별로 관리하므로 다른 계정에 같은 이름이 있을 수 있습니다. UUID와 소유 계정 없이 이름만으로 세션을 식별하지 않습니다.

## 4. 데이터 폴더

모든 새 일반 연구 세션은 `<persistent-folder>`를 `/home/work/<persistent-folder>`에 읽기·쓰기(`rw`)로 마운트합니다. 작업 파일은 `/home/work/<persistent-folder>/workspaces/<workspace-name>` 또는 승인된 `shared` 하위에 저장합니다.

payload 실행 전 `<persistent-folder>`의 계정별 UUID, 마운트 경로와 권한을 확인합니다. 실행 후에는 다음 명령으로 검증합니다.

```bash
test -d /home/work/<persistent-folder> && echo "mount ok" || echo "mount missing"
```

`mount missing`이면 해당 세션에 영속 데이터를 저장하지 않습니다. 별도 데이터 폴더를 사용하는 기존 프로젝트는 해당 세션 기록의 경로를 따릅니다.

## 5. 세션 생성

확정 값을 `EnqueueSessionInput` JSON으로 작성합니다. RAM은 바이트 단위 문자열을 사용합니다.

```json
{
  "session_name": "<세션 이름>",
  "session_type": "interactive",
  "image_id": "<환경 이미지 UUID>",
  "resource_entries": [
    {"resource_type": "cpu", "quantity": "<CPU 코어 수>"},
    {"resource_type": "mem", "quantity": "<RAM 바이트 수>"}
  ],
  "resource_group": "H200-141G",
  "cluster_mode": "single-node",
  "cluster_size": 1,
  "mounts": [
    {
      "vfolder_id": "<데이터 폴더 UUID>",
      "mount_path": "/home/work/<persistent-folder>",
      "permission": "rw"
    }
  ],
  "preopen_ports": [],
  "project_id": "<프로젝트 UUID>"
}
```

GPU를 사용할 때만 `resource_entries`에 다음을 추가합니다.

```json
{"resource_type": "cuda.shares", "quantity": "<GPU 수>"}
```

실행 직전 다음을 확인합니다.

- 활성 계정과 선택 계정 일치
- 해당 계정 GPU 한도 이내의 요청
- 이름, 이미지, CPU, RAM, GPU, 프로젝트와 자원 그룹
- 데이터 폴더 UUID, 마운트 경로와 `rw`
- 각 요청량이 최신 `assignable` 이하

```powershell
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 session enqueue '@<payload-json-path>'
```

4xx 오류가 발생하면 같은 요청을 반복하지 않고 payload, 권한, 활성 계정과 최신 자원 상태를 다시 확인합니다.

### 5.1 kt cloud 2025.7 서버 호환 생성

`v2 config show`가 API `v9.20250722`를 광고하는 kt cloud 배포에서는 v2 session 조회는
가능하지만 26.7 DTO의 `v2 session enqueue`가 서버 내부 오류로 실패할 수 있다. 현재 Web UI와
동일한 legacy session-create 계약을 canonical wrapper 뒤에서 사용한다. 이는 wrapper를
우회하는 예외가 아니며, 서버 버전이 이 값과 일치할 때만 적용한다.

Windows에서는 절대 mount path를 legacy CLI에 전달하지 않는다. slash 변환을 피하기 위해
`--mount <persistent-folder>`만 전달하면 서버가 vfolder 이름의 기본 위치 `/home/work/<persistent-folder>`에 마운트한다.
생성 후 v2 조회와 SSH에서 절대 경로 및 `rw`를 반드시 검증한다.

```powershell
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- session create `
  --name <세션-이름> --type interactive --priority 10 --enqueue-only --no-reuse `
  --architecture x86_64 --cluster-mode single-node --cluster-size 1 `
  --group NIPA-H200 --scaling-group H200-141G --mount <persistent-folder> `
  --resources cpu=<코어> --resources mem=<MiB>m --resources cuda.shares=<GPU> `
  <이미지-이름>
```

호환 경로를 사용할 때도 실행 직전 full history, image, project/group, vfolder, user assignable과
resource-group free를 재조회한다. legacy 응답의 UUID를 얻은 직후 `v2 session get`과
`v2 my session search`로 결과를 검증한다. 서버 API가 바뀌면 이 경로를 자동 재사용하지 않고
Web UI/공식 서버 계약을 다시 대조한다.

## 6. 생성 결과 검증

생성 응답의 UUID를 즉시 기록하고 다음 명령으로 검증합니다.

```powershell
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 session get <세션 UUID>
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- v2 my session search --limit 100
```

세션 이름, UUID, 이미지, CPU, RAM, GPU, 자원 그룹, 프로젝트, 상태와 `INTERACTIVE` 타입이 요청과 일치해야 합니다. `RUNNING` 이후 터미널 또는 SSH에서 다음을 확인합니다.

```bash
whoami
hostname
nvidia-smi
df -h
test -d /home/work/<persistent-folder> && echo mount-ok
```

컨테이너에서 `free -h`가 호스트 전체 메모리를 표시할 수 있으므로 실제 제한은 cgroup의 `memory.max` 또는 `memory.limit_in_bytes`로 확인합니다.

## 7. 세션 기록

세션 생성 직후 private state root의 `sessions/active/<계정 별칭>/`에 기록을 만듭니다. 세션 목록을 별도 README나 인덱스에 중복 기록하지 않습니다. Git-ignored private root만 사용하고 공개 스킬 디렉터리, portable skill copy, 임시 작업 폴더에는 세션 기록을 만들지 않습니다.

```text
<state-root>/sessions/active/<계정 별칭>/<세션 이름>.md
```

필수 항목:

- 소유 계정: `trinity`, `abydos` 또는 사용자가 명시적으로 선택한 `ariusN`
- 세션 이름과 UUID
- 상태와 마지막 CLI 확인 시각
- 생성 목적
- 프로젝트와 자원 그룹
- CPU·RAM·GPU
- 이미지 이름과 UUID
- 데이터 폴더, UUID, 마운트 경로와 권한
- 원격 workspace
- 마지막 연결 검증 시각과 성공·실패 결과. SSH 사용자·호스트·포트·키 경로·proxy PID·직접 접속 명령은 기록하지 않음
- 다음 작업 및 종료 전 보존 항목

실제 사용자 ID, 비밀번호, OTP와 개인키 내용은 기록하지 않습니다. 세션 이름이 같아도 소유 계정과 UUID가 다르면 별도 세션입니다.

## 8. SSH 접속

세션 기록에 있는 소유 계정으로 로그인한 뒤 CLI에서 `RUNNING` 상태를 확인합니다. 저장된 endpoint를 찾지 말고 Backend.AI CLI가 매 연결마다 새 임시 프록시와 키를 준비하게 합니다.

```powershell
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account <계정 별칭> -- session ssh <세션 이름> -p <비어 있는 로컬 포트>
```

여러 터미널에서 동시에 연결할 때는 각 호출에 서로 다른 비어 있는 로컬 포트를 지정합니다. wrapper는 SSH 키 staging을 호출별 임시 디렉터리로 격리하고 Windows proxy 트리를 kill-on-close Job Object에 넣으므로 연결 수명 동안 다른 SSH/SCP 호출을 막지 않으며 wrapper가 강제 종료돼도 proxy 자식이 남지 않습니다.

```powershell
# 터미널 1
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- session ssh kei-example -p 9972

# 터미널 2
& (Join-Path $SkillRoot 'scripts\ktcloud_cli.ps1') -Account abydos -- session ssh kei-example -p 9973
```

호스트·포트·키를 직접 추출해 기록하거나 재사용하지 않습니다. wrapper가 생성한 키는 연결 종료 시 삭제되고, 다음 wrapper 실행은 죽은 부모와 연결된 managed proxy, 참조되지 않는 정확한 random-key 형식, 전용 temp directory만 제한적으로 회수합니다. SSH 실패 시 같은 명령을 반복하지 않고 CLI 상태를 다시 확인합니다.

2026-10-12 호환성: 관리형 Windows 25.5.2 SDK의 SSH 키 다운로드는 `files`를 JSON 본문에 보내지만, 새 manager의 `DownloadFilesRequest`는 query에서 읽습니다. canonical runner는 해당 POST session/kernel download에만 반복 `files` query를 추가하고 기존 JSON 본문도 유지합니다. SDK 설치 파일과 인증 상태는 수정하지 않습니다. 근거: [manager download handler](https://github.com/lablup/backend.ai/blob/main/src/ai/backend/manager/api/rest/session/handler.py), [QueryParam list parser](https://github.com/lablup/backend.ai/blob/main/src/ai/backend/common/api_handlers.py). 연결 동작 변경 후에는 서로 겹쳐 실행하는 읽기 전용 SSH 두 건의 성공과 임시 키·proxy 정리를 확인해야 합니다.

동일 날짜의 Windows 정리 보강: 동기 키 다운로드만 임시 staging 디렉터리에서 실행하며, 장시간 유지되는 proxy에는 호출자의 작업 디렉터리를 명시합니다. proxy 및 자식 프로세스가 staging 디렉터리를 현재 디렉터리로 붙잡지 않게 하고, 기존 Job Object 종료·대기 후 일반 파일 삭제 순서를 유지합니다. 로컬 비정상 종료 fixture는 원래 종료 코드 보존, proxy 트리 종료와 staging 제거를 검증합니다.

## 9. 종료와 보관

- 세션 종료를 CLI에서 확인하면 문서를 private state root의 `sessions/archive/<계정 별칭>/`로 이동합니다.
- 종료 상태, 확인 시각, 완료 작업, 미완료 작업과 다음 세션 인계 사항을 남깁니다.
- 프록시 호스트·포트·개인키 경로·proxy PID·직접 접속 명령은 active와 archive 어디에도 보관하지 않습니다.
- 세션 전용 SSH/SCP 매크로와 접속 로그는 만들지 않습니다. 기존 파일이 발견되면 안정적인 작업 인계 정보만 세션 문서에 남기고 제거합니다.
- 문서를 보관해도 세션 이름은 재사용하지 않습니다.
- 소유 계정이 확인되지 않은 과거 기록은 임시 `unassigned` 폴더에 두고 양쪽 계정 조회 후 즉시 이동합니다.
- 활성 여부가 필요하면 인덱스를 조회하지 않고 private state root의 `sessions/active`를 직접 탐색한 뒤 CLI에서 최신 상태를 확인합니다.
