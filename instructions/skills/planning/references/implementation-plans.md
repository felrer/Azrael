# Execution Preparation

Use only the parts relevant to the planned change. These are agent responsibilities, not a required user-review checklist. Keep a brief execution record when dependencies, handoffs, or omission risk justify one; link evidence rather than reproducing investigation logs.

## Reuse And Minimum Change

Before new implementation, inspect plausible existing owners, project code, standard or platform capabilities, installed dependencies, and mature reusable options. Select reuse or extension where it satisfies the agreement. Record the concrete gap and minimum change when useful; do not require a candidate table or exhaustive inventory.

Identify affected owners and dependency order to the degree needed for reliable execution. Surface any resulting material scope or resource change in the user-facing plan.

## Tests And Evaluation

Choose the smallest existing evidence or checks that establish the agreed outcome and distinct material risks. For each necessary procedure, state what it checks, how it runs at an appropriate level of detail, how results are interpreted, and what failure changes.

Do not stack unit, integration, broad-suite, and manual checks that establish the same fact. Expand for concrete uncovered risks, findings, or project requirements. Record changes to existing tests only where relevant; do not remove tests merely because they fail.

For research, keep task success and intermediate metrics distinguishable. Check whether evaluation or parsing failures make results uninterpretable before committing to expensive intervention. Define the initial informative comparison and conditional next steps rather than an unconditional search grid. Exact metrics and thresholds depend on the agreed task.

## Transitions And Closeout

For consequential state changes, identify relevant preconditions, abort conditions, recovery steps, and irreversible boundaries. Keep preparation reversible where practical and preserve existing authorization limits.

Track temporary artifacts, cleanup, documentation updates, and handoff only when they apply. Completion evidence must support the actual agreed outcome; partial checks do not establish whole-system completion.

Put decisions affecting user-visible results, scope, resources, or authority in the user-facing core. Keep commands, file lists, and routine mechanics in optional execution notes rather than making them prerequisites for user approval.
