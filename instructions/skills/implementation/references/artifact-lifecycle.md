# Work, Version And Shared Artifact Lifecycle

Read this reference when planning generated outputs, adopting artifact ownership, or cleaning work/build evidence. Use the project's artifact-lifecycle playbook for its paths and migration procedure. This contract works with existing commands and records; it does not require a particular program or background scheduler.

## Ownership And Paths

Use configured equivalents of these defaults; work documents remain in their separately configured work directory:

| Scope | Default path | Owns |
| --- | --- | --- |
| Work/run | `artifacts/tasks/<work-id>/runs/<run-id>/{inputs,temporary,outputs,logs,reports}` | Generated snapshots, fixtures, backups, command output and raw execution evidence |
| Version | `artifacts/versions/<product-version+unique-build-id>/{payload,verification}` | Identified deliverables and required release verification |
| Shared | `artifacts/shared/<cache-kind>/<content-key>` | Reusable generated cache entries with explicit consumers |

Each artifact has exactly one owning work/run, version or shared group, regardless of file type. A work group may aggregate its runs; it is not a second owner of their files. Other consumers hold explicit references rather than accumulating copies. Original source and user files stay outside generated ownership. A cleanup operation owns its generated reports, while observed targets retain external references to their existing owners; observation cannot claim ownership of a parent or its descendants. Keep protected management records in a separate bounded location, outside groups subject to recursive deletion; define their owner, size/retention limits and safe compaction conditions.

Before creating outputs or reusing a path, inspect ancestor and descendant claims in producer and native management records, including claims marked deleted. Prefer a new unique boundary; a deleted receipt neither permits ignoring a new generation nor proves ownership of its contents. If claims conflict, verify actual paths, current producers/readers and complete membership, then use the tool's explicit generation reconciliation or a formal migration: claim the new destination as pending before creation, preserve content and applicable filesystem identity, update readers/references, re-register the complete affected group and verify actual absence at the old boundary. Keep migration and deletion outcomes separate. Do not bypass a conflict by force deletion, editing raw manifests or fabricating missing historical records.

Before a command, register its group, planned output paths, input/tool identity and active references in the existing management record or work record. Do not wait for successful completion to discover ownership. Record creation and terminal outcomes, including failure, cancellation and unconfirmed exits; reconcile partial outputs and keep unresolved runs protected. Reattempts preserve prior evidence and use distinct run/attempt identities where inputs or outputs change. Input ownership includes only actual verified files; preserve dangling inputs and retained/incomplete states when importing records instead of promoting them to completed evidence.

## Evidence And Shared Use

Raw logs remain with the work/run that generated them. Before removing task evidence needed by a release, copy or record the required verified evidence into version scope with source identity, content identity and verification outcome; confirm it is independently usable and switch the references. The resulting version evidence is a separate version-owned artifact. A reference to a file about to be deleted is insufficient.

Product version and unique build identity are separate: two builds of the same version must not overwrite each other's payload or verification. Shared cache reuse requires matching content, tool and environment identity. Shared entries own their explicit references; an active, uncertain or last required consumer blocks deletion until its dependency is released or replaced and verified.

## Test Profiles And Application State

- Use an application's profile/path options to isolate test-only state under `artifacts/tasks/<work-id>/runs/<run-id>/temporary/profiles/<app>` or a configured equivalent. Before creation or launch, record the work/run owner, actual resolved paths, whether each path already exists, related process identities, and the full generated bundle: profiles, extension copies, caches, logs and backups. A profile option alone does not prove where all output goes.
- After reruns, diagnosis and handoff no longer need the disposable state, the model chooses cleanup: stop and confirm termination of only the test-owned processes, ordinarily delete the whole generated bundle, then verify actual absence at every recorded path. Review the same cleanup obligation after success, failure and cancellation; do not treat a successful test or exited parent process as proof of cleanup. Preserve necessary acceptance evidence through the lifecycle rules above before removing its raw files.
- If ongoing diagnosis, an active process, uncertain ownership or a deletion failure prevents cleanup, record the actual remaining paths/processes, defer/failure state, reason and condition for release or retry. Do not report cleanup complete. Use the current conversation's decisions within existing authority; this rule adds no resident scheduler, mandatory management program or new test-script creation criterion.
- When a test must use an existing user profile, track the test's additions and modified pre-existing state before mutation. Remove only those additions and restore the recorded modifications after use; never delete the whole existing profile. A real installation and the immediately preceding verified recovery copy retain their separate persistent owner and protection.
- For a physical root outside the selected project's management boundary, use a separately owned, explicitly registered management root or the established owner cleanup procedure, with verified actual paths and scope supported by the chosen tool and current authority. Preserve a tool's refusal to delete outside its selected project root; do not widen deletion scope or switch APIs to bypass it. If supported cleanup cannot be established, leave the state unresolved and report the blocker.

## Review And Group Decisions

Use available artifact-management tools and their current records and review results as the primary operational evidence for registered groups. The tool owns the filesystem, ownership, membership, reference and protection checks it implements; the model owns the authorized scope and delete/defer decision. Start with existing group records, update changed membership or references through supported operations, review the affected group, apply explicit decisions, and reconcile the reported outcome. A changed group requires a fresh review; do not reuse its previous deletion approval. Do not re-register unchanged groups or repeat tool-covered checks through shell inventories, recursive hashes or a second manifest. Investigate only unregistered paths, conflicting evidence, uncertainty reported by the tool, or a concrete check outside its coverage. Use the established owner procedure when the required tool operation is unavailable; a record alone does not establish capabilities the tool lacks. If an operation is slow, identify its stage and wait for its actual result rather than launch duplicate scans. This delegates checks to the tool without removing its safeguards or asserting that its internal scans are optimized.

After execution, review results and fix/rerun as needed. The model chooses delete or defer for each reviewed group within existing authority, with reason and revisit condition for deferral. Age, passing tests or finishing a run never selects deletion automatically. Test creation criteria and required verification remain unchanged.

Protect the whole selected group if any member is an active input, running output, pending handoff, required release evidence, sole usable recovery copy, user/source file, or has unknown ownership/use. Have the management tool check descendants, actual paths, links, references and protections before application within its implemented coverage; investigate any uncovered boundary explicitly. Required evidence must exist and match its consumer scope and identity. Reuse reviews when selected group and relevant consumer identities/protections remain unchanged and the tool accepts them; unrelated registry updates alone do not invalidate them. Before normalizing generated-file attributes, establish hardlink identity and shared attributes through the owning tool or a targeted check of uncovered cases; preserve source/user originals and retain uncertain items. Use ordinary deletion and the generated-file-only attribute rules in [build inputs](build-inputs.md#protection-and-cleanup-of-artifacts-caches-and-backups).

Record decision, attempted members, actual deleted/retained paths and errors separately from test/build success. Partial deletion leaves the group partial/failed; preserve unattempted evidence and retry only after reconciling actual remaining paths and current protections. Keep command exit, durable per-item deletion results, actual absence, reference state and finalization separate. After interruption, reconcile durable per-item results, remaining paths and references before retrying; never rewrite unknown execution as success. Finalize only reconciled groups and safely reconcile empty records after verified absence and released references, retaining necessary recovery evidence without unlimited empty history. An attempted cleanup is not a deleted group.

When a tool supports reviewing or applying several independent groups in one dispatch, batch already-ready groups to reuse common observations and fixed call overhead. Preserve each group's current tokens, the same decision for every live member, references, protections and partial-failure boundary. Choose batch size from measured fixed overhead and changing file counts; do not hold ready groups until unrelated investigation finishes. Do not re-register or rehash groups whose deletion is already reconciled as complete. For long calls, use completion-aware yielding or status observation to keep progress communication available, and await confirmed completion before dependent work.

For adoption into an existing project, use its artifact-lifecycle migration playbook. Bootstrap provides a copy-ready owner; it does not migrate files or create application/runtime scaffolding.

For initial adoption or migration of unregistered legacy paths, inventory the union of producer manifests, native management records, cache records, nested ownership records and actual paths across the named roots. Resolve parent/child boundaries to one owner; overlap is not proof of ownership. This adoption inventory is not a prerequisite to every cleanup of already registered groups. Limit new discovery to unregistered or changed boundaries and concrete gaps in existing evidence. Classify metadata separately from content checks on selected exact candidates, reuse unchanged evidence and avoid repeated full-root hashing. Report representative actual elapsed time and files/bytes; do not extrapolate a small experiment to full-scope performance.

Keep unknown legacy paths in management inventory as protected/unclassified with a custodian, evidence and next discovery condition; custody does not establish a generator or deletion authority. Resolve producers and consumers before assigning generated ownership or moving items; never infer ownership from a filename alone. Report policy, actual tool availability, classification of every named root, writer/reader adoption and actual deletion as separate completion layers with their own evidence and remaining work.
