# 보드

보드는 사용자가 복잡한 요구사항과 정보를 화면에서 입력·분류·비교·배치하고,
그 결과를 에이전트에게 전달하도록 돕는 작은 프로그램이다. 이 폴더는 보드의 목록과 공통 제작 기준을 관리한다.

## 제작 요청

짧게 **“보드 만들어줘”**라고 요청하고 정리할 정보를 설명한다.

- “기능 요구사항을 분류하고 우선순위를 정할 보드 만들어줘.”
- “화면 후보를 비교하고 선택 이유를 남길 보드 만들어줘.”
- “게임 맵에 구역과 오브젝트를 배치하고 분류할 보드 만들어줘.”

제작 시 입력할 정보, 필요한 조작, 완료한 결과의 전달 방법을 구체화한다.
기존 목록과 공통 기능을 확인해 재사용하고, 새 보드를 만들면 아래 목록에 등록한다.

## 관리와 경량성 기준

상태: `target` — 보드를 만들고 유지할 때 적용할 기준이다.

- 각 보드는 `docs/boards/<name>/`에 화면과 필요한 코드를 함께 둔다.
  사용법·실행 방법·입출력·제약은 해당 보드의 README 하나로 설명할 수 있는 크기를 유지한다.
- 보드 내부에 별도 `docs/`가 필요할 정도로 복잡해지면 기능과 책임을 줄이거나 독립 프로젝트로 분리할지 검토한다.
- 프로젝트 코드, 플랫폼·표준 기능, 설치된 의존성, 재사용 가능한 라이브러리를 먼저 확인한다.
  필요한 기능에 맞춰 가장 작은 구성을 선택한다.
- 함께 사용하는 저장·백업·분류 기능은 공통으로 유지하고, 각 보드는 목적별 입력·표현에 집중한다.
  아직 쓰지 않는 확장 계층이나 빈 프로그램 폴더를 미리 만들지 않는다.
- map은 위치를 표현하고 요소를 자유롭게 배치하는 화면을 의미한다.
  게임 맵의 구역·오브젝트 배치처럼 공간을 다루는 용도로 사용한다.
- 프로그램 코드와 사용자 입력 데이터의 저장 위치를 구분해 표시한다.
  수정 중인 값, 저장된 값, 에이전트에게 전달한 결과를 사용자가 알아볼 수 있어야 한다.
- 실제 UI는 [Azrael UI 표현 계약](../architecture/ui-presentation.md)을 따른다.
  기존 레이아웃·컴포넌트·테마 토큰을 재사용하고, 밝은·어두운 테마에서 화면과 상호작용을 확인한다.

## 공통 모듈과 양식

상태: `partial` — Node 로컬 서버와 브라우저 화면으로 구현하며, 수용 범위는 목록과 개별 README에 표시한다.

Node.js 22 이상으로 `node docs/boards/server.mjs`를 실행해 loopback 주소에서 사용한다.
요구사항 보드는 외부 패키지와 번들 빌드 없이 실행한다. 편집기 패키지가 필요한 보드는
해당 README의 준비 절차를 따른다. Azrael 내장과 원격 서비스 연결은 별도 범위다.
프로그램 데이터는 브라우저 캐시가 아닌 파일에 저장한다.

### 공유할 코드와 보드별 코드

```text
docs/boards/
  README.md              # 목록과 공통 계약
  server.mjs             # 로컬 HTTP·파일 접근 경계
  shared/
    model.mjs            # 양식·데이터 검증과 항목 생성
    storage.mjs          # 저장·백업·복원
    context.mjs          # 고정된 전달본 생성
    ui.mjs               # 입력·분류·map·설정·전달 화면
    board.css            # 공통 테마와 레이아웃
  <name>/
    README.md            # 목적·실행·입출력·제약
    board.json           # 양식·좌표 체계·기본 분류
    rules.md             # 입력값 해석 지침
    index.html
    board.js             # 공통 UI 또는 보드별 화면 조합
  tests/                 # 저장·전달과 실제 화면의 회귀 검사
```

공통 코드의 계약은 이 README가 소유한다. 보드는 공통 저장 기능을 호출해 자기 데이터를 읽고 쓰며,
저장·백업 구현을 복사하지 않는다. 화면에서 공통으로 제공할 저장 위치·저장 상태·백업·분류 조작은
보드 목적에 맞는 입력 화면과 조합한다.

폴더·목록과 카드·검색 화면은 `shared/modules/folder-list.mjs`와 `card-browser.mjs`를 재사용한다.
두 모듈은 문서·선택·필터를 받아 콜백으로 편집 의도를 전달하고, 파일 저장은 호출자가 공통 저장 계층으로 수행한다.
[목록·카드 시험 보드](catalog/README.md#두-모듈의-사용-계약)가 모듈 API와 조합 예제를 소유한다.

기기별 HTML 미리보기와 디자인안 비교는 `device-preview.mjs`와 `design-gallery.mjs`를 재사용한다.
[디자인 보드](design/README.md#두-모듈과-커스텀)가 커스텀 프리셋·정적 HTML/CSS의 격리 경계와 조합 API를 소유한다.

### 새 보드의 양식

[prototype](prototype/README.md) 폴더가 작은 제작 양식이다. 해당 폴더를 새 이름으로 복사하고
`board.json`의 `id`를 폴더 이름에 맞춘 뒤 제목·필드·분류·해석 지침을 수정한다.
`node docs/boards/server.mjs --board <name>`으로 실행하고 위 목록에 등록한다.
공통 화면이 충족하지 못하는 조작은 해당 보드의 `board.js`에서 조합한다.
입력 필드는 `text`, `number`, `select`, `boolean`을 지원한다. id·라벨·기본값을 정의하고
선택 필드는 options, 숫자는 min/max를 지정한다. 프론트엔드와 백엔드가 같은 양식을 사용한다.

### 데이터와 보존

한 보드의 `workspace` 자료를 JSON 파일로 관리한다. 기본 요구사항 보드는 `schemaVersion`, `boardId`, `datasetId`,
`revision`, 제목·분류·map·항목과 저장 시각을 포함한다.
항목에는 이름과 독립적인 id, categoryId, position, size, values, note와 `specifiedFields`를 둔다.
`specifiedFields`는 사용자가 직접 조작한 양식 필드를 구분한다. 나머지는 기본값으로 해석한다.
별도 편집기는 같은 저장·충돌·백업 경계에 전용 검증 codec을 연결한다. 목록·카드 보드는
`kind: catalog` 문서의 folders·lists·items를 ID로 연결하고, 디자인 보드는 `kind: design`의 devices·states·items와 미리보기 설정을 저장한다. 스케치 보드는 그림 원본 형식을 사용한다.

데이터 저장소는 UI에서 설정하고 현재 위치를 표시한다.
기본 경로는 프로젝트의 `artifacts/board-data/<name>/`이며 사용자 데이터는 Git에 포함하지 않는다.
저장 위치 변경은 해당 폴더의 자료를 불러오는 동작이다. 기존 자료를 이동하거나 삭제하지 않는다.
원본, 백업, 에이전트에게 전달할 결과가 각각 어디에 있는지 확인할 수 있어야 한다.

저장은 수동이며 파일 교체가 완료된 기록만 성공으로 표시한다.
원본이 있으면 교체 전에 자동 백업하고, 복원은 현재 자료를 백업한 뒤 저장 버전을 증가시킨다.
원본·백업 오류와 변경 충돌은 파일을 덮어쓰지 않고 편집본을 유지한다. 백업 자동 삭제는 하지 않는다.
여러 화면은 저장 버전과 저장 위치를 확인해 오래된 편집본으로 교체하지 못하게 한다.
백업 형식·내용 해시를 검증한다. 중단된 파일 작업의 잠금은 자동으로 삭제하지 않는다.

### 기능별 책임

| 기능 | 공통 프론트엔드 | 공통 백엔드 |
| --- | --- | --- |
| 저장 위치 | 현재 위치 표시, 위치 설정 안내 | 설정된 위치 해석, 접근·쓰기 가능 여부 확인 |
| 정보 관리 | 불러오기·편집·저장, 저장 중·성공·실패 표시 | 입력 검증, 파일 읽기·쓰기, 기존 값과 충돌 확인 |
| 백업·복원 | 백업 목록, 복원할 항목과 교체 범위 확인 | 원본과 연결된 백업 보관, 복원 전 현재 데이터 보존, 실패 처리 |
| category 분류 | 분류 편집·선택·필터 | 분류와 항목의 연결 저장, 이름 변경 시 연결 유지 |
| map 표현 | 위치·크기를 가진 요소의 배치·선택, 화면 이동·확대/축소, category별 표시 | 항목의 위치·크기·분류와 좌표 체계 저장 |
| 결과 전달 | 결과 미리보기, 내보내기, 전달할 파일 위치 표시 | 기계가 읽을 데이터와 사람이 읽을 요약 생성 |

map은 요소를 놓고 옮길 수 있는 2D 배치 화면이다.
예를 들어 게임 구역을 배경 위에 놓고, 오브젝트 위치를 이동한 다음 category별로 표시할 수 있다.
화면 이동·확대/축소에 쓰는 표시 좌표와 저장되는 배치 좌표를 구분해 다시 열어도 배치가 유지되도록 한다.
좌표의 단위와 원점은 보드가 정하고 데이터에 포함한다.
category를 바꾸거나 숨겨도 항목의 위치 데이터는 유지된다.
실제 지리 지도를 사용하는 보드는 지리 좌표 체계와 지도 데이터 제공 방식을 별도로 정한다.
지도 엔진은 해당 사용 사례에 필요한 경우 검토한다.

공통 프론트엔드는 조작·상태 표시를, 공통 백엔드는 데이터 저장과 복구를 담당한다.
map 배경 이미지·실제 지리 좌표·자료 묶음 여러 개·자동 백업 보존량 정책은 후속 사용 사례에서 정한다.

### 저장 값과 지침의 연결

프로젝트 작업 지침은 이 관리 진입점에 연결하고, 사용자 입력값을 `AGENTS.md`에 누적하지 않는다.
각 보드의 `board.json`은 입력의 구조를, `rules.md`는 필드의 의미·기본값·단위·작업 반영 규칙을 소유한다.
조건과 메모는 항목 id에 연결된다. 보드 지침은 프로젝트 권한이나 설치된 지침을 변경하지 않는다.

사용자가 저장된 버전에서 선택한 항목으로 결과를 만들면 고정된 `result.json`과 `result.md`를 생성한다.
원본 버전·선택 id·원본 내용 해시, 보드 양식과 지침 원문·해시가 결과에 포함된다.
같은 폴더의 `board.json`, `rules.md`, `receipt.json`으로 출처를 다시 확인할 수 있다.
후속 편집은 기존 전달본을 바꾸지 않는다. 화면의 결과 경로를 대화에 전달해 에이전트가 읽도록 한다.

### 스케치 보드의 편집기 연결

상태: `partial` — Excalidraw 편집기를 재사용하며 Windows Chrome 저장·복구·전달을 수용했다. Linux/macOS는 미검증이다.

스케치 보드는 그림 원본의 요소·이미지·표시 상태를 저장한다. 요소의 id와
`customData.board`에 연결된 categoryId·note가 분류·메모를 소유하며, 카드 위치를 별도로 복제하지 않는다.
저장·백업·충돌 확인은 공통 저장 모듈을 사용하고 보드별 데이터 검증과 전달 어댑터를 연결한다.
수동 저장, 저장 위치 변경과 백업 복원의 의미는 공통 계약을 따른다.

편집기는 버전을 고정한 npm 패키지로 준비하고 로컬 정적 번들과 글꼴을 사용한다.
라이브러리의 CDN 글꼴 대체 주소는 보안 정책으로 차단하며 외부 응답에 의존하지 않는다.
UI는 편집에 필요한 기본 도구와 저장·전달·설정에 집중하며 서비스 메뉴와 중복 저장 UI를 줄인다.
UI 표시 변경은 편집기 코드 제거를 뜻하지 않는다. 엔진 포크·협업 서버·온라인 도형 라이브러리는 별도 범위다.

전달은 저장된 버전의 선택 요소와 연결된 글자·화살표·프레임 요소, 해당 이미지 파일을 포함한다.
선택이 없으면 전체 그림을 전달한다. JSON 원본과 PNG 미리보기·분류·메모·지침이 함께 고정된다.
색상이나 가까운 배치만으로 요구사항 관계·승인을 추론하지 않는다. 미리보기는 시각 보조 자료이며
원본 그림과 명시된 메모를 기준으로 해석한다.

### 사용자 정보가 작업으로 이어지는 흐름

1. 에이전트가 작업에 필요한 보드를 만들어 사용자에게 실행 진입점을 제시한다.
2. 사용자가 정보를 입력하고 분류·비교·배치한다. 저장 성공 여부와 위치가 화면에 표시된다.
3. 사용자가 완료한 결과를 확인하고 전달한다. 결과에는 실제 선택과 메모, 항목 식별자,
   해석에 필요한 분류·관계가 포함된다.
4. 사용자가 결과 경로를 대화에 전달하면 에이전트가 관련 데이터와 해석 지침을 읽어 요구사항이나 작업에 반영한다.
5. 추가 수정 시 저장 상태와 전달할 결과를 갱신한다. 작업에 반영한 결과를 다시 찾을 수 있도록 식별한다.

저장 실패 시 편집 내용을 유지하고 재시도할 수 있어야 한다.
읽기·복원 실패와 동시 변경 충돌은 원본을 보존한 상태에서 사용자에게 해결 방법을 보여준다.
저장됐다는 사실만으로 에이전트에게 전달됐다고 표시하지 않는다.
