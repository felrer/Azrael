# Upstream feature preservation

Status: `partial`. Feature registration, candidate-specific source checks and receipt verification are implemented and checked with source and disposable fixtures. Actual native, package and installed-host acceptance remain separate execution scopes.

Azrael accepts a Codex UI or engine candidate only after its registered behavior contracts pass against that candidate. UI source hashes, unique transformation anchors and engine provenance establish source identity and structural application; behavior checks establish the registered functional scope.

## Ownership and inventory

Architecture sections own agreed behavior under [feature maintenance](README.md#feature-maintenance). The versioned inventory at `scripts/azrael-feature-contracts.json` connects stable feature IDs, UI/engine scope, implementation owners, contract references and mandatory executable checks. Every UI injector in the namespace transformation rules must have an inventory entry. Engine coverage is explicitly registered through existing deterministic native fixtures; it is not inferred from root Git changes. Adding, changing or retiring a customization updates its owning design, inventory and behavior check together.

Official UI assets remain pristine inputs. Version-specific adapters apply Azrael-owned policy at preparation boundaries and reject unknown or duplicate anchors. Engine integration uses the selected source root and existing provenance verification; importing an inventory is not behavioral acceptance.

Deferred-turn, task-work-time, BTW and Pets retirement tests reuse complete native transform results through `scripts/ui-test-transform-fixture.cjs`. Their assertions remain unchanged. The feature inventory binds the helper and its mandatory identity/invalidation guard to each consuming feature. Reuse requires matching source bytes, exact path arguments, transform rules, actual Node/TypeScript and helper/module identities, and the complete environment. Uncertain contexts run the original transform. Test fixture reuse does not replace production transformation or final package and fresh-host checks.

Engine inventory and destination validation pin the physical root and its directory identity for one validation context. Each file still resolves its physical path and must remain inside that root; lexical path, file identity and content checks remain required. The original root is checked at phase boundaries and before returning a snapshot, and replacement with an identical-content directory is rejected. Standalone inventory and destination validators create their own context. The registered `engine.source-provenance` source check retains the root replacement and path escape regressions. The implementation and its 79 passing Python tests are verified on Windows x64/Python 3.12; four platform-dependent tests are skipped and other operating systems remain unverified.

Explicit local engine integration can record a new direct Rust crate manifest at `codex-rs/<crate>/Cargo.toml`, alongside reviewed Rust, prompt and protocol TypeScript additions. Manifests require the existing explicit expected-path declaration, tracked regular-file mode and exact content inventory; nested/root manifests and other TOML additions remain excluded. The original import and before/after descriptors remain bound by `engine.source-provenance`.

## Upgrade scope review

An upgrade reviews the existing behavior contracts and inventory against the selected baseline release and candidate. Implemented sections and explicitly retained requirements define preservation scope, including implemented parts of `partial` or `target` documents. Unimplemented targets and draft proposals remain separate implementation requirements. Any removal, reduced check scope or applicability exclusion needs its corresponding design decision and existing task authorization; a missing registration or failing check is an acceptance gap.

This review is a maintenance requirement. The current runner validates registered features and their declared references/checks; it does not discover every behavior from architecture prose or automatically compare the feature inventory with a prior release. Record these coverage and baseline comparisons in the existing work record until executable enforcement is implemented. Source provenance, matching document bytes and passing registered checks do not establish completeness of the behavior inventory.

## Candidate acceptance and receipts

The preservation runner selects UI, engine or both explicitly. UI checks execute against the selected pristine UI and transformation rules. Engine checks execute against binaries whose receipt matches the selected source. Missing owners, missing mandatory checks, failed checks and input changes during verification prevent a passing receipt.

Receipts bind the registry and check/implementation inputs, UI contents and engine provenance/binary identity for their verified scope. Packaging binds the passing UI receipt to the prepared transformation report and exact VSIX hash. Deployment requires UI and engine acceptance for the actual inputs before installing the candidate. Owners automatically reuse valid results by default only when all relevant identities match. Affected checks plus mandatory acceptance are the default scope; unknown impact broadens coverage. UI source cache schema 2 covers only the audited deferred-turn, task-work-time UI, BTW, Pets retirement, UI cleanup and provider-context behavioral commands. Keys retain the complete source snapshot including unknown fields, selected pristine UI, commands, declared dependencies, effective environment, Node and both supplied and actual project-local TypeScript runtime identities; only the copied engine package identity is excluded from that source key. Whole-gate input equality, uncached cache-owner and fixture guards, render checks and six fresh exact-package host stages remain mandatory. Each completed eligible source/native/Cargo check may publish after its own complete input/runtime and log validation under its current lease. A later failure preserves those independent entries while the whole receipt remains failed. Changed, incomplete or signalled checks never publish; final whole-gate integrity validation remains mandatory.

Logs and execution artifacts live under `artifacts/`. Checks use disposable state and deterministic fixtures; live or paid model requests are separate acceptance. A passing receipt names its verified feature IDs and scope. It does not establish full upstream regression acceptance or rendered behavior in an installed user window.

Repeated commands and upgrade procedures are owned by [development](../ops/development.md) and [source distribution](../ops/instruction-distribution.md).

## Pipeline execution and retry

Current primary-source preparation validates and deduplicates recipes before partitioning safely mapped affected packages/owners for early execution. Exact deferred recipe/check IDs remain with final native consumers, which prepare and run on a cache miss. Empty, broad configuration or unmapped native changes retain conservative complete preparation; final selected checks remain unchanged. Recipes retain exact package/features/target/profile and environment boundaries, with changed or unsupported wrappers blocking consumers. Source-only receipts cover matching source checks; complete engine acceptance still requires every selected check, current provenance and unchanged inputs. [Development operations](../ops/development.md#pipeline-verification-and-retry) owns the pipeline and current gaps.

Cargo test wrappers share explicit cache/target/profile inputs while preserving each mandatory test filter. Deterministic Cargo check evidence may reuse the existing guarded evidence store only with complete selected engine source, registry/check/contract inputs, toolchain, environment and log identity. Failures, changed inputs or incomplete evidence cannot pass. Cargo configuration is parsed with isolated Python 3.11+ tomllib; its executable, version, parser sources and helper content are part of evidence identity. Only enumerated self-contained scalar settings and target rustflags are accepted, including numeric stack options and the current Windows static CRT/ARM64 options. Unknown tools, paths, response files or flags disable reuse. The repository MALLOC_CONF environment table is accepted only with literal value `thp:always`, an optional boolean force, and absent or false relative; unknown environment variables, scalar shorthand, paths and extra fields disable reuse. Raw configuration bytes and the full process environment remain part of the identity. Schema 5 source-backed Cargo keys omit the validated release engine directory address, aggregate project/manifest hashes and execution-project location metadata. The Zod snapshot path is also omitted only with a complete directory identity containing an absolute path, a SHA-256 and nonnegative integer file and byte counts; incomplete or relative identities retain the path. Zod content and every other known or unknown identity field remain bound, and original whole-gate receipts retain raw paths. Explicit source roots, complete selected source provenance, per-group files/declarations, global registered hashes and transform rules, tools and effective environment remain bound. Only audited source-only wrapper recipes with unchanged reviewed wrapper/helper bytes may omit a complete recognized product bundle binary identity and known code-mode-host fields from their individual Cargo result key. Unknown receipt/runtime fields, incomplete receipts and changed source-only implementations remain bound. Whole-gate product provenance and binary validation remain mandatory. Target production/test/tool fingerprints must preserve the full source audit; general test-only source equivalence is not implemented, and filenames do not establish it. Unknown inputs remain bound. Whole project/manifest identity remains mandatory before and after the gate; earlier schema receipts are not migrated. An optional absolute Cargo evidence storage owner shares guarded result storage across execution snapshots without changing their frozen inputs or lease rules. The exported `CACHE_NAMESPACE` selects the independent `cargo-v2` root for both passing entries and every lease; entries are never shared across lock namespaces. Legacy `cargo` storage remains intact and protected because minimal `{token,pid}` owners cannot establish exact producer-tree termination for retirement. No PID or age heuristic retires those leases, and active or abandoned new-namespace leases retain fail-closed exclusion and explicit verified recovery. Full regression selects complete coverage while retaining valid evidence reuse; ForceNativeVerification forces selected native/Cargo checks. An unchanged build may be reused after verification failure under existing source and binary provenance. Final package binding and six fresh host stages remain mandatory; the operational pipeline owns dependency joins, failure cancellation and retry decisions.

The selected inventory feature IDs and all mandatory check IDs remain the acceptance scope. Task-work-time retains its deferred-turn integration as a separate mandatory check with the same single-file command as deferred-turn itself; selecting both features shares that execution while preserving each check record and all original test files. `scripts/deploy-azrael.ps1`, `scripts/feature-preservation.cjs` and their source/Cargo runners own ordering, handoff and evidence reuse; [development operations](../ops/development.md#pipeline-verification-and-retry) owns execution and regression procedures.

Shared namespace caching is an execution boundary: an explicit absolute owner supplies only a byte-identical, physically verified asset-cache module and its guarded store. Frozen namespace producers, rules and TypeScript remain the execution inputs. Each UI feature owns the common resolver and its mandatory guard; identical guard commands execute once while every selected check remains recorded. Cache directory and owner are bound to preparation checkpoints.

Execution checkpoints record actual starts and completions, check execution and cache lookup separately. Concurrent check durations are not summed into pipeline wall time.

Cache ownership is separate from passing verification evidence. Access-guard operations queue per cache root within one process while the filesystem guard continues to coordinate other processes. A failed owned-lease release leaves the handle retryable, and overlapping closes of one handle share the same release attempt; a failed lifecycle release retains its ownership for retry. Completed checks validate their complete current inputs/runtime, publish under their owned check/key lease and release that lease before later checks run. Final whole-gate validation rechecks both executed and reused results; a lease release or publication failure remains explicit and cannot create a passing whole receipt. Exact owner inspection and independently verified producer-tree retirement may recover abandoned leases without turning an interrupted run into a pass. Token/hash changes and live owners block recovery; a recovery interrupted while holding the access guard remains recoverable using its exact claim identity and claimant termination evidence. Cargo target-owner recovery likewise requires exact physical owner identity, token/hash and independently verified producer-tree evidence; a separate exclusive receipt precedes metadata-only retirement, without changing interrupted verification into a pass or deleting compiled payload. Module-cache project registrations require genuine lifecycle catalogs and released consumers before retirement. Missing provenance remains blocked with a recovery condition, and cleanup reports actual deletion counts and remaining paths. Implementations and mandatory source checks are registered with the shared-engine and project-maintenance feature owners; operational commands and evidence requirements are in [development](../ops/development.md#ui-source-verification-result-reuse).

Engine source preflight may supply complete, unfiltered `node --test` file coverage to the general source runner. Each feature retains its own check record when identical commands share execution. Reuse requires the same project/input identity, passing mandatory checks, intact stdout/stderr, Node executable and effective environment. The runner validates the receipt before and after execution and retains its reference; filtered checks never establish complete-file coverage. Missing, failed, signalled or changed evidence prevents reuse.
