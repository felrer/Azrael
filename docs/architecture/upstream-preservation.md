# Upstream feature preservation

Status: `partial`. Feature registration, candidate-specific source checks and receipt verification are implemented and checked with source and disposable fixtures. Actual native, package and installed-host acceptance remain separate execution scopes.

Azrael accepts a Codex UI or engine candidate only after its registered behavior contracts pass against that candidate. UI source hashes, unique transformation anchors and engine provenance establish source identity and structural application; behavior checks establish the registered functional scope.

## Ownership and inventory

### Selective upstream review records

Status: `current` for the development-tool contract; execution evidence is in the [work record](../../work/DO-01-codex-version-comparison/04-plan.md).

Collected, reviewed and accepted checkpoints are distinct. Review requires every item's decision; acceptance requires passing recorded verification for selected changes and satisfied dependencies for selected/equivalent changes. Deferred items remain backlog. Checkpoints cannot skip unfinished earlier ranges.

Records bind evidence bytes or immutable Git blobs and reference preservation feature IDs and integration commits. They do not replace provenance, execute tests, establish the truth of review conclusions or imply package/installed acceptance. Initial historical coverage remains unknown. ### Feature preservation inventory

Engine integration uses the selected source root and existing provenance verification; importing an inventory is not behavioral acceptance.

Cache ownership is separate from passing verification evidence. Access-guard operations queue per cache root within one process while the filesystem guard continues to coordinate other processes. A failed owned-lease release leaves the handle retryable, and overlapping closes of one handle share the same release attempt; a failed lifecycle release retains its ownership for retry. Completed checks validate their complete current inputs/runtime, publish under their owned check/key lease and release that lease before later checks run. Final whole-gate validation rechecks both executed and reused results; a lease release or publication failure remains explicit and cannot create a passing whole receipt. Exact owner inspection and independently verified producer-tree retirement may recover abandoned leases without turning an interrupted run into a pass. Token/hash changes and live owners block recovery; a recovery interrupted while holding the access guard remains recoverable using its exact claim identity and claimant termination evidence. Access-guard recovery shares the local mutation FIFO and uses exclusive creation of one successor claim per predecessor hash across processes. The complete predecessor chain remains until ordinary guard deletion; missing, changed or forked claims block recovery, and the current request must still own the exact claim before deletion. Cargo target-owner recovery likewise requires exact physical owner identity, token/hash and independently verified producer-tree evidence; a separate exclusive receipt precedes metadata-only retirement, without changing interrupted verification into a pass or deleting compiled payload.
