## OpenAI profiles

Profiles distinguish the login identity and workspace account; email alone is not identity. Outside the native secure credential store only IDs and display metadata are stored.

Saved profile plan metadata is a login-time claim, not proof of a current subscription. Successful native usage queries persist an observed plan only after checking the profile's workspace and user identity; absent plans and failed requests do not infer a subscription. Account-summary presentation is defined above; plan confirmation metadata is not required for displaying an observed quota.

Profile authentication homes live under `CODEX_HOME/azrael/accounts`, separate from the fixed execution home. Each profile uses a native AuthManager with strict keyring storage on the platform's native backend; there is no plaintext fallback. The engine's native external-auth provider seam resolves the selected managed ChatGPT authentication without changing the native account type or rollout root. Profile managers use the root manager's application network policy for outbound requests; loading a profile's stored identity does not invalidate that shared policy, and root account changes remain responsible for policy invalidation and reload.

Additional login uses the native OAuth server in a staged authentication home. Reauthentication replaces a profile only when both user and workspace identity match. Capturing the existing Azrael login is an explicit action, never an import from ordinary Codex storage. Removing a profile deletes local credentials without revoking unrelated sessions. The management RPC uses the `azrael/account` method and `azrael/account/updated` notification; only sanitized state and the temporary native login URL cross it.

### Credential preservation across updates

Status: `partial` — Windows source migration regressions pass with a mock keyring and the real encrypted-file backend; installed-update and native platform keyring acceptance remain separate.

Azrael restores both its root login and selected managed profile from the same isolated state home after an update. When a keyring-backed account uses the encrypted Secrets backend, cold startup migrates a saved Direct keyring credential under the account's existing cross-process credential transaction. The encrypted destination commits before the Direct entry is removed; a failed destination write preserves the saved credential. An existing encrypted auth file is authoritative, including the empty credential state left by logout, so migration cannot restore an older identity over a current login or explicit logout. Normal credential reads use the selected backend only. Migration never imports ordinary Codex storage or writes plaintext credentials. The Windows backend default requires this transition; platforms selecting Direct retain their native backend.

### MCP OAuth credential identity

Status: `current` in source with Windows regression verification; installed runtime, live provider and other-platform acceptance are separate.

MCP OAuth storage keys use a fixed, sorted JSON encoding independently of the binary's JSON map features. File, Direct keyring and encrypted Secrets storage prefer the canonical key. The transition reader accepts the insertion-order key written by existing binaries only when the canonical credential is absent; expiry is not a login timestamp and does not select the newest login. Existing duplicates without reliable write timestamps cannot establish which authorization was most recent. Reauthentication establishes the authoritative credential by saving under the canonical identity.

File saves consolidate matching server-name and exact-URL entries under the aggregate storage lock. Keyring and Secrets saves commit the canonical credential before removing the legacy alias. An alias-cleanup failure leaves the canonical credential authoritative and records a bounded warning. Logout removes aliases before the canonical key in keyring storage, and all matching entries in File, so a successful logout cannot expose a legacy credential. Storage coordination and existing File/Auto/Keyring backend selection remain with their native owners.

The transition preserves local-name escaping, executor ownership, enterprise profile identity and unrelated server/URL credentials. Legacy key interpretation is confined to credential lookup and cleanup, and can be retired after all retained credential stores have migrated. These rules apply to the common Windows x64, Linux x64 and macOS ARM64 engine; platform and installed-service acceptance remain distinct. Preservation feature: `engine.mcp-oauth-store-identity` in the [feature inventory](../../scripts/azrael-feature-contracts.json).

### Window selection and shared credentials

Each window may independently select any account, including one selected in another window. Root and managed-profile usage take shared OS leases. Credential refresh takes a separate cross-process transaction lock with a 30-second admission deadline and reloads persisted tokens before contacting the authority, so concurrent instances reuse persisted credentials. Identity-changing native login, capture and logout require exclusive usage admission; same-identity reauthentication is serialized with refresh. Account removal follows the deletion-priority contract below. If an older engine holds an exclusive lease, a new engine starts without borrowing its root credentials and still offers account selection; it never terminates the older engine or removes its lock. Runtime selection is engine-local.

Selected-account state uses two host-private paths. `AZRAEL_EX_ACCOUNT_STATE_FILE` is scoped by workspace storage and a hash of the opaque VS Code session ID (global storage for empty windows), preserving independent selections in simultaneously open windows. `AZRAEL_EX_ACCOUNT_DEFAULT_FILE` is stable per workspace (or global storage for empty windows) and holds the last committed selection as the default for a new editor session. An existing session file, including an explicit empty selection, takes precedence; otherwise startup restores the default. A completed switch or explicit clear atomically replaces both files and reports a save failure if either replacement fails; pending, cancelled and failed switches change neither. A missing default is initialized from the most recently modified valid legacy session selection in the same storage scope, reading only the sanitized selected-profile JSON and never credentials. Runtimes that supply neither path fall back to `CODEX_HOME/azrael/account-state.json`. The wrapper does not change `process.env`.

When a window has no managed-profile selection, the account snapshot still marks a saved profile active when both its workspace account ID and user ID exactly match the engine's current authentication, so the page shows the actual account on first open. Snapshots carry an instance-local revision so delayed responses cannot revert newer UI state. Authentication cache reload and refresh discard results from a provider replaced while the request was in flight.

Account removal does not wait for another window to release its usage lease: the shared retirement state stops affected work before serialized credential cleanup. Missing storage and denied access are reported only for their confirmed I/O error kinds; unclassified failures are not attributed to authentication or leases. Lock files are never deleted to force admission.

## Switching

Manual switching is scoped to the connected engine. Automatic quota recovery follows the opt-in contract below. Active or approval-waiting turns defer a switch without cancelling work; pending switches are visible and cancelable. A switch atomically blocks new turn admission and verifies idle, validates target authentication, refreshes account-dependent native state, verifies the actual identity, then emits native account events and resumes admission. A failed switch keeps or restores the previous identity; uncertain recovery blocks new work. Account changes propagate to official host/cloud authentication as well as local model requests.

Execution leases follow actual core task lifetimes, including completion and child handoff, rather than delayed UI status events. Existing tasks finish their child work, and a switch tries the exclusive lease without queueing a writer to avoid parent/child deadlock. Realtime conversations and detached memory inference also hold execution leases.

Ordinary composer input and automatic dispatch still wait for the switch. It cannot enter an exclusive account commit or failed account recovery. ## Account retirement

Status: `partial`; native/profile/core regressions, managed-provider helper tests and isolated two-engine OpenAI retirement/restart acceptance pass. Account pages are verified in light/dark themes. Release packaging and installed-host acceptance remain pending.

Removing an OpenAI or managed-provider account takes priority over its use in other Azrael sessions. The removal becomes authoritative before credential cleanup. Every engine observes the shared retirement state, blocks new work on that account and interrupts affected running work and parked reservations. The account is removed from management lists; credential refresh, pending login and reauthentication cannot recreate the removed profile. Credential cleanup remains serialized with refresh. The operation does not revoke unrelated remote sessions or remove other accounts.

A confirmed permanent authentication failure, including a revoked refresh token, retires the affected account from execution while retaining its registration for explicit reauthentication or removal. A transient network failure, an unreadable store or an unclassified HTTP 401 is not proof of deletion. Explicit successful reauthentication can restore an unavailable account; it cannot undo an explicit local removal.

After stopping affected work, the engine chooses a healthy account of the same provider, preferring accounts with automatic switching enabled and then other registered accounts. Candidate validation establishes usable authentication and identity before publishing the replacement. The session and workspace default select the replacement so restart cannot restore the retired identity. When no valid replacement exists, the engine remains stopped and reports that login or another account is required. For OpenAI, a credential-free recovery flag in both selection stores preserves this state across restart and prevents leftover root credentials from becoming an implicit fallback. Successful explicit recovery clears the flag.

Interrupted work keeps its conversation, recorded tool results and pending inputs. Switching accounts does not restart the interrupted turn, replay tools or automatically dispatch its queue or reservation. Managed-provider replacement changes the binding used by future turns; stopped turns retain their original account attribution. Sessions and providers that do not use the retired account continue normally. The account-removal confirmation explains that removal applies across sessions and stops affected work.

## Management connection recovery

The pinned host's model catalog listens for native `account/updated` notifications. It invalidates the affected host's cached model list and requests fresh backend discovery. An account update during discovery schedules another refresh after the pending query finishes, so the picker updates without a manual refresh.

Management startup has one 70-second budget covering owner readiness, connection retries and account identity verification. Each native bridge connection receives at most 65 seconds within the remaining budget. Standalone readiness observes the owning app-server's successful initialization handshake; integrated endpoint discovery is not readiness, and the bridge must complete private registration and initialization. Transient endpoint failures retry with capped delays until the budget expires. Home, version and engine-identity mismatches, permission failures and invalid protocols fail closed. Recovered startup failures leave no permanent disabled notice; disposal cancels readiness waits and scheduled recovery.

Native terminal failures use the bounded `azrael/bridgeError` schema: phase, closed error code and retryability. The host preserves those fields with attempt number, child PID and elapsed time in its bridge output channel. Raw stderr, paths, credentials and RPC contents are not copied into diagnostics. A disconnected or timed-out mutation that was handed to the bridge has an uncertain outcome; reconnect and query state before deciding what to do. Reconnection never replays account, Devin or root-resume mutations. Late events from a replaced bridge cannot invalidate the current connection. Windows source-level coverage verifies these contracts; installed-host acceptance and Linux/macOS execution are separate verification scopes.

The reservation management page and inline wait controls offer an explicit **관리 연결 재접속** action after management connectivity is lost. It reconnects through the existing bounded startup and verifies the same home, version and engine instance before querying reservations. It does not reset engine identity or resend a resume/cancel/account mutation. Only the owning supervisor's verified engine restart may reset the instance through its separate recovery path. Concurrent reconnect actions share one operation. A successful reservation refresh clears connection errors in every embedded surface while preserving reservation/action errors. Responses from an earlier connection or superseded request cannot restore stale error or reservation state. Connection messages distinguish unavailable management controls from the engine's independent scheduled execution; a disconnected host cannot promise whether a reservation will run.

Host bridge diagnostics additionally classify protocol failures with a closed, content-free `protocolReason`: malformed JSON/message/connected notice/native failure notice, a native protocol failure, or request encoding. Native protocol failures remain a broad category until native evidence identifies their cause. The optional field does not change the native bridge wire schema or permit raw payload logging. This recovery and diagnostic extension is a source contract; packaging and installed-host acceptance are separate gates.

Processed reset timestamps are retained in a bounded history and excluded from future scheduling. Active attempt guards schedule a read at their expiry without authorizing another request before then.

Reservation policy migration runs once under the account's OS lock and persists atomically. Enabled legacy reservations return to a fresh usage check; explicit ON/OFF, observation history, processed resets, attempt guards and uncertain in-flight confirmation are preserved. Migration itself sends no model request. Re-registering the same account or transferring reservation ownership to a surviving profile also requests fresh verification while preserving these guards. Reservations belonging only to removed accounts remain inactive. A policy-version marker makes migration idempotent across restarts and windows; a busy owner retains its committed snapshot until the lock is available.

Zero usage with missing, past, or full-duration sliding reset timestamps is a suspicion. A second observation at least ten seconds later must implicate the same window before inference. Failed queries, unknown durations and missing included-usage permission never authorize a model request. A stable future absolute reset or positive usage confirms progress; integer-rounded zero alone cannot establish failure. Confirmation evaluates the supported ordinary windows together, so a request is not assumed to start both periods.

Before inference, the engine persists confirmation state and a per-window attempt guard covering that window's period. Transport retries are disabled. A timeout, crash or failed response leads only to confirmation queries, never a replay of that attempt. Confirmation retries after 15 and 45 seconds are steps of the same account reservation. An unconfirmed outcome is shown explicitly. Disabling and re-enabling preserves attempt guards. Failed usage reads back off up to ten minutes without authorizing inference or fabricating a refill.

The Devin CLI identity's quota comes from the official CLI's read-only interactive `/usage` screen. A bounded PTY child in a dedicated working directory (`~/.azrael-ex/azrael/devin-usage`) runs only `/usage` and `/exit`; no model prompt or credential export occurs. A headless terminal emulator reconstructs the daily/weekly percentages and reset times. This is a pinned CLI presentation contract, not a public API: unknown output or timeouts produce an explicit error while keeping same-account last-success data as stale. CLI identity is checked before and after the query, and data is discarded when it changes. Omitted extra-balance values are not fabricated. The page owns polling while visible; closing it cancels work. The PTY and terminal-emulator dependencies ship inside the host's account module. Managed Devin accounts show quota as unsupported until an account-scoped source exists.

For OpenRouter, successful key information is usage evidence even when the per-key cap is `null`. Returned spend is shown in USD, and unset, zero and positive caps and unavailable data are distinguished. An unset per-key cap does not establish unlimited balance, and lifetime usage is not subtracted from a resettable cap when authoritative remaining-cap data exists.
