## Native instruction state and prompt projection

Status: `partial` — The selected engine implements typed instruction-state projection and dynamic Apps, Environments and Plugins guidance. Existing source tests are evidence for their declared fixtures; this documentation audit does not execute Rust tests or establish package, installed or live-provider acceptance.

The engine projects a prompt copy before discarding typed provenance or estimating prompt tokens. Only explicitly replaceable instruction kinds with their expected producer role and complete provenance can replace earlier state. Removal notices use the same kind and withdraw that producer's previous contribution. Ordinary additive instructions, malformed or untyped content, wrong-role content, user messages and stored conversation history keep their existing meaning. Prompt projection does not delete recorded history.

Apps, Environments and Plugins producers refresh their guidance when availability changes and emit explicit disabled/withdrawn state so previously enabled guidance cannot remain active merely because it is in history. A complete host skill catalog replaces an earlier catalog; environment deltas retain their additive meaning. Selected skill bodies reuse the last identical body for a normalized path, while changed bodies or an intervening replacement require the current contribution.

Custom API prompt copies additionally filter known desktop-control skill entries and selected bodies using typed skill fragments, without removing similarly worded untyped history or unrelated skills. Their catalog, deferred-tool search and token-estimation boundaries are owned by [API request context projection](custom-api-models.md#요청-컨텍스트-투영). This request-time projection is distinct from installing instruction files: file distribution and captured thread instructions retain the lifecycle below.

The engine owners are `codex-rs/core/src/context/instruction_state_projection.rs`, `core/src/world_state/{apps,environments,plugins}_instructions.rs` and `ext/skills/src/{world_state_catalogs,host_prompt}.rs`, relative to the selected engine source. These native contracts are outside the registered `ui.instruction-settings` check's settings-surface scope and require separate preservation review.

Provider/model behavior templates and runtime/tool guidance are composed through [model harness profiles](model-harness-profiles.md). User templates replace the behavior layer; sandboxing, approvals, declared-tool eligibility and user/project provenance stay with the native runtime. Maintained profile prompts have identical embedded copies alongside the common agent behavior.

## Work intent, entry and feature preservation

Status: `partial` — maintained instructions and active skill files define this policy; model behavior in real use remains a separate acceptance condition.

Common work-entry guidance identifies the conversational goal, requested deliverable, allowed actions, settled decisions and open questions before choosing a skill. Follow-ups retain this context: a design-stage request to refine an idea refines the design, while an authorized implementation-stage refinement stays within that implementation. Mentioning a skill or a needed change does not grant execution authority. Clarification is needed only for unresolved interpretations that change scope or authority; settled permissions persist across turns.

Entry uses `design-collaboration` when linked user choices require iterative discussion, or `development-workflow` when investigation can gather the approach and questions into one plan. Technical size alone does not determine the route. Discussion and planning share one work record containing understanding, requirements, design differences, recommendations, decisions and verification; no prerequisite understanding document is required. Small tasks use short plans without unnecessary approval waits. Questions remain in the document and are surfaced by a conversational link and key decision. `design-documentation` maintains enduring agreed design in its existing owner, and `implementation` executes the resulting plan within existing authority. Specialized skills and route changes cannot expand that authority or restart settled approval.

Both routes compare agreed architecture with code, tests and observed behavior to preserve features, constraints and permissions. Draft proposals and missing documentation do not authorize removing an existing feature. Unapproved architecture deviations, deletion, hiding or disabling of features, and weakened verification to evade an error receive review before affected implementation. New execution findings return only the changed decision to the same record while independent authorized work continues. A fix is checked both for resolving the failure and for preserving existing behavior; architecture is updated for agreed changes, not rewritten to justify a reduction after the fact.

Policy acceptance distinguishes file/format checks from conversational behavior: design-stage change mentions and refinements stay in design, explicit execution requests change only the authorized scope, linked planning decisions reuse the same record, and error-driven feature reductions trigger review. Intent interpretation, selected skills and performed actions must all agree in real-use tests before claiming behavioral acceptance.

## Sources and releases

The Azrael repository owns the complete instruction library in `instructions/`, including agent roles, skill reference material and scripts, project playbooks, examples and documentation. Its `azrael-environment.json` declares independent semantic version `instructionVersion`, schema version 1, minimum compatible Azrael version and installable components. Source files retain their upstream provenance; Azrael-owned code and instructions use MIT, while imported engine and dependency notices retain their original conditions.

The skill components are `development-workflow`, `design-collaboration`, `design-documentation`, `implementation` and `project-bootstrap`, all selected by default with their support resources. Their source-relative paths, original and copied hashes and distribution adaptations are recorded in `SKILLS-SOURCE.json`; `SOURCE.json` retains the historical library import. Common execution guidance belongs to `implementation`. The optional workspace playbook component applies app logging guidance, while project-specific Work guidance remains under its existing owner.

Root scheduling guidance is an engine-owned developer instruction with the [root coordination contract](root-coordination.md). It applies across Azrael projects independently of instruction-library installation and configured role text, without enabling delegation or expanding authority. Shared worker rules and project-specific constraints remain in their existing owners. Removing legacy AGENTS coordination text from an active installation requires confirming that its installed engine supplies the replacement guidance.

An instruction release uses tag `instructions-vX.Y.Z` and three assets: `azrael-instructions-X.Y.Z.zip`, `azrael-instructions-X.Y.Z-manifest.json` and `azrael-instructions-X.Y.Z-documents.json`. The external manifest identifies the repository, source commit and source content digest, archive and document asset sizes/hashes, every archive file's relative path/size/hash, and component definitions. The document asset maps listed text-document paths to their content for browsing before downloading the complete package. The archive contains the entire instruction source tree; selecting components affects application, not download completeness.

Components have unique `id`, `title`, `kind`, `default`, `scope` (`home` or `workspace`) and `files` with `source` and `target`. Home targets are confined to `AGENTS.md`, named `agents/*.toml`, named `skills/` directories and the separately merged agent configuration. Workspace playbooks target `docs/playbooks/`. A configuration component reads `config.example.toml` and merges only the declared agent configuration keys into the existing `[agents]` table; credentials, root model, sandbox and unrelated settings stay under their existing owners. Preview and planning expose differences and unmanaged or locally edited target conflicts before application.

## Version acquisition and integrity

The host downloads through bounded HTTPS requests to GitHub's API and release-asset hosts. The configured repository defaults to `felrer/Azrael` and can be changed in Azrael settings. It queries instruction tags, excludes drafts/prereleases from latest compatible selection, validates schema/version/app compatibility and binds all asset selections to that release. Git is not needed. A pinned version remains authoritative until explicitly unpinned. Activation does not silently download or replace instructions.

Caches live at `CODEX_HOME/azrael/instructions/versions/<version>/`. Each contains a verified manifest, complete extracted package and document preview data. The installer state at `CODEX_HOME/azrael/instructions/state.json` records applied version, repository, pinned version, selected component IDs and managed original hashes. Version cache entries are immutable for their recorded repository and content; a different release claiming the same version cannot replace them silently.
Reopening settings restores downloaded versions and document previews from the
verified local cache without a network request. Missing or corrupt cached
documents cause an error; initial page loading does not repair them over the network.

Archive extraction rejects absolute paths, `..`, backslashes, Windows aliases/reserved names, symlinks, duplicates, case collisions, unexpected files, excessive entry sizes and total size. Actual file bytes must match the external manifest. A checksum from the same release establishes content integrity, not an independent publisher signature. Downloads and validation complete before active files are changed. Cancellation and network or validation failures preserve the current installation.

## Application and recovery

The application plan uses the selected components and hashes from the last successful installation. Existing unmanaged files whose content differs from the proposed file and files differing from the managed originals are conflicts. An identical unmanaged file can be adopted without rewriting; its original bytes are retained for restoration. Conflicts are shown with current/proposed content and stop mutation; they are never overwritten automatically. Removing a component or a file restores the recorded original or deletes an unchanged newly managed file. Unrelated files in a skill directory are preserved.

Application takes an exclusive lock, captures source and destination states, stages complete output, validates the staged native agent configuration using the selected engine, rechecks for concurrent edits, and records backups and a recovery journal before replacing files. It commits the state receipt last. Handled failures restore the affected files and receipt; interrupted commits leave explicit recovery data and require recovery before another mutation. Pin/unpin uses the same state lock and preserves applied file state. Rollback selects a previously verified cached version and follows the same conflict and compatibility checks as an update. Running threads retain their captured instructions; new threads use the applied instruction files.

## Selectable instruction packages and task profiles

Status: `draft` for the detailed package and task-activation contracts. Independent instruction resources plus composed task profiles are agreed product scope, recorded in the target contract below. These details preserve the agreed sharing classes and save/apply/publish separation; they do not establish implementation or approve changes to the application's installed defaults.

The maintained release currently has ten selectable components: global `AGENTS.md`, two agent roles, five skills, an optional workspace logging playbook and agent configuration. The home components are selected by default in the existing release manifest. These are distribution components, not proof of current remote publication. Engine-owned runtime identity, root coordination, permission enforcement and provider/tool eligibility retain their native delivery and are not selectable instruction resources.

The proposed reusable unit is a versioned package, with a stable identity, kind, content digest, complete support-file inventory and declared dependencies. The kinds are `skill`, `agent-role`, `context` and `task-profile`. A context package groups a coherent guideline, playbook or reference set; it declares whether its content is persistent task guidance or material to load when needed. An agent role includes its task responsibility, instructions and declared model requirements. An import never copies the full source `config.toml`, credentials or machine-specific execution settings.

An individual resource can be browsed and imported independently. A task profile composes references to versioned resources with a provider/model selection, reasoning settings, task instructions, harness composition and optional role requirements. It records a repeatable recipe rather than embedding duplicate copies of every skill. One repository release may contain several packages; the publication archive boundary, reusable package boundary and task activation boundary are distinct.

For example, a repository-review profile can select a review model, a review guideline context, a repository-inspection skill and an explorer role. Import displays the profile and required package versions; the user can inspect that complete set before acquiring it. Importing the explorer role does not itself spawn a child. Profiles declare required resources separately from optional extras; omitting a requirement makes the profile unavailable, rather than silently substituting empty context.

Imported packages enter the user's local library without modifying global `AGENTS.md` or immediately changing a running conversation. A separate Apply operation makes their frozen resources available to a new selected task. Save and Publish retain their existing meanings. Library availability, installation destination and activation are separate: user-level storage does not make all imported instructions active in every conversation. Explicit global or project default changes need their own visible application scope. The proposed initial activation scope is a new conversation selected with a task profile; a project default is an optional later choice.

The existing native named configuration profile can supply model/provider/reasoning settings; the existing [harness profile](model-harness-profiles.md) supplies compatible behavior templates and tool composition. A task profile is a shareable composition above those two owners, not an account login profile. Its resolver adds resource selection and task-context provenance, which existing harness definitions do not currently carry. The profile-management UI and native task-resource admission require additional implementation and acceptance.

Regular task guidelines are additive context with explicit source attribution; they do not wholesale replace global/project `AGENTS.md`. A behavior-template replacement, if a profile declares one, follows the existing harness semantics and is shown explicitly in the application preview. Native runtime instructions and authority retain their independent meaning. The resource resolver must not promise a task has isolated context merely because a list is filtered in the UI: model catalogs, prompt projection, tool discovery and execution admission must agree on the active selection.

The default model policy remains a proposal: record a recommended model and permit an explicit local override, while preserving the shared recipe and recording the effective choice. Required provider/tool compatibility and capabilities are checked after any override. A missing model or login prompts for an explicit compatible selection rather than silently choosing another provider or a more expensive model. A strictly fixed-model profile is the alternative policy under discussion. A task captures its effective model, resource versions and context digests; later package updates do not mutate that captured task.

Context is classified by loading behavior. Short task goals and rules can enter the task's persistent prompt; complete skill bodies and longer references retain on-demand loading. A profile does not unconditionally inject every support file or the user's conversation history. Preview shows persistent instruction content, available skills/roles, required connections and any local variable bindings. Tokens, account sessions, personal memories, absolute local paths, private workspace files and raw conversation snapshots are excluded from shared profile exports. Local context attachments remain local task bindings unless explicitly made a shareable context package.

Dependencies are pinned to approved versions and content identities. Cycles, missing dependencies, conflicting install names and incompatible harness/provider combinations stop Apply. Publication checks dependencies before emitting even their identifiers: a public profile cannot reference collaborator-only or local-only packages, and a collaborator profile cannot reference local-only packages. The user must change the dependency's publication scope or remove it from the profile. Local profiles may use resources the user can access. Updating a resource or changing its class shows affected profiles and requires explicit profile-version review; published recipes do not silently follow a moving latest dependency.

The proposed UI has a library with filters for Skills, Agent roles, Context and Task profiles, with common search, sharing class and publication state. A task-profile detail shows the recommended model, required/optional resources and effective application scope. A new-task entry selects a local task profile, previews changes and starts with a captured configuration. The baseline instruction bundle remains a separately identifiable distribution source; optional resources need no mandatory application install to be browsed or acquired.

Initial verification must distinguish availability from activation: acquiring an unused package does not change ordinary task prompts; selecting a profile activates its approved persistent context and catalogs with native ownership; deselection in a new task removes that profile contribution without removing runtime/project instructions. Also cover dependency version preservation, unavailable models, provider incompatibility, publication scope leaks, local overrides, token budgets and child role availability without automatic delegation. Existing personal-library integrity, source-separated caches, collision handling and recovery requirements still apply.

## Personal skill management

### Agreed product contract

Status: `target`. This extends the existing instruction settings surface. The source, package and installed acceptance of the existing release installer do not establish implementation of personal skill management.

Azrael provides one management surface for personal skill sources, installation and sharing. A skill includes its `SKILL.md`, scripts, references, templates and other support files. Sharing applies to the complete skill folder rather than individual files.

Sharing supports both independently acquired instruction resources and task profiles that compose resources with model settings. A user can acquire a complete task profile or reuse an individual instruction resource. The detailed package schema, dependency resolution and task activation are specified by the draft composition contract above.

Three sharing classes are supported: public, one fixed collaborator group and local only. Public and collaborator content use separate GitHub repositories. Repository access controls the fixed group; membership in the Azrael application repository does not automatically grant access to the collaborator skill repository. Local-only content is excluded from Git tracking by the application repository and from all publication inputs. The management directory may reside inside the local Azrael project, while each remote repository remains independent.

New and first-imported personal skills default to collaborator sharing. This selects their intended publication destination without transmitting content. Existing verified remote provenance is retained rather than treating an imported published skill as unpublished.

Save updates only the local management source. Apply separately updates the Azrael installation and takes effect in new conversations. Publish separately presents the destination and included changes before transmitting them to GitHub. Apply and publish are independent: publication does not install a skill, and installation does not publish it. Running conversations retain the existing instruction lifecycle.

Sharing-class changes preserve past Git commits and release assets while restricting subsequent publication to the new class. Entries retain a `Previously published` indication with their known destinations and versions. Collaborator publication is available to every user with actual write capability on the collaborator repository; Azrael does not impose a separate owner-only publication role.

Local-only means exclusion from skill-sharing repositories and publication. It does not define a new model-inference policy: normal use of a selected skill remains governed by the native prompt and provider context contracts.

### Proposed source, data and installation structure

Authoring sources, remote read caches and private metadata have separate subdirectories. An explicit publisher assembles public or collaborator output outside the source tree from approved skill IDs and file inventories. A different configured management root uses the same containment and publication rules. An already tracked directory is not accepted as protected solely because a `.gitignore` rule exists.

The existing `instructions/` remains the owner of the maintained baseline instruction bundle, global guidance and agent roles. Bringing its skills into the management surface retains their source ownership instead of creating competing editable copies. Managed baseline skills can reference their existing owning directories; the publisher still selects explicitly approved content. Personal additions, collaborator sources and local-only content must not be placed in the baseline release tree. The existing whole-tree baseline release builder requires a separate boundary review before combining it with personal publication.

Each library entry has an immutable `skillId`, editable display name, validated engine skill name, source location and provenance. A renamed skill keeps its identity; its old installation name is removed only by an explicit apply plan. The registry records desired sharing class separately from known published destinations. Local metadata records the current content digest, installed digest and receipt owner, and publication commit, release and manifest digest for each destination. Tokens and machine-specific paths are not publication metadata.

The proposed first personal-skill installation target is `CODEX_HOME/skills/<engineName>`, matching the current Azrael personal installation. Duplicate names are not silently renamed or installed over another source. A skill name can have only one installation owner per destination.

Validate `SKILL.md` frontmatter and complete support-file inventory before apply or publish. Reject escaped paths, symlinks and case-colliding names; retain the existing platform path protections. Incomplete edits can be saved as invalid drafts, with apply and publish unavailable and specific errors shown. Importing or editing a skill does not execute its scripts.

Reuse the existing installer's staged writes, original-file receipts, content hashes, locks, conflict handling and recovery. Extend receipt ownership to stable source and skill IDs before managing overlapping destinations. A local application plan compares source, previous receipt and current installation. External installation edits stop application; the user can bring them into the source, compare them or explicitly replace them after review. Unrelated files remain protected. Undoing an installation restores preserved originals or removes unchanged managed files. Deleting a management source and uninstalling it are separate operations.

### Proposed GitHub connections and publication

Each connection records a stable source ID, repository identity, branch, expected visibility, account and available read/write capability. Public and collaborator connections must refer to different repositories. Connecting checks the actual repository visibility and access; changing a repository's visibility externally blocks incompatible publication until reviewed. The application does not silently create repositories, invite collaborators or change repository visibility. Initial repository setup is an explicit onboarding action.

Prefer the host's GitHub authentication session when available. A scoped token alternative uses VS Code SecretStorage if the installed host cannot supply a suitable session. Authentication-provider availability is verified in the actual Azrael package before choosing the supported route. Credentials stay in the host and credential owner, never in webview messages, source files, publication manifests or diagnostic logs. See [VS Code authentication and secret storage](https://code.visualstudio.com/api/references/vscode-api).

Read access permits remote browsing, download and local installation. Write operations require actual repository write capability. Every writer can publish under the agreed group policy. The UI reflects the actual GitHub permissions rather than claiming an access restriction from button visibility. Private repository visibility alone is not an application-enforced read-only grant.

Use GitHub APIs for remote source commits and release assets so ordinary browse and installation retain the existing no-Git requirement. A publication freezes the approved source bytes, target repository and sharing class, complete file list, base branch commit and release version. Changes made while publication runs remain newer local edits and are not added to that operation.

The outgoing repository tree combines the accepted remote base with only the selected skill changes. The release represents that complete resulting repository inventory, preserving unselected published skills and excluding unselected new local entries. It does not publish every locally edited skill merely because it has the same desired destination. Files outside the managed skill roots and generated release metadata are not edited by skill publication.

Build one commit from the approved changes and update the branch without force. A changed remote branch stops publication for review and a new comparison; remote work is not overwritten. GitHub supports non-forced reference updates and reports conflicts. See [Git reference updates](https://docs.github.com/en/rest/git/refs).

Publication has two visible milestones: source commit accepted and installable release published. Assemble the existing archive/manifest/document format from the frozen, filtered source; upload a draft release and publish it only after every expected asset is verified. Advance the published receipt only after the installable release is complete. If the commit succeeds but asset publication fails, report that the source is already shared and retain the exact commit/version for retry. Retrying must inspect remote outcomes before creating another commit or release. The operation does not promise a transaction across GitHub commits and releases.

Public and collaborator repositories maintain independent instruction release versions. The cache key includes repository/source identity, version and manifest digest, rather than version alone. Pinning is per source; one installed destination still has one owner. Keep a single coordinated installation ledger or equivalent shared destination lock across sources, so separate stores cannot race to install the same name. Existing single-source receipts and immutable caches need a staged migration with provenance retained; the old layout is not simply opened by both new sources.

Private assets are fetched through the authenticated GitHub asset API. Credentials are attached only to the authenticated GitHub API origin and are not forwarded to redirected asset hosts. Public downloads can remain anonymous. See [GitHub release asset download](https://docs.github.com/en/rest/releases/assets).

The package, manifest, document previews and release notes contain only the approved destination's skill inventory. File names, private source paths and the complete local registry are excluded when not public. Local-only metadata never enters remote payloads. Logging records operation IDs and outcomes, avoiding private document bodies, credentials and publication previews. Backups and recovery snapshots containing private or local data stay local and are excluded from app/release artifacts.

### Proposed scope changes, updates and recovery

Changing the desired class changes future publication selection. Applying a scope change does not erase known publication destinations. The publication preview identifies additions at the new destination and any removal from the current source tree at the previous destination. A move across repositories records both outcomes independently and resumes only unfinished steps after failure.

The history policy preserves old commits and release assets. Public-to-collaborator or shared-to-local transitions display `Previously published` with the known destinations and versions; they never claim previously published bytes have become confidential. New local-only changes are excluded from every publication. Scope changes do not delete historical releases or rewrite Git history, and copies already downloaded remain outside the application's custody.

Update checking is explicit. Opening the settings page restores local state and verified caches without automatically contacting GitHub. A downloaded update is not automatically applied. Compare local source, the last synchronized base and remote source: when both sides changed the same managed entry, require a comparison instead of silently replacing it. Pinned sources retain their selected version until unpinned. Offline save, comparison and local apply work without GitHub; publication remains pending until a requested retry.

Operations are serialized per library and installation destination. Host-side validation binds each approved action to its frozen input digest and account/repository identity. A changed source, target, permission or library revision requires a new plan. Cancellation before mutation discards preparation; after a remote commit, cancellation preserves the known remote result and records what remains. Interrupted local changes use a recovery journal; interrupted remote publication uses commit/tag/asset identifiers and confirms actual server state on explicit recovery. Recovery does not publish newer edits or widen the sharing class.
