# Switched multi-pointer experiment

Status: `target` — standalone Windows x64 development prototype. Native input, real-app effects, installed MCP availability and human concurrency require separate acceptance. Feature: `tool.multi-pointer` in the [preservation inventory](../../scripts/azrael-feature-contracts.json).

## Behavior and authority

Multiple logical pointers retain separate screen coordinates and colored, non-activating overlays. Moving an overlay does not move the physical Windows cursor. Clicking, dragging, scrolling or typing switches the shared Windows input stream and foreground to that pointer's bound application. This is Switched operation; it does not provide simultaneous independent OS mouse/keyboard streams or background-only input. With collaboration disabled, foreign hardware input can interrupt an action and leave a partial application effect. Explicitly enabled and proven relative-mouse routing queues supported user gestures; physical keyboard input and routing failures still stop model input.

The standalone MCP is started explicitly with a verified native runtime and a fixed target allowlist. Each entry pins the root HWND, PID, process creation time and executable of a same-user, non-elevated process on the local default interactive desktop. A tool cannot add targets. The bound application includes its visible, enabled popup surfaces only when a bounded, same-process window-owner chain reaches the exact pinned root; unrelated windows of that process remain excluded. Target replacement or physical held input prevents actuation; foreground/occlusion preparation follows the bounded recovery target below. Action coordinates are physical screen pixels inside the bound main client area, including popup coverage within that area. When Windows refuses programmatic foreground activation, the broker can select that same main root by a real tagged click on an exposed nonclient point reporting `HTCAPTION`. It rechecks visible hit identity before input, excludes window control buttons and does not click through another app. No exposed safe caption means this fallback fails. Caption selection can already change the foreground before a later input check fails; results must retain that partial action.

The standalone MCP does not itself grant managed Window Use authority. The optional integration below has a separate capability and consent; existing semantic and DLL-input grants do not enable it. Linux, macOS, remote desktops, other users, elevated/protected targets and x86 are outside this prototype. Virtual desktop axes above 32,768 pixels are rejected because this prototype requires exact physical-pixel positioning through 16-bit absolute input. Caption hit testing also requires its screen coordinates to fit the Win32 signed 16-bit message representation.

## Input and stopping

The native executable draws overlays and monitors low-level input in its own process; it does not inject a DLL into target apps. Actions use documented Windows input APIs, with own injected events tagged so they are distinguishable from physical input. Pointer switches release previously held synthetic state. Unsupported or unverified physical input, the emergency stop, `stop`, EOF and process shutdown stop further model input and release tracked synthetic buttons/keys. Supported physical mouse gestures use the cooperative queue only after capability preparation succeeds. Unknown delivery is reported without replay or alternative injection.

Delivery success means the OS accepted input. It does not prove a rendered stroke, selected control, text edit or absence of foreground interference. MCP results preserve this distinction and include observed pointer/foreground state. Unicode text injection is separate from IME composition. Keystrokes reach the active app focus; the tool does not replace values through UIA or clipboard operations.

## User and model collaboration

Status: development source implements the mouse-first routing and FIFO contract below. The Windows Paint trial observed model strokes during physical motion, queued user operations, two-target foreground switching and rendered Unicode text. Cursor ownership acceptance is blocked by a reported drag-completion jump toward the model endpoint. The system cursor may move first and the logical user pointer may then resynchronize to it; event ordering remains under investigation. Click-location confirmation alone does not establish correct final cursor restoration. Installed Azrael has not been replaced. See the work record for run evidence.

Ordinary user input is available while the model is idle. During authorized Window Use input, user and model pointers retain distinct positions and submit operations to a shared input scheduler. A user click must not cancel the model or end collaboration. Observation alone does not reserve the shared input stream. Cancellation, stop and connection loss release model-held synthetic state and leave ordinary user input available. The user must not configure a replacement device or individual process IDs to use this flow.

The native routing layer collects physical motion separately, displays a user pointer while the model owns the OS cursor, and prevents that motion from redirecting the model's current gesture. Raw Input collects motion; a low-level hook suppresses legacy events during the capability probe and model-owned input. Raw Input registration alone does not replace mouse routing in other processes. Hook timeout/removal, raw-input-consuming apps, pointer acceleration, absolute devices and restoration of the latest user position require real acceptance before claiming isolation. No driver or target DLL is included in this implementation.

Own synthetic mouse events require a one-use full-tag injected hook receipt matching the raw packet's marker, event time, kind and shape. A raw packet arriving before that receipt is quarantined for at most 20 milliseconds in a fixed eight-packet buffer; a marker alone never admits it. The next synthetic mouse input waits for both notifications to reconcile. Missing, inconsistent or overflowing evidence fails open and stops model input. Actual notification-order handling remains subject to manual acceptance.

Initial cooperation covers ordinary relative mouse motion, clicks, bounded drags and wheel actions. Model key chords and Unicode text remain available; physical user keyboard/IME input passes through and stops model input. Independent or queued human keyboard/IME use is outside this initial acceptance scope. Explicit collaboration enable starts capability preparation; mouse isolation is not active merely because the request was accepted. Suppressed-input/raw-motion delivery must be observed with actual manual movement, and unsupported or uncertain routing must leave physical input available.

During a model gesture, the Windows system cursor follows the shared input stream. The white, dark-outlined pointer labelled `사용자` identifies the user's separate logical position; the colored `모델` pointer follows the active model path and returns to any separately requested next logical position afterward. The visibility owner below hides the system pointer only during proven cooperation with its replacement overlay present. Concurrent-click acceptance must check both the user's reported experience and the submitted logical coordinates; rendered model strokes alone do not establish that the user's click stayed independent. Motion survival watchdogs correlate physical motion in either notification order; a button or wheel event is not itself evidence of missing motion RAW packets.

The scheduler uses broker admission order for bounded operations from either participant, rather than a whole model task or individual low-level events. A click includes down/up; a drag keeps its down, path and up together; a shortcut includes modifier release. Separate cursor movement updates the participant's position without joining this execution queue or redirecting the other participant's active gesture. A user request arriving during a model drag waits for that drag, then runs before later model requests. Neither participant's normal requests cancel the other participant's pending work.

Queued input binds its intended target and position at submission rather than looking up the participant's latest cursor position at execution. Revalidation before delivery detects unavailable or materially changed targets and exposes a skipped/failed operation instead of blindly clicking changed screen content. The development implementation bounds the queue to 16 operations, human intent lifetime to five seconds and drags to two seconds with at most 128 path points. Each vertical wheel event is an operation. Collaboration rejects cross-request key-down/key-up holds and provides atomic `press` chords. These limits and live human gesture ordering require real acceptance. Long model tasks must not reserve input while reasoning, observing or waiting for another tool call. Explicit emergency stop and uncertain delivery still prevent automatic replay.

Window Use integration must preserve its app control or conversation desktop authority, target identity, observation and stop checks. Shared foreground input is an explicitly disclosed backend with corresponding authority, rather than an implicit fallback from failed window-directed input. Keyboard ownership is not made independent by separating mouse positions. Model failure must leave ordinary user input available; timeout and held-state cleanup need verification separately from normal completion.

## Cursor visual design

Status: `partial` — the native Windows x64 renderer implements the adopted [HTML/SVG design](../../work/EZ-01-window-use-multipointer-review/cursor-motion-preview.html). Frozen-source compilation, light/dark native frames, premultiplied-alpha upload and motion checks pass. A direct MCP Paint trial also confirms two model cursors' drag-dot/idle-arrow transitions and the user queue save badge with intended click placement. This acceptance is bounded to that local Windows trial; installed-host availability, broad input reliability and other desktop/DPI combinations remain separate. The model cursor uses the Fluent Cursor 16-derived 90%-width body with preserved circular corner radii and a white outline. Its selectable colors use the 72 registered defaults from Life-All-In-One; this does not read that app's live user overrides.

The user cursor remains white and sharp, preserving the approximate silhouette, direction and hotspot of the current Windows arrow. Its outline uses seven straight support edges with tangent rounded corners; the white interior follows an inset of the same structure. Raster edge fluctuations are not part of the design. The preview retains the local 32-pixel Windows reference and before/after overlays; exact pixel equality is not a design requirement. Native surface anchoring is tested at 96/144/192 DPI; mixed-monitor appearance, accessibility sizes and live user acceptance remain separate. Labels remain `사용자` and `모델`. A supported human intent admitted but not started in the actual FIFO queue adds a save icon without recoloring the pointer.

The ordinary-to-user transition combines a crossfade from the loaded Windows arrow with growth from a dot at the input origin, starting only after cooperation becomes ready. The model becomes active for a native actuation request, fades and shrinks in place into a dot during dragging, becomes 32% opaque while idle and shrinks/fades when explicitly removed. Teleportation moves the live logical cursor immediately, leaving only a soft stationary body at the previous location for 180ms. Each pointer has at most one remnant. Removed pointers retire for at most 220ms within a bounded list; stop/shutdown destroy all surfaces immediately. Mode disable restores the system cursor immediately while its outgoing label fades. Reduced Windows client-area animation disables growth, ghosts and retirement motion.

GDI+ paints cached premultiplied-alpha surfaces; opacity applies to the completed cursor rather than independently to overlapping fill/border/text. Per-monitor visual scaling does not change physical input coordinates or hotspots. Raw Input relocates the current user surface immediately; it does not interpolate position or repaint an animation for every raw packet. The existing safety timer advances visual tweens, and unchanged settled frames do not repaint. Rendering failure releases routing and leaves the system-pointer restoration owner active. Assets, attribution, renderer, motion state and native non-actuating checks are owned by `native/multi-pointer/cursor-*.hpp` and the `tool.multi-pointer.cursor-native` preservation check. No target DLL, new package or cursor-scheme replacement is introduced.

## System cursor visibility during cooperation

Status: `partial`; development source and Windows guard lifecycle checks are implemented. The user confirmed system-pointer hiding in a target-free probe, a Paint drag with product overlays temporarily suppressed, and the ready cooperative mode during idle movement. The user accepted the subsequent tracking improvement, with unchanged visibility producing no extra guard commands during the movement trial. These observations do not establish numerical display latency or general application compatibility. Successful visibility API acknowledgments alone do not establish rendered hiding. Earlier intermittent completion jumps remain a separate reliability concern. Installed availability remains unverified. Multiplex exploration is stopped; this change retains the Switched scheduler and its input boundaries.

Target behavior: while proven mouse cooperation is ready and its user overlay is visible, the system pointer remains hidden across both model gestures and idle periods. The existing user/model overlays remain visible. Missing replacement-overlay visibility stops routing and leaves the system pointer displayed. Capability preparation alone does not hide it. Mode disable, routing failure, stop and shutdown restore system-pointer visibility. Legacy operation without proven cooperation remains unchanged.

User-overlay placement is updated immediately after Raw Input processing rather than waiting only for the safety timer. The timer retains watchdog and idle-coordinate reconciliation responsibilities, updating the overlay before visibility work. A repeated visibility health check observes the existing acknowledgment and helper state without waiting for a new command. Only a visibility transition requires acknowledgment; this state does not prove what another application or compositor renders. Actual tracking latency and user-perceived improvement require separate real-use acceptance.

The broker still restores the latest user position after model/queued human input before releasing capture, but does not show the system pointer at that boundary. It drains a bounded batch and revalidates the restoration point without blocking visibility IPC after release. This ordering does not establish a global hardware-input completion barrier. Hiding is presentation only and does not repair or establish coordinate isolation. Mode-wide hiding and idle overlay tracking require their own real-use acceptance; earlier gesture-only hiding observations do not establish them.

Use the Windows Magnification cursor-visibility API without replacing cursor resources, changing a cursor scheme or injecting a target DLL. An independent helper of the same verified native executable owns the temporary visibility state, excludes competing cooperative cursor owners on the same desktop, and restores visibility when the broker exits or its heartbeat expires. Stop, routing failure and normal shutdown also request restoration. Hide/show failure must be observable rather than reported as successful visual suppression. This Windows x64 local-desktop behavior does not add other-platform support.

## Bounded active recovery

Status: development source implements bounded preparation recovery and stable operation outcomes. The Paint trial verified foreground reacquisition, exposed-caption fallback and duplicate-operation suppression across observations. Forced live budget exhaustion remains unverified.

Foreground changes and covering windows are recoverable conditions for shared foreground input. They must not, on their own, pause the whole task. Read-only observation continues without taking the foreground when the backend can capture the bound target. Before the next model input, the coordinator observes the current target, reacquires its permitted foreground surface, obtains a fresh observation and revalidates the intended action. Model-owned input must never be delivered through a foreign covering window.

The initial recovery budget is at most three recovery rounds and five seconds of active recovery per intended operation, whichever is exhausted first. Each round performs fresh identity/authority/stop checks, inspects foreground and hit state, attempts an appropriate permitted activation or restoration, and verifies the actual result. Waiting for another participant's already admitted gesture does not count as active recovery and must not cause that gesture to be interrupted. A recovery round runs only in the model's input turn; further rounds preserve the same operation identity and counters and must not jump ahead of already waiting user operations. Progress requires verified readiness for the next intended input, not a successful API return or a transient foreground sample. Reissuing a request or repeating a capture does not reset an exhausted budget.

Use supported activation and, where separately permitted, exact-target restoration. An exposed exact-target caption click is an existing fallback; completely covered targets can still be attempted through supported activation APIs. The coordinator cannot close or move an unrelated covering window, manipulate shell shortcuts, or change foreground-lock/security settings merely to recover. OS refusal is a recoverable attempt failure rather than evidence that the target is impossible to control. Recovery cannot bypass user stop, revoked authority, process/target replacement or unresolved synthetic-held cleanup.

Recovery retries window preparation, not uncertain application mutations. An operation proven not to have delivered application input can proceed once readiness and its current intent are verified. If a drag, shortcut or text operation was partly delivered or its result is unknown, release tracked model-held state and observe the application before planning the next operation; do not replay the original mutation or continue an old coordinate path blindly. Restored foreground does not establish unchanged focus, layout or control meaning. On budget exhaustion, stop the affected model operation, release its held state, leave ordinary user input available and report attempted recovery, last observed blocker and partial effect. Subsequent resumption requires new information or an explicit retry, with the earlier failure retained.

## Optional Window Use integration

Status: development source and scoped host/staging checks are implemented. Full product packaging and installed availability remain separate acceptance steps.

Windows runtime staging accepts an optional multi-pointer directory with its own native manifest and source identity. The enclosing Window Use manifest binds both the native runtime and the `multi-pointer-mcp.cjs` / `window-switched-input.cjs` host modules. Host construction verifies these declarations before loading the adapter, and construction performs no input. Other platform packages do not activate this Windows backend.

General conversations invoke `switched_input` for an explicit `windowId`; missing control permission is requested automatically by the host. Consent names shared foreground input, possible target activation, cooperative mouse preparation and the physical-keyboard limitation. App control authority pins the exact process lifetime and executable; individual calls still bind the selected root and a fresh image observation. Conversation-only desktop authority may cover individual input under the same Security App exclusions. Whole-screen `desktop_input` separately requires that desktop authority and revalidates its live hit target for each operation. Dedicated selected-window conversations retain their existing tool ceiling. The master switch, app policy, occupancy, user stop and trusted active-turn context remain mandatory. Numbered-stage or global all-app settings cannot manufacture these permissions; the [Window Use permissions](window-use.md#permissions) own admission and revocation.

The Switched backend virtualizes logical pointer positions over shared foreground input. It does not resume the retained process-hook `virtualInput` prototype, grant independent background input, or use that prototype's consent as shared-input authority. Failure in either backend cannot silently switch to another delivery path.

`switched_input` accepts strict atomic operations and explicit collaboration enable/disable. Coordinates are physical screen pixels inside the bound main client. The adapter supplies its private model pointer ID and creates a one-root native allowlist; callers cannot pass an executable, PID or arbitrary native method. The first pointer operation supplies an explicit point; observation or capability preparation does not invent a point, activate a window or click. Input results retain native operation/recovery/capability details and remain application-effect unverified until a new observation.

Stop, selection replacement, grant changes and disposal retire the native session. The adapter waits for verified successful process termination before removing its exact temporary allowlist and session directory. Unknown or failed termination retains the session, blocks replacement and reports the cleanup failure. Native failure or unknown termination propagates to the standalone MCP exit status rather than being hidden by a successful parent exit.

## Ownership and preservation

The native broker owns target validation, shared-input arbitration, held state and overlays. The stdio MCP owns bounded protocol/schema validation, verified runtime launch, request identity and failure/EOF propagation. The native checker owns immutable source preparation, compilation and runtime integrity. Maintained source and mandatory checks are connected through `tool.multi-pointer`; task-specific analysis and real-app evidence remain in the [work record](../../work/EZ-01-window-use-multipointer-review/01-plan.md).
