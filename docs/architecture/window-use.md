## Linux selected-window backend

Status: `partial` — Source implementation and isolated Linux GTK-window verification are recorded in [Linux operations](../ops/linux.md). The Windows acceptance statements elsewhere in this document retain their own scope; integrated-host readiness does not establish control of arbitrary user windows.

Linux Xorg uses `native/window-control/src/linux_backend.py` through the verified runtime selected by `scripts/window-control-runtime.cjs`. The runtime requires Python, Gtk 3/Atspi 2, Pillow and X11/XComposite libraries. Capture reads the selected window's XComposite pixmap rather than the foreground desktop. AT-SPI supplies inspection and supported value, invoke, toggle, selection, expand/collapse and scrollbar actions. Supported patterns are determined from the actual element; missing patterns return an explicit unsupported result.

The host retains selected-target identity, app approval, conversation authority, occupancy, cancellation and uncertain-result rules. Key delivery is restricted to the selected window's already-focused exact element. Return uses AT-SPI activation; other named keys use window-message delivery and can be ignored by the application, so delivery alone is not effect confirmation. The backend does not substitute global input, clipboard access or foreground activation. Wayland and whole-desktop Computer Use are excluded. Linux uses a GTK stop control, with `hotkeyRegistered: false`; the Windows stop shortcut and corner-glow behavior are not Linux guarantees. See [platform visualization](window-use-visualization.md#플랫폼-범위).

## Product requirements

Status: `partial` — the settings and managed authority paths are implemented; child-session admission and installed acceptance remain pending.

Window Use is the single product name for window observation, isolated app execution, selected-window control in the user's session and whole-desktop control. Settings, approval cards, notifications, panels and model guidance use that name. The existing Computer Use/Sky runtime remains the internal desktop backend for stage 4; its implementation and verified limits are owned by [the desktop backend](computer-use.md). The four-stage policy is implemented in source. Isolated execution has a pinned native helper and host adapter; its live environment admission remains unverified.

| Stage | Scope | Authority |
| --- | --- | --- |
| 1 — Observation | Discover and select an exact window; read status, capture and accessibility state | Master and stage 1 enabled; all windows observable without per-app or per-window consent |
| 2 — Current-window control | Control the exact selected window in the user's Windows session | Master and stage 2 enabled; individual or all-app approval plus authority for the task's stage and execution context |
| 3 — Isolated execution | Launch and control an approved app in a same-user Windows child session with independent input | Master and stage 3 enabled; individual or all-app approval plus authority for the task's stage and execution context |
| 4 — Whole-desktop control | Use the desktop backend across the user's current desktop | Master and stage 4 enabled; individual or all-app approval plus authority for the task's desktop scope |

Observation must not raise a window, change focus, restore a minimized window, resize it, launch an app, deliver input or write the clipboard. An occluded capture returns the target's own content. Selection identifies an observation target and does not approve mutations. Capturing the whole desktop is not stage-1 window observation. Native permission, target identity, protected-capture, freshness and request-authentication checks remain mandatory at every stage.

Stage 3 separates physical input from the parent's session. Stage 2 can conflict with the user's interaction and must state that impact when authority is requested; UI Automation can activate the app or its dialogs. Stage 4 denotes desktop scope rather than unrestricted authority over files, credentials or account settings. Unsupported operations remain unsupported at a higher stage until an appropriate backend and scope are available.

General mouse and keyboard isolation is the stage-3 priority. Its selected architecture is a same-user Windows child session that reuses existing installed apps and the user's stored profile. Admission on each environment still requires actual connection, rendering, input and data verification; selecting this architecture does not establish Home support. Limited window-message adapters and a separate desktop within the parent's session do not fulfill this stage's general input requirement. Input must remain inside the isolated context, and app approval still constrains which app can receive it. Control of another app or the isolated desktop requires the corresponding authority. An independent input mechanism does not establish capture, application rendering, GPU, shortcut or concurrent-data compatibility.

Ordinary conversations retain their coding tools. Existing dedicated selectedWindow conversations retain their immutable native tool ceiling; stage elevation cannot relax that ceiling. A new unified conversation must establish its managed tool surface at creation and enforce stages at execution. Browser tasks prefer the existing Chrome control route and its own authorization rules; child-session browser profiles and cookie extraction are outside this design. Failure of Chrome control does not grant native window or desktop input authority.

Task macros support both immediate execution of a supplied definition and saving a definition for reuse. The host implementation supports both paths; real-window acceptance remains pending.

Window Use must reduce model context and time to a verified result compared with equivalent supported operations in the existing control paths. Observation size, provider work, model round trips and session startup are separate costs. Performance gains must preserve target validation, authorization, cancellation, outcome checks and existing functionality. New capabilities without a successful baseline require functional acceptance, not a speed comparison against an earlier failure. Measurement scenarios and candidate thresholds belong in the implementation plan.

## Stage authority and recovery

Status: `partial` — source host and pinned-transport tests cover stage grants, cancellation and revocation; installed-host and real desktop behavior remain separate.

Settings schema 2 stores a master switch and four independent stage switches. New defaults enable observation, current-window control and the existing desktop scope; the new isolated scope starts disabled. Migration preserves the prior master, all-app grant and desktop switch. Disabling the master preserves individual stage choices. Settings changes invalidate task grants and queued input without reenabling a stopped task.

App approval and task-stage authority are separate. Individual app grants and the all-app setting apply to stages 2–4. The all-app setting skips app consent; it does not grant a higher stage, select a window, clear a user stop or alter native permissions. Existing accepted authority is reused within its scope. When a task needs additional authority, the request identifies the required stage, app/window, execution location, reason and effect on the user's work. The model requests elevation and cannot approve it.

### Upfront task permission preparation

Status: `partial` — implemented in source and verified through protocol tests, the pinned React approval components, and Windows x64 isolated-package acceptance in `u19c` (`2026.0.10`). The external installation's files and runtime binding were verified. Human approval and notification sound in the reopened external profile remain separate live checks. Evidence and limitations are tracked in [the active work plan](../../work/CF-01-window-use-admin-setup/01-plan.md).

`prepare_permissions` lets a model request a task's required stage and up to eight known apps at the beginning of work. Apps are fresh opaque candidates from `list_windows`, revalidated before approval; arbitrary executable paths, stale candidates and unknown or other-task occupancy are rejected. Stage 2 still requires the exact selected window. Preparation performs no child-session creation, app launch, UAC setup or input. A prepared stage-3 grant is activated through the ordinary `request_stage` admission path before app launch, retaining child ownership and compatibility gates.

The user reviews the stage and missing app cards inside Azrael at the start, with independent acceptance/refusal for each app. Existing grants skip redundant cards. A refused app remains unauthorized; cancellation or expiry stops further prompts. Preparation does not create wildcard or persistent app grants automatically. A new app, execution context, revoked permission or expanded scope requires its own authorization. Accepted stage-4 authority remains tied to its active turn. Preparation never substitutes for action-time confirmation or Windows UAC.

Stages are not a compulsory sequence. Prefer isolated execution when a new app instance can perform the task. Current unsaved UI state can require stage 2 directly from observation; a task requiring the desktop can request stage 4 directly. Changing from child to parent execution binds a new target and discards observations from the old execution context. An unavailable child session never silently falls back to parent input.

One Window Use enable setting gates every managed observation and control path. Disabling or revoking authority rejects subsequent steps, invalidates outstanding requests and prevents late replies from restoring authority across hosts. Existing app grants are preserved through settings conversion without treating discovery, observation or an ambiguous app name as consent. Existing disabled scopes must not be enabled implicitly during conversion.

Each stage also has an independent enable setting. Disabling stage N disables admission to that stage, without automatically disabling lower or higher stages. Stage 1 gates standalone observation; an independently authorized stage 2, 3 or 4 may still perform the target observations required to execute and verify its own task. Those observations inherit that control context and cannot expose unrelated windows through the disabled observation stage. The master switch overrides every stage. A disabled stage cannot be entered through an all-app grant, a macro, a backend-specific tool or an elevation request.

Stage 1 defaults to enabled in a new configuration. While the master and stage 1 are enabled, every window is observable without per-app or per-window consent. There is no separate all-window observation toggle or observation-grant store. The user disables stage 1 to disable standalone observation. This observation scope does not enable all-app control in stages 2–4; native permissions, protected content, exact target identity and freshness checks still apply.

Disabling an active stage stops further input and invalidates in-flight requests and references for that stage. Outstanding approvals cannot re-enable it. Stop model execution without force-closing user apps or discarding unsaved data; teardown remains bound to owned sessions and processes. Re-enabling a stage does not replay input or automatically resume a cancelled task. Capability responses and UI distinguish a disabled stage from a backend that is unavailable on the current platform. Settings retain each stage's value while the master is off, and migration preserves existing disabled scopes. Persist authority by capability and execution context, with a schema version; renumbering stages must not reinterpret a current-window grant as an isolated-execution grant or vice versa.

Recoverable observation failures retain the target and require a fresh observation. Temporary user interaction can pause further input for state revalidation; an explicit user stop remains terminal until user resume. Ordinary Escape must not become an accidental stop merely because the app activated. A dedicated stop control and Ctrl+Alt+Shift+F12 provide explicit interruption on Windows when the exact target is foreground; shortcut conflicts report the Azrael stop path. Bare Escape is left to the application. Unknown mutation outcomes never authorize automatic replay or elevation. Already-delivered actions can still complete.

## Efficient observation and retrieval

Status: `target` — summary, find, read and changes are the selected structured-observation design. Implementation and performance acceptance remain pending; numerical budgets are reviewed in the work plan. Existing capture and inspect behavior retains its current acceptance scope.

Observation has separate image and structured-data paths. Image capture defaults to a fresh target image without accessibility-tree enumeration. Structured observation defaults to a bounded summary; it does not return the full raw tree or complete document values. Either path carries its execution context, live target identity, observation identity and explicit coverage. An image observation without element references cannot authorize a semantic element action; an element query does not establish a captured frame for coordinate input.

Extend `inspect` with summary, find, read and changes operations. Find accepts a bounded search for control name, AutomationId, control type, supported operation and state, optionally scoped to a previously observed container or client-area region. Read returns selected properties, children or a bounded text range for an exact observed element. Changes returns bounded differences from a named compatible observation, including removals; it requests a fresh summary if the base has expired. Names, values and document text are separate requested fields. A default result contains short names, role, necessary state and opaque IDs; long values, help text, coordinates and supported patterns are obtained when required.

Query execution belongs in the native/provider boundary. Reuse UI Automation conditions and cache requests for supported exact predicates and property batching; use bounded traversal for predicates or providers that require it. Avoid unbounded provider allocations or a whole-tree walk followed only by output filtering. Provider calls run under worker deadlines with cancellation and bounded retained references. UIA caching reduces cross-process property requests; it is not proof that an observation remains fresh. The platform mechanism is described in Microsoft's [UIA caching guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-cachingforclients).

Each result reports returned coverage and any output, scan or time limit independently. A partial search cannot establish absence, a total match count or a selector's uniqueness. Finding a second match can establish ambiguity without collecting all matches. A macro requiring a unique selector stops if that selector's search scope is incomplete. Exact-element actions retain identity and purpose checks and do not infer an intended target from the first ranked result. Virtualized or offscreen content unavailable to read-only observation remains unavailable; realizing it through scroll or other UI mutation needs the appropriate stage.

Pagination cursors are opaque and bind the observation, query, target, execution context and authority generation. Paginating a bounded retained result is distinct from continuing a live provider scan. A resumed scan over changed UI creates a new observation or reports expiry; it does not concatenate unrelated states. Text ranges identify the text revision and indicate omitted content. Password fields remain redacted and do not become searchable secret values. Application text is untrusted content, separated from host-generated capability guidance.

Retained results and change tracking are bounded by target and execution context. Session changes, target replacement, grant revocation, cancellation and actions invalidate dependent references. Events can invalidate caches and support condition waits, but event absence does not prove unchanged UI. Every mutation revalidates live authority and target identity. Frame reuse or compression never labels an old screenshot as a fresh capture; unavailable or unchanged frames retain truthful freshness metadata.

The public `inspect` tool accepts `summary`, `find`, `read` and `changes`. Native `task` inspection remains private to existing host macros. The initial limits are 20 returned elements, at most 100, a 6 KiB default/24 KiB maximum response budget and 4096-character text ranges. Provider work is bounded by scan count, depth and deadline. Results expose `retrieval.coverage`, omission reasons and budgets; a deadline-limited query cannot prove absence or uniqueness. A changed or incompatible baseline falls back to a small summary with a reason. Images carry no semantic element references. Current retrieval uses fresh bounded queries rather than public pagination cursors.

## Isolated execution and stored data

Status: `target`.

A child session runs another app instance under the parent's Windows user account. It separates UI, focus and process memory; it does not create a new anonymous user, copy the current window or sandbox the account's stored data. Saved documents, profile folders and user settings can be shared by both sessions. Changes to shared files/settings can affect the parent's apps. Stored application authentication may be reusable, but each app must verify that behavior; unsaved edits, undo history and the live parent's window state are not transferred. This follows the [Windows profile model](https://learn.microsoft.com/en-us/windows/win32/shell/about-user-profiles) and the same-account behavior described by [LibreAutomate's child-session implementation](https://libreautomate.com/editor/PiP%20session.html).

Apps can reject concurrent instances or lock files/profiles. A conflict must be reported before continuing; the system does not close the user's apps, bypass locks, copy credentials or create a different app profile automatically. Browser work uses the existing Chrome route. General saved-data access, actual app login behavior and application-specific concurrency are separate verification targets.

The installed RDP ActiveX client exposes Microsoft's `IMsRdpInputSink` and `IMsRdpClientNonScriptable` interfaces on the tested Windows host. They are candidates for sending mouse and keyboard input through an isolated RDP connection. Interface availability does not establish a connected child session, actual input delivery, capture or general app compatibility; those remain admission gates. See [RDP input sink](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpinputsink) and [scan-code key delivery](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpclientnonscriptable-sendkeys).

A Windows VM has a separate operating system, installed apps and user profile. The host's app installation, login and saved profile are not automatically present in it. It remains an alternative requiring a new data decision rather than the current profile-reuse route. File sharing, app setup and authentication require an explicit data contract before using that backend for user work. Virtual keyboard and mouse devices can receive host-issued commands without delivering input into the user's Windows session; host hypervisor availability alone does not establish a usable Windows guest. See [QEMU input and display](https://www.qemu.org/docs/master/system/qemu-manpage.html#display-options) and [QMP input events](https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html#input-send-event).

A diskless QEMU guest on the tested Windows Home host consumed keyboard characters, a modifier shortcut and mouse movement/button packets through virtual devices with WHPX acceleration. Its owned process exited after graceful shutdown. This verifies the device transport in that disposable guest, not a Windows guest, Windows applications, existing data access, GPU rendering or concurrent physical-user acceptance. The VM remains a stage-3 candidate pending those gates.

The host owns the child-session connection, scoped app launch and authenticated helper transport. Capture and input execute inside that session, not through parent-session input directed at a remote-view window. Target identity includes the execution session and live window/process identity. Remote viewing can offer explicit user-control/model-control ownership; simultaneous input owners are excluded. Disconnects, hidden/minimized viewing, rendering availability, clipboard redirection and shortcut routing require independent verification.

Home support is unresolved across environments. On the tested Windows 11 Home 10.0.26200 x64 local host, administrator feature enablement, state readback and restoration succeeded. With explicit desktop dimensions, CredSSP enabled and clipboard redirection disabled, both elevated and standard-user child-session clients reached `OnConnecting` but disconnected with reason 516 before login; no child session was created. Windows logged TerminalServices-LocalSessionManager event 17 with `0x80070005` during feature enablement. These observations establish that this host's current configuration cannot execute stage 3 through the tested native path. They do not isolate the failure to edition, policy or service configuration, and app execution, capture, input isolation and saved-data access remain untested. Remote-access policies, firewall rules and credential-delegation settings were not changed.

Power Automate and LibreAutomate exclude Home from their supported PiP configurations, which does not establish that every direct Windows implementation is impossible. Native feature enablement, connection, child-process execution, capture, input isolation and data behavior determine the accepted environment. Availability through the child-session backend requires those capabilities; a successful enablement API alone does not make it available. Until the gates pass, the UI reports the observed prerequisite or failure and keeps observation available; the user can explicitly authorize a different stage. Pro/Enterprise remain verification candidates rather than accepted Azrael environments. The investigation, experiment evidence and implementation sequence are in the [implementation plan](<G:/내 드라이브/ObsidianVault/PARA/30 Project/pi-harness/Tasks/Task2/DU-01-window-use-stages/01-plan.md>).

## Isolated-execution lifecycle and cleanup

Manual recovery (`target`, Windows local child sessions) is an explicit one-shot operation for an existing same-user child after host ownership is lost. `scripts/request-window-child-recovery.ps1` queues a private request under the selected Azrael state root, bound to SID, profile, parent/child session and a ten-minute expiry. Only an authorized stage-3 activation consumes it; observation does not reconnect, and no ticket retains the ordinary rejection of an unowned child. Consumption does not grant stage or app authority. An ordinary pinned host requests UAC for a bounded recovery broker, which validates the exact existing child and rejects active matching helpers before running a triggerless, temporary Task Scheduler task in that session with an interactive, non-elevated user token. The exact task registration is removed after launch, with unconfirmed cleanup reported as failure. The worker must pass the existing nonce/pipe-peer, process lifetime, executable hash, SID/profile/session and platform admission checks. Recovery does not call the child-creating viewer connection API or log off the recovered session. Cancellation, authority revocation, stale identity or uncertain input cannot trigger an automatic retry or replay. Missing proof prevents control. General automatic reconnect and recovery of arbitrary foreign sessions remain outside this path. The feature inventory's `ui.window-control` owns the request, manager and native checks; installed/live acceptance is recorded in the current work plan.

Direct installed-app launch (`target`, Windows local MSIX full-trust applications) lets `launch_isolated` accept an exact registered `packageName` and optional manifest `applicationId` instead of an observed parent `targetId`. The two identities are mutually exclusive. A bounded read-only current-user registration query resolves a single full-trust executable within its registered package directory and rejects ambiguous registrations, link redirection, path traversal, arbitrary paths, arguments and URI activation. The existing Azrael app consent binds the resolved executable; registration is checked again after consent, the file is hashed, and the existing ordinary child worker verifies that hash and the launched session. No parent app window is created or controlled. This route does not grant stage authority or change cancellation, app revocation, child target and fresh-observation checks. Registry lookup success does not establish package activation, rendering or input compatibility; those require live acceptance. Unpackaged app discovery and non-full-trust activation remain outside this route. The existing observed-window route remains available.

## Task macros

Status: `partial` — Host implementation and native compilation are verified; real-window acceptance is pending.

A task macro is a bounded sequence of structured operations within one selected target. It complements the existing size macros. Initial operations can reuse UI Automation Invoke, Value, Toggle, Selection, ExpandCollapse and Scroll, with explicit conditions for waiting and checking results. A typical sequence sets a search field, invokes its search button, waits for results and returns a screenshot.

The executor resolves each element again inside the selected window before acting. A macro stores semantic selectors and required patterns rather than observation-specific element IDs or screen coordinates. A selector must resolve uniquely; missing or ambiguous matches return an error. The native inspector exposes names, control types, patterns, AutomationId and parent relationships for reusable selectors; provider-specific availability still requires acceptance.

Large accessibility trees return a bounded breadth-first snapshot with `elementsTruncated: true` instead of failing the target capture. The same field is false for complete observations. Element, depth and pending traversal limits remain enforced, and only returned elements retain action references. An incomplete snapshot cannot establish selector uniqueness or absence, so macro inspection stops before evaluating conditions or issuing a mutation. A direct action can use a verified exact reference from the current partial observation.

A selector combines exact AutomationId or accessible name, control type and an optional ancestor scope. Runtime IDs identify live elements during a run and must not be treated as reusable IDs. Conditions require explicitly readable properties: presence, enabled state, non-sensitive value, selection, toggle and expansion state where the provider exposes them. Missing property support is distinct from a condition evaluating false. An off-screen accessibility flag alone must not exclude a control in an occluded window. Password values remain excluded from inspection and persisted inputs.

Each step checks target identity, authorization and cancellation, observes fresh relevant state, performs one operation and evaluates its postcondition. Waits have deadlines. A failed or uncertain mutation stops the sequence and reports completed steps, the failing step and available final state. The executor must not replay an uncertain mutation automatically. Already-delivered actions cannot be promised to roll back; interruption prevents subsequent steps.

Execution through one tool call avoids a model round trip per mechanical step. Read-only condition polls should use accessibility state without generating and transmitting a PNG each time. Images are returned when needed for a decision, at completion or failure. Internal observations and target checks remain necessary. Reusing a capture session is a possible optimization after measurement; performance is not established by this design.

The execution tool is `run_task_macro`, accepting the selected `targetId`, a supplied definition or saved definition ID, and execution parameters. It returns a run ID, overall state, per-step outcomes and final observation when available. `save_task_macro` and `list_task_macros` manage reusable definitions. `run_size_macro` retains its separate meaning. An example task has these steps:

| Step | Operation | Result condition |
| --- | --- | --- |
| 1 | Set the uniquely matched search field to the supplied query | Field value equals the query |
| 2 | Invoke the search button | Invocation delivered; completion is checked in the next step |
| 3 | Wait for the results element | Element exists and is ready before its deadline |
| 4 | Capture the selected window | A fresh target frame is returned |

The host owns bounded orchestration and per-step authorization; the native worker owns exact-window element resolution, property reads and supported operations. `inspect` provides accessibility state without PNG capture. The backend timeout disposes its owned helper; a macro must surface an uncertain action result and cannot interpret timeout as proof that the app did nothing. A stopped run must cease condition polling and skip subsequent steps even while an already-issued provider call is settling. A definition contains at most 32 steps, runs for at most 20 seconds and waits at most 10 seconds per condition, within the existing 30-second transport deadline. Longer tasks split at verified checkpoints.

Parameters supply strings at execution time. A definition contains `schema: 1`, parameter names and structured steps; saved definitions also require a stable `id` and `name`. Selectors and operations carry no live window authority or old element handles. Sensitive text belongs in runtime parameters instead of persisted definitions.
