## Native instruction state and prompt projection

Status: `partial` — The selected engine implements typed instruction-state projection and dynamic Apps, Environments and Plugins guidance. Existing source tests are evidence for their declared fixtures; this documentation audit does not execute Rust tests or establish package, installed or live-provider acceptance.

The engine projects a prompt copy before discarding typed provenance or estimating prompt tokens. Only explicitly replaceable instruction kinds with their expected producer role and complete provenance can replace earlier state. Removal notices use the same kind and withdraw that producer's previous contribution. Ordinary additive instructions, malformed or untyped content, wrong-role content, user messages and stored conversation history keep their existing meaning. Prompt projection does not delete recorded history.

Apps, Environments and Plugins producers refresh their guidance when availability changes and emit explicit disabled/withdrawn state so previously enabled guidance cannot remain active merely because it is in history. A complete host skill catalog replaces an earlier catalog; environment deltas retain their additive meaning. Selected skill bodies reuse the last identical body for a normalized path, while changed bodies or an intervening replacement require the current contribution.

Target extension refresh behavior: the step lifecycle observes authentication changes during an active turn and refreshes cloud plugin and skill catalogs before projecting the next step. Refresh attempts and retry state are scoped to the current authentication and resource; failures use a bounded 30–300 second cooldown, and success or a changed authentication scope resets it. Stale in-flight results cannot replace a newer scope's catalog. Local skills, tool eligibility, contributor order and typed instruction replacement retain their existing contracts. The current source adaptation and native acceptance are recorded in the [selected update work](../../../../work/DO-01-codex-version-comparison/02-plan.md).

Producer-typed `model_switch.instructions` also keeps only its latest contribution in a prompt copy. Identical rendered behavior across model selections does not produce another switch-instruction body; actual behavior changes still refresh. The [profile persistence contract](../model-harness-profiles/README.md#persistence-replay-and-future-extension) owns the comparison snapshot and legacy reconstruction boundary.

Custom API prompt copies additionally filter known desktop-control skill entries and selected bodies using typed skill fragments, without removing similarly worded untyped history or unrelated skills. Their catalog, deferred-tool search and token-estimation boundaries are owned by [API request context projection](../custom-api-models/README.md#요청-컨텍스트-투영). This request-time projection is distinct from installing instruction files: file distribution and captured thread instructions retain the lifecycle below.

The engine owners are `codex-rs/core/src/context/instruction_state_projection.rs`, `core/src/world_state/{apps,environments,plugins}_instructions.rs` and `ext/skills/src/{world_state_catalogs,host_prompt}.rs`, relative to the selected engine source. These native contracts are outside the registered `ui.instruction-settings` check's settings-surface scope and require separate preservation review.

Provider/model behavior templates and runtime/tool guidance are composed through [model harness profiles](../model-harness-profiles/README.md). User templates replace the behavior layer; sandboxing, approvals, declared-tool eligibility and user/project provenance stay with the native runtime. Maintained profile prompts have identical embedded copies alongside the common agent behavior.

## Work intent, entry and feature preservation

Status: `partial` — maintained instructions and active skill files define this policy; model behavior in real use remains a separate acceptance condition.

Common behavior applies relevant skills using reasonable judgment. If a named skill's file is missing, it searches other locations; if the skill is still unavailable, it briefly explains the issue and continues with the best fallback. It does not prescribe avoiding skill rereads. Conditional skill catalog instructions retain their separate model-controlled delivery and require review alongside common behavior.

Common work-entry guidance identifies the conversational goal, requested deliverable, allowed actions, settled decisions and open questions before choosing a skill. Follow-ups retain this context: a design-stage request to refine an idea refines the design, while an authorized implementation-stage refinement stays within that implementation. Mentioning a skill or a needed change does not grant execution authority. Clarification is needed only for unresolved interpretations that change scope or authority; settled permissions persist across turns. Common behavior carries existing authorization forward and confines changes to the approved plan; changes beyond its scope require additional authorization before execution and reporting afterward. Routine implementation choices within the authorized scope use context and judgment; discretionary choices absent from the plan are explained in both commentary and final responses. Confirmation requests explain their reason and governing instructions or circumstances. An automatic approval review rejection that prevents completion is explained with the rejected action and stated reason in both channels. Feature `engine.model-harness-profiles` connects these maintained and embedded behavior sources to the existing source guidance check in the [feature inventory](../../../../scripts/azrael-feature-contracts.json).

Common communication behavior asks for a thoughtful, candid collaborator, with the main point first in clear, concise, connected prose and active, direct statements. It reduces unnecessary introductions, conclusions and repeated work descriptions. Important commands explain their purpose and impact; tool calls or code comments do not replace progress reports. Requested work receives necessary action and follow-up; approach questions receive an answer first. Technical accuracy and truthfulness take priority over affirming user beliefs, and uncertain claims are investigated. Progress includes relevant assumptions, findings, decisions and direction changes. Change reports explain what changed, why, verification and material limitations once, without duplicating this rule in the testing paragraph. Existing alternative profiles and custom behavior replacement retain their separate contract.

For source code and project file searches, common behavior prefers `rg` or `rg --files` and permits another tool better suited to the search target or execution environment. Multiline PR descriptions, issue bodies and comments prefer structured tool arguments; `gh` accepts body files or standard input, preserving actual newlines and intentional literal escapes. Product screen copy fits the product's functions and user actions. Design direction and quality requirements guide construction; their wording appears on screen only when the user designates it as display text. Common behavior routes tests, verification, task-level commits, cleanup, build inputs and platform matters to applicable project instructions and skills. Newly written task-specific tests are disposable by default after necessary verification, re-verification and result review; retention requires an explanation and summary. Meta tests that check test presence, count, wording or structure without verifying product behavior or a required contract are prohibited. Detailed logs belong to task-owned artifacts. These model instructions do not replace native lifecycle protection or prove conversational compliance.

Entry uses `design-collaboration` when linked user choices require iterative discussion, or `development-workflow` when investigation can gather the approach and questions into one plan. Technical size alone does not determine the route. Discussion and planning share one work record containing understanding, requirements, design differences, recommendations, decisions and verification; no prerequisite understanding document is required. Small tasks use short plans without unnecessary approval waits. Questions remain in the document and are surfaced by a conversational link and key decision. `design-documentation` maintains enduring agreed design in its existing owner, and `implementation` executes the resulting plan within existing authority. Specialized skills and route changes cannot expand that authority or restart settled approval.

Both routes compare agreed architecture with code, tests and observed behavior to preserve features, constraints and permissions. Draft proposals and missing documentation do not authorize removing an existing feature. Unapproved architecture deviations, deletion, hiding or disabling of features, and weakened verification to evade an error receive review before affected implementation. New execution findings return only the changed decision to the same record while independent authorized work continues. A fix is checked both for resolving the failure and for preserving existing behavior; architecture is updated for agreed changes, not rewritten to justify a reduction after the fact.

Policy acceptance distinguishes file/format checks from conversational behavior: design-stage change mentions and refinements stay in design, explicit execution requests change only the authorized scope, linked planning decisions reuse the same record, and error-driven feature reductions trigger review. Intent interpretation, selected skills and performed actions must all agree in real-use tests before claiming behavioral acceptance.

## Sources and releases

The Azrael repository owns the complete instruction library in `instructions/`, including agent roles, skill reference material and scripts, project playbooks, examples and documentation. Its `azrael-environment.json` declares independent semantic version `instructionVersion`, schema version 1, minimum compatible Azrael version and installable components. Source files retain their upstream provenance; Azrael-owned code and instructions use MIT, while imported engine and dependency notices retain their original conditions.

The skill components are `development-workflow`, `design-collaboration`, `design-documentation`, `implementation` and `project-bootstrap`, all selected by default with their support resources. Their source-relative paths, original and copied hashes and distribution adaptations are recorded in `SKILLS-SOURCE.json`; `SOURCE.json` retains the historical library import. Common execution guidance belongs to `implementation`. The optional workspace playbook component applies app logging guidance, while project-specific Work guidance remains under its existing owner.

Root scheduling guidance is an engine-owned developer instruction with the [root coordination contract](../agent-coordination/README.md). It applies across Azrael projects independently of instruction-library installation and configured role text, without enabling delegation or expanding authority. Shared worker rules and project-specific constraints remain in their existing owners. Removing legacy AGENTS coordination text from an active installation requires confirming that its installed engine supplies the replacement guidance.

An instruction release uses tag `instructions-vX.Y.Z` and three assets: `azrael-instructions-X.Y.Z.zip`, `azrael-instructions-X.Y.Z-manifest.json` and `azrael-instructions-X.Y.Z-documents.json`. The external manifest identifies the repository, source commit and source content digest, archive and document asset sizes/hashes, every archive file's relative path/size/hash, and component definitions. The document asset maps listed text-document paths to their content for browsing before downloading the complete package. The archive contains the entire instruction source tree; selecting components affects application, not download completeness.

Source release integration checks prepare a clean copy of the current public instruction inputs through the existing release builder. Version, app compatibility and component mappings come from maintained metadata; tests do not require a fixed historical release. Synthetic semantic-version fixtures remain for version selection, pinning, rollback and validation failures. Host adapter checks retain isolated native configuration validation and do not establish installed or public-release acceptance.

Components have unique `id`, `title`, `kind`, `default`, `scope` (`home` or `workspace`) and `files` with `source` and `target`. Home targets are confined to `AGENTS.md`, named `agents/*.toml`, named `skills/` directories and the separately merged agent configuration. Workspace playbooks target `docs/playbooks/`. A configuration component reads `config.example.toml` and merges only the declared agent configuration keys into the existing `[agents]` table; credentials, root model, sandbox and unrelated settings stay under their existing owners. Preview and planning expose differences and unmanaged or locally edited target conflicts before application.

## Canonical sources and personal versions

Status: `partial`. Source implementation provides explicit project/release selection, personal derivatives and reviewed linked-installation migration. Existing installations are not migrated automatically; installed-host acceptance remains separate. Preservation feature: `ui.instruction-settings`.

On computers developing Azrael and its maintained instructions, the Azrael project's `instructions/` tree is the authoritative authoring source for that instruction set. On recipient computers, the selected GitHub source is authoritative for the distributed documents. Local downloaded caches and installed files are derived copies. Personal Obsidian Vault paths and Vault-backed directory links are not required authoring, acquisition or runtime dependencies of this system.

Users can browse documents, copy them for personal work, install selected content, and publish their own versions. A personal working copy does not change the upstream source merely by being edited or installed. Developer project changes, personal working copies, verified downloads and installation destinations retain their distinct ownership. Saving, installation and publication remain separate actions under the existing review and recovery contracts.

Recipient acquisition defaults to a verified compatible stable GitHub release. The selected repository, release version and content digest identify the acquired snapshot; a moving branch head does not silently replace that snapshot or an installed version. Upstream changes to a personal derivative are shown for comparison and require explicit application rather than overwriting local edits.

The official browsing/acquisition source and the personal publication destination are selected independently. Users can retain access to official releases while publishing a personal version to another repository on which they have write capability. Source and destination identity include the repository, account context and visibility; sharing class alone does not identify a connection. Existing visibility separation and publication-content exclusions remain enforced for each selected destination.

Creating a personal derivative assigns a new stable resource ID and retains the upstream source, resource ID, version and content digest as provenance. Subsequent edits or renames of that derivative retain its own identity. A downloaded original, its personal derivative and the installed content can be compared without treating them as the same resource solely because their display or installation names match.

Developer authoring mode requires explicit selection of the owning Azrael project. Opening a project directory alone does not switch a recipient from its GitHub source to local authoring. The selected project source and mode are visible before edits or installation plans are prepared.

GitHub publication requires the authenticated account's actual write capability on the selected destination repository. Read access, a local copy, installation or membership in another repository does not grant publication authority. The host checks capability for publication; UI availability alone is not authorization. Existing public/collaborator visibility and local-only exclusions remain applicable. Read-only users can use the operations their source read access permits without gaining a write grant.

Migration preserves existing local changes and provenance. A path recognized as a Vault link is not sufficient evidence that its contents are duplicated by the project source or safe to discard. Migrating application-managed installation paths and deleting an external original are separate actions. The project-to-GitHub-to-recipient flow must work without a personal Vault on Windows x64, glibc Linux x64 and macOS ARM64; acceptance evidence remains environment-specific.

### Coexisting skills and runtime selection

Status: `partial`. Official and personal skill versions can remain preserved together. Coexisting installed skills use distinct validated installation names and retain separate source and receipt ownership; installation does not silently overwrite or rename another resource.

Instruction settings provide a per-skill control for inclusion in the model's available skill catalog. An excluded skill remains visible in the management catalog, retains its files and versions, and can be enabled again. Personal derivatives initially install with inclusion disabled; the installation review can enable them. Existing installed settings survive managed updates. Inclusion is distinct from acquisition, installation and publication. Exclusion must reach the native skill catalog and its prompt/discovery projections rather than merely filtering a settings list. It does not revoke ordinary filesystem access to the documents.

The selection identifies the resource and its concrete installed instance, so disabling the official version does not disable a personal derivative merely because their names or roles overlap. Path changes caused by a managed update must not silently enable an excluded resource. Required task-profile dependencies and captured running-thread state must be accounted for before changing effective selection; the UI must state when the setting takes effect rather than claiming that previously loaded instructions have been removed from a running conversation.

### User-created resource deletion

Status: `partial`. The management surface provides deletion for user-created personal resources, including personal derivatives. It distinguishes deletion of the local authoring resource, removal of a managed installation, and remote publication changes. Deleting a personal entry does not delete the upstream project or GitHub original or its publication history, and does not grant management rights over provider-owned resources.

Deletion defaults to removing the personal authoring source. Removing its unchanged managed installation requires a separate checkbox. Detached metadata retains installation and publication receipts and required immutable versions. Incomplete publication journals and dependent profile versions block deletion. The deletion review identifies the exact resource, affected local content, installed instances and dependent profiles or captured versions. Referenced content required for active work or recovery cannot be discarded by deleting its catalog entry. Deletion preserves truthful installation and publication receipts, detects concurrent edits, and uses the owning operation's locking and recovery procedure. Settings must report actual completed removal and any remaining protected content separately; a hidden row alone is not successful deletion.

## Version acquisition and integrity

The host downloads through bounded HTTPS requests to GitHub's API and release-asset hosts. The configured repository defaults to `felrer/Azrael` and can be changed in Azrael settings. It queries instruction tags, excludes drafts/prereleases from latest compatible selection, validates schema/version/app compatibility and binds all asset selections to that release. Git is not needed. A pinned version remains authoritative until explicitly unpinned. Activation does not silently download or replace instructions.

Caches live at `CODEX_HOME/azrael/instructions/versions/<version>/`. Each contains a verified manifest, complete extracted package and document preview data. The installer state at `CODEX_HOME/azrael/instructions/state.json` records applied version, repository, pinned version, selected component IDs and managed original hashes. Version cache entries are immutable for their recorded repository and content; a different release claiming the same version cannot replace them silently.
Publishing a verified staging directory uses an ordinary atomic rename. On Windows, transient `EPERM`/`EBUSY` errors receive up to five bounded retries (775 ms of total delay); persistent errors remain failures. Each attempt checks the staging directory identity and rejects an existing version destination, preserving immutable cache entries.
Reopening settings restores downloaded versions and document previews from the
verified local cache without a network request. Missing or corrupt cached
documents cause an error; initial page loading does not repair them over the network.

Archive extraction rejects absolute paths, `..`, backslashes, Windows aliases/reserved names, symlinks, duplicates, case collisions, unexpected files, excessive entry sizes and total size. Actual file bytes must match the external manifest. A checksum from the same release establishes content integrity, not an independent publisher signature. Downloads and validation complete before active files are changed. Cancellation and network or validation failures preserve the current installation.

## Application and recovery

The application plan uses the selected components and hashes from the last successful installation. Existing unmanaged files whose content differs from the proposed file and files differing from the managed originals are conflicts. An identical unmanaged file can be adopted without rewriting; its original bytes are retained for restoration. Conflicts are shown with current/proposed content and stop mutation; they are never overwritten automatically. Removing a component or a file restores the recorded original or deletes an unchanged newly managed file. Unrelated files in a skill directory are preserved.

Application takes an exclusive lock, captures source and destination states, stages complete output, validates the staged native agent configuration using the selected engine through strict app-server startup with closed standard input. The validator clears inherited window/management connection context and disables remote control for that child; the staged home remains isolated. Invalid native configuration blocks application before file replacement. Application then rechecks for concurrent edits, and records backups and a recovery journal before replacing files. It commits the state receipt last. Handled failures restore the affected files and receipt; interrupted commits leave explicit recovery data and require recovery before another mutation. Pin/unpin uses the same state lock and preserves applied file state. Rollback selects a previously verified cached version and follows the same conflict and compatibility checks as an update. Running threads retain their captured instructions; new threads use the applied instruction files.

## Settings surface

The integrated `Azrael 설정` command opens the existing native settings panel at its general settings section through the private host command `azrael.openSettingsPanel`. The command reuses the panel's settings navigation and does not substitute VS Code's configuration picker. Standalone instruction settings retain their owned renderer and service. Source routing is tested; rendered installed acceptance is separate.

The existing settings navigation has an Instruction documents / 지침 문서 entry with a thin monochrome document icon after personalization. Its labels, controls and generated status messages follow the active app language in English or Korean; the standalone surface follows VS Code's display language. The content follows the existing neutral typography, spacing, rounded gray selection, setting rows, buttons and focus styles in light/dark themes. It shows the source, applied/latest/pinned versions, compatible versions and changes, a categorized document list and scrollable plain-text preview, plus context-appropriate check, download, apply, update, pin/unpin and rollback controls. It distinguishes downloaded from applied state and exposes progress, retryable errors, incompatibility and local conflicts in the page. Source release notes, document content and external diagnostics retain their original text.

The host owns networking, filesystem operations and version state. Webview requests use `azrael-instructions` with a mount `clientId`, request ID, locale and validated action. The host keeps locale per mount and renders shared state for each language independently. Responses use `azrael-instructions-state` and retain those IDs. A mount releases its subscription on navigation/close or language change; late responses cannot update a new mount. Opening a page reads the persistent host state and can recover visibility of operations completed while the page was closed. An Azrael-owned standalone settings surface uses the same renderer and service as the integrated settings entry. Imported UI assets do not acquire new redistribution rights from this visual design.

Installed-host verification permits the renderer's exact empty `data-client-error` alert target. Populated errors, other alert elements and missing-module errors still fail verification; response identity, locale, baseline distribution and library revision remain mandatory.

Personal resource library initialization failures display a library-specific error while preserving the independently read baseline distribution state, including applied/pinned versions, cached documents and available baseline actions. A library failure does not establish that baseline instructions are unapplied. Packaged instruction modules and their transitive runtime dependencies must load entirely from the shipped account payload; preparation rejects missing dependencies and resolutions outside that payload before accepting the package. Preservation feature: `ui.instruction-settings`.
