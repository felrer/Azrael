## Parent decision requests

Status: `current` in source with Windows x64 MSVC lifecycle and direct plaintext router/guard/storage fixtures verified. This common engine contract does not establish packaged, installed-host, live-model or other-OS acceptance. Actual tool exposure is limited to the native OpenAI V2 path with the Azrael tool namespace, direct messages enabled and persistent sessions; other sessions use the existing message/final fallback. Source checks and native fixture results are recorded in the [work record](../../../../work/AR-01-root-child-mail-analysis/01-plan.md), and routing verification is owned by the [routing work record](../../../../work/AR-01-root-child-mail-analysis/03-plan.md), separately from delivery acceptance. Preservation feature: `engine.parent-requests` in the [feature inventory](../../../../scripts/azrael-feature-contracts.json).

Ordinary progress, verification and artifact readiness remain `send_message` mail. A child uses `request_parent({request_key, question, context, recommendation, blocked_action})` when its actual immediate parent's decision or coordination is needed now. The engine owns target identity and stores the request before scheduling delivery. Same-key identical retries reuse the request; conflicting contents fail. The return separates `request_id`, pending request status and delivery status, without promising an answer. Related known decisions are batched, but currently blocked work is not delayed for future questions or unrelated completion.

The Azrael namespace shares one plaintext-only tool predicate between direct-call classification and execution admission. It covers `request_parent`, `await_parent_response` and `respond_to_request` along with existing agent task/message tools. Direct calls accept absent or empty encryption metadata; nonempty encrypted metadata and code-mode calls remain rejected. Other namespaces retain their own supported tool and metadata rules. Plaintext request/response arguments are redacted from tool diagnostic payloads.

Immediate requests also expose a dedicated [chat activity row](ui.md#parent-decision-request-activity). Its optional durable presentation metadata binds the actual child path and original parent turn once, and stable activity IDs keep saved response updates in that same history row through resume and replay. Activity remains an interaction rather than child completion. A saved decision is displayed even if delivery back to the child fails. An older request without presentation can bind to an actual retained parent turn; absence of a real turn leaves delivery explicitly blocked without inventing history. Ordinary progress mail does not gain a received-message row. The UI owner's status separates rendered and installed acceptance.

A pending request wakes a parked parent through revision-checked admission or joins the running parent's next safe processing boundary. Concurrent requests join one admitted execution. Requests outside selected completion targets can still need that parent's answer. The engine does not synthesize child completion or duplicate parent turns. User stop/cancel and failed admission preserve the unresolved request and delivery reason without automatically restarting stopped work.

The child continues permitted independent work and suspends only dependent actions. `await_parent_response({request_id})` waits for the same request through the control boundary; it is neither final nor child completion and creates no second request or wake. A parent uses `respond_to_request({request_id, status, decision, reason, retry_condition?})` with explicit `resolved`, `cancelled` or `deferred`. Deferral requires its reason and retry condition; it is not approval. Ordinary mail, receipt, elapsed time and checkpoints do not resolve a request. Before waiting for completion again, the parent handles every pending immediate request through one of those states, preventing a cycle where it waits for a child that needs its answer.

Requests and answers are scoped to the actual parent/child relationship and child task identity. Automatic mailbox wakeups cannot start a fresh task while a child is suspended waiting for its own parent. An immediate request to such a nested suspended parent is retained with delivery reason `parent_waiting_for_its_parent` until that parent can process it; it does not override the existing wait. Explicit new user input ends the old wait before normal new-turn admission. A late answer cannot authorize a different task. Responses and retry keys are idempotent; failed delivery is separate from saved request state. Crash recovery preserves unresolved delivery and uses existing ambiguous-boundary/admission rules. An answer remains durably associated with its originating task. Starting a later assignment uses explicit existing followup semantics; a late answer cannot automatically start it.

The engine records request/delivery/response stages and individual response-wait intervals using `request_id` and `wait_id`, without question/answer bodies. Request-to-response time is distinct from actual blocked wait time. Request-to-response time uses stored wall-clock timestamps. Blocked wait uses a monotonic active-engine measurement; restart/offline intervals remain unknown. Recovery rotates the active wait identity while preserving the previous measured interval and requires retained await-call/task identity and compatible model/provider/authority settings. Wait checkpoints start after 60 seconds and repeat every five minutes through engine timers, without model polling or duplicate wakes. Answer, cancellation and interruption end the active interval and clean its timer; waiting failure does not delete the request. These diagnostics do not impose a timeout or grant automatic approval.

Communication guidance is a separate typed developer fragment, maintained in `instructions/instructions/parent-request-guidance.md` and embedded in prompts with an equality check. Its child/parent wording is selected from actual parent identity and current tool capability independently of configurable or empty role hints. Fresh context, compaction and reload use the world-state section; capability or relationship changes replace its fingerprint. Full-history forks remove the inherited fragment and snapshot before reconstructing the child's guidance. Unsupported sessions receive no instructions to call unavailable structured tools: they use `send_message`, independent work and, when blocked, a `PARTIAL` final stating completed scope, needed decision and next execution condition.

Implementation owners are `core/src/session/parent_request.rs`, the tool/protocol adapters, shared plaintext policy in `core/src/tools/multi_agent_tool.rs`, classification in `core/src/tools/router.rs`, admission in `core/src/tools/spec_plan.rs`, `prompts/src/parent_request_guidance.rs`, `core/src/context/world_state/parent_request_guidance.rs`, `core/src/session/world_state.rs` and fork sanitation in `core/src/agent/control/spawn.rs`. The feature inventory connects `scripts/check-parent-requests.cjs` to the native router/guard/storage and lifecycle fixtures plus state/core/prompts fixtures, and `scripts/test-common-agent-instructions.cjs` to source equality/provider mapping checks. Native lifecycle and model-context fixture acceptance remain separate from source-only checks and live-model delivery. Operational log fields and repeatable checks are owned by [native diagnostics](../../../ops/native-diagnostics.md#parent-request-and-response-wait-evidence).
