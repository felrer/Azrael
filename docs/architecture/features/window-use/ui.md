## Window Use settings

Status: `target` for unified presentation. Source implementation and installed UI acceptance have separate scopes below.

Window Use is the single settings, panel, consent and notification identity for window observation, selected-window control and whole-screen control. The page has one product enable switch, a Security App list and a control whitelist. Discovery, window capture and bounded inspection are allowed while enabled except that Security Apps require explicit observation approval; whole-screen capture masks those apps. Individual control automatically requests app approval unless whitelisted or covered by conversation-only desktop authority. Security Apps are blocked from all control, including when whitelisted or previously approved. Observation approval neither unmasks whole-screen images nor permits control.

Consent identifies the requested app or conversation desktop scope, purpose and shared-foreground effects. The UI distinguishes semantic window actions, Switched mouse collaboration and whole-screen coordinate input according to [input modes](README.md#input-modes-and-virtualization-boundaries). Separate logical cursors do not imply independent OS keyboard streams. Existing grants and disabled scopes survive settings conversion without implicit elevation; numbered-stage flags and global all-app approval cannot become new app authority. The current scope, pending approval, user Stop and recoverable failures remain visible. Browser tasks use the existing Chrome route. Settings and consent reuse native OpenAI-style components, semantic theme tokens and accessible keyboard behavior, with light/dark rendered acceptance required. The policy owner is [Window Use permissions](README.md#permissions).

User actions supersede quiet background reads; late replies cannot replace the acknowledged result. Keyboard interaction and both themes require actual rendered acceptance. App cards name the verified app; desktop cards name the conversation scope without fabricating an app identity. Whitelist and Security App settings entry points belong to the trusted current request; opening settings does not accept it. Waiting, expiry, denial and cancellation remain visible states; terminal requests cannot retain active approval buttons. Source light/dark rendering and interaction acceptance at normal and narrow widths remain distinct from the exact consent package's six isolated host acceptance stages and installation; real-user consent after reload remains unverified. Those package checks do not accept the revised app-based settings and consent scope. The model-visible permission and result contract is owned by [Window Use permissions](README.md#permissions).
