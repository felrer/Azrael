Status: `partial` — OpenAI용 UI 연결과 턴 제출 제한은 소스에서 구현·검증했다. 엔진 계약은 기존 빌드의 격리 실행으로 확인했으며, 현재 패키지와 설치된 앱에서 Auto-Review에 대한 수용 검증은 완료하지 않았다. 일반 패키지·설치 성공으로 이 기능의 설정 탐색과 제출 동작을 검증했다고 해석하지 않는다. 검증 절차와 범위는 [development operations](../../../ops/development.md)에 기록한다.

## 권한 선택과 실행

이 절의 UI 제공 여부·선호 보존·턴 제출 동작은 현재 소스 계약이다. 엔진의 조직 요구사항 적용은 기존 구현을 재사용하며 실제 관리 환경의 수용 검증은 별도 범위다.

Azrael의 기존 권한 선택 메뉴에 원본 `Approve for me` 모드를 제공한다. 앱 전체의 [OpenAI 서비스 계정](../accounts/README.md#independent-openai-service-account)이 준비되면 Anthropic 등 다른 채팅 공급자의 승인 요청도 독립 OpenAI 리뷰어가 판단한다. 기존 기본 모드와 저장된 선택은 유지하며, 전체 액세스는 기존 `never` 승인 정책을 유지한다. 이 서비스 경로의 구현·수용 범위는 [작업 기록](../../../../work/FO-01-azrael-auth-entry-review/01-plan.md)이 소유하며 설치 수용 전에는 target으로 구분한다.

### 전체 액세스의 삭제 승인

상태: `target`. 구현과 검증 범위는 [작업 기록](../../../../work/BT-01-request-scoped-command-approval/01-plan.md)이 소유한다. 보존 기능 ID는 `runtime.deletion-approval`이다.

전체 액세스의 native 정책은 `never`와 비활성 샌드박스를 유지한다. 종전 정책이 허용한 삭제 호출과 자동 승인한 `apply_patch`는 그대로 통과한다. 종전 위험 명령 분류가 차단한 명시적 삭제 호출은 사용자 승인을 요청한다. 일반 명령, Git의 변경 폐기, 시스템 설정 변경을 새 승인 대상으로 추가하지 않는다. 기존 명시적 forbidden 규칙과 파일 접근 제한, hook의 Deny는 유지한다. hook의 Allow와 Guardian이 이 삭제 승인을 대신하지 않는다.

삭제 분류는 Windows PowerShell/CMD 및 POSIX 셸의 알려진 삭제 명령과 기존 파서가 해석하는 래퍼·복합 명령을 다룬다. 강제 옵션 없이 수행하는 삭제도 포함한다. 셸에서 삭제 실행 파일명이 정적으로 확인되면 동적 인수 구문의 존재를 보존하여 `rm "$f"` 같은 호출도 식별한다. 인수가 없는 `rm`과 명시적인 `--help`·`--version` 호출은 POSIX 삭제로 분류하지 않는다. 임의 외부 스크립트나 MCP 내부의 모든 삭제를 탐지하는 보편적인 파일 접근 감시 기능은 아니다. 별도 프로젝트 관리 도구의 정리 계약은 유지한다.

기존 명령 승인 카드를 재사용하고, 승인 전에는 해당 호출을 실행하지 않는다. 승인 대상 삭제 명령에는 한 번 승인 또는 중단을 제공하며 세션 승인 캐시와 영구 prefix 허용을 적용하지 않는다. 전체 액세스가 확인된 호스트도 이 삭제 승인 요청을 자동 수락하지 않는다. 거절·취소는 실행 허가로 해석하지 않는다. 에이전트 지침의 강제 삭제 금지는 실행 승인과 별도로 유지한다.

서비스 메인 계정의 인증·리뷰 모델·정책 준비 상태를 기준으로 기능 제공 여부를 계산한다. 채팅 공급자만으로 기능을 차단하지 않는다. 계정이 없거나 만료·확인 실패·정책 제한이면 항목을 유지한 채 비활성화하고 마우스 hover와 키보드 focus로 실제 사유를 제공한다. 화면의 준비 상태와 실제 제출의 재검사를 분리해 오래된 화면이 실행을 허가하지 못하게 한다. managed 공급자의 구조화 출력 지원을 임의로 해제하지 않는다.

모델 로딩은 Auto-Review 선택 가능 여부에만 적용한다. 설정·조직 요구사항·작업 경로가 준비되면 모델 로딩 중에도 기존 기본 권한과 전체 액세스 메뉴를 사용할 수 있다. 실제 설정 미준비와 정책에 따른 권한 제한은 유지한다.

서비스를 사용할 수 없을 때 수동 승인 전환은 기존 정책이 허용하는 범위에서만 가능하다. 샌드박스·쓰기 경로·권한 프로필·승인 정책은 그대로 유지하며, 실행 중인 턴은 소급 변경하지 않는다. 저장된 Auto-Review 선호는 유지하고 준비 상태 회복 후 다시 적용한다. 일시적인 인증·서비스 미지원 때문에 전체 권한 프리셋을 다시 저장하지 않는다. 실제 설정·조직 요구사항이 변경된 경우에는 기존 설정 유효성 규칙을 적용한다.

조직 요구사항이 사용자 리뷰어를 허용하지 않으면 미지원 제공자의 다음 턴을 시작하지 않는다. 기존 설정 오류 경로로 실패를 표시하며, 권한 제한을 변경하거나 실패한 리뷰어 갱신을 성공으로 취급하지 않는다.

Auto-Review는 `on-request` 또는 검토 대상 요청이 허용된 세분화 승인 정책에서 동작한다. 샌드박스와 파일·네트워크 권한은 기존 승인 경계를 유지한다. 경계 안에서 이미 허용된 작업은 추가 검토 없이 실행한다. 조직의 허용 모드와 명시적 기능 제한을 적용하며, Azrael의 기능 제공 여부가 이러한 제한을 해제하지 않는다.

설정 저장·대화별 권한 갱신·선택 확인은 기존 UI와 app-server 경로가 소유한다. 권한 갱신 실패를 성공한 선택으로 표시하거나 해당 실패를 우회해 작업을 시작하지 않는다. Computer Use의 앱 접근 승인은 기존 사용자 승인 경로가 소유한다.

## 리뷰어와 판단

이 절은 재사용하는 기존 엔진 계약이다. 격리 실행은 합성 OpenAI 응답을 사용하며 실제 계정의 추론 품질·사용량 검증을 대체하지 않는다.

기존 Codex Guardian 리뷰어와 정책·출력 계약을 재사용한다. 리뷰어는 제안된 작업과 공개 대화·도구 근거를 받아 위험도, 사용자 권한 근거, 승인 또는 거절, 사유를 반환한다. 비공개 추론은 검토 대화에 넣지 않는다. 리뷰어의 도구와 권한은 별도 제한하며 재귀 승인을 만들지 않는다.

Azrael 서비스 리뷰는 메인 계정의 OpenAI 제공자·카탈로그에서 리뷰 모델을 선택하고 해당 인증과 정책을 내부 리뷰 thread에 전달한다. Anthropic 부모 모델로 대체하지 않는다. 일반 CLI/native 리뷰어는 기존 계약을 유지한다. 서비스 리뷰는 시작 시의 계정·revision에 귀속되며 교체로 재실행하지 않는다. 요청 종료 뒤 새 리뷰는 최신 선택을 확인한다. 검토에는 OpenAI로의 공개 근거 전송과 추가 사용량이 발생한다.

공급자를 넘는 검토에는 공개 메시지와 정확한 도구 call/result만 투영한다. 외부 공급자의 비공개 reasoning·암호화 상태를 재사용하지 않고, 안전하게 해석할 수 없는 불투명 checkpoint만 남아 있으면 근거 부족으로 검토를 실패시킨다. 원본 기록은 수정하지 않는다. 서비스 리뷰의 인증·카탈로그·정책과 재사용 키는 부모 채팅과 분리하며 다른 계정의 reviewer 세션을 재사용하지 않는다.

승인된 요청만 실행한다. 거절은 사유와 함께 주 에이전트에 전달하고 같은 결과를 얻으려는 우회를 금지한다. 검토 생성·파싱 실패나 시간 초과 시 요청을 실행하지 않으며, 시간 초과는 위험 판정과 구분한다. 연속 거절과 최근 검토의 누적 거절에 대한 기존 엔진 중단 규칙을 유지한다.

## 화면과 기능 제공 여부

원본 메뉴 항목·아이콘·설명·확인 화면·승인 카드의 안내를 재사용한다. 동일한 기능 제공 여부 계산을 메뉴와 안내에서 공유한다. 원본 UI의 외부 서비스 실험 플래그에 의존하는 부분을 Azrael의 로컬 기능 제공으로 연결하되, 허용된 권한 모드와 명시적 설정 제한 및 조직 요구사항의 우선순위는 유지한다. 로컬 설정·요구사항·모델을 확인한 뒤 외부 실험 플래그 로딩 때문에 선택지가 계속 대기하지 않는다. 별도 설정 페이지나 리뷰어 모델 선택 화면을 만들지 않는다.

표시는 [UI presentation](../../shared/ui-principles.md)의 기존 OpenAI 스타일과 테마 토큰을 따른다. 밝은·어두운 테마의 실제 렌더링과 선택 상호작용을 검증한다. 소스 검증·격리 엔진 검증·패키지 검증·설치 상태를 구분하며, 검증 범위를 넘어서 제공자 지원을 선언하지 않는다.
