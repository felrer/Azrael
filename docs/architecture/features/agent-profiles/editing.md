## Package development workbench

Status: `partial`. The standalone browser workbench implements the package experience in an isolated development sandbox. The native settings adapter and request snapshot integration are implemented and undergoing package/native acceptance. Windows source tests and browser checks cover the standalone adapter; installed-engine application remains unverified until that acceptance completes. Implementation and acceptance scope belong to the [work record](../../../../work/FA-01-instruction-package-dev-tab/01-plan.md).

Packages provide an image, title and description with one or several skills, Playbooks, reference documents, roles and optional model profiles. A compound package is an existing immutable context resource whose complete inventory includes `AZRAEL-PACKAGE.json`, component files and optional image asset. The versioned manifest identifies component files and profile selections. These bytes use the existing library digest, validation and GitHub release protocol. Existing individual resources remain browsable through a single-component adapter; a pinned task-profile resolves its declared resources rather than following current versions. A new derivative package copies selected component snapshots, retains provenance and has its own identity. Runtime activation does not merge several installed packages.

The common catalog combines local resources and connected GitHub sources. Source identity and package identity distinguish unrelated entries with the same name; downloaded copies remain associated with their remote source. Market source identity is reserved for future integration, without a market service or acquisition implementation. Images are bounded validated raster assets, not executable markup or unrestricted external URLs.

The maintained baseline manifest appears as one `Azrael 기본 패키지` card; its instructions, skills, Playbooks and roles are listed inside the package detail rather than as separate catalog cards. Catalog discovery reads only its manifest. Component names participate in package search, and the kind filter returns containing packages. Composer resources keep their existing independent selection identities. Details show source, version, component/profile counts, expandable component files and included-profile selections; file bytes are read on opening details, not on listing packages.

Cards have a uniform horizontal layout with an image on the left and title/description on the right. The grid adds columns as space permits, uses one column on narrow screens and avoids horizontal overflow below the normal card width. Source, downloaded state, current-project use and a known new version have separate accessible icons or badges. Selecting a card opens an expanded detail card with the complete description, component/file previews and profile details. Returning preserves search and position. Existing library management is accessible in a collapsed area below the new catalog. Source-mode, source-project and project download-target controls are absent from the workbench.

Opening the page displays local metadata and verified cached remote entries without waiting for GitHub, native skill enumeration or complete support-file scans. `업데이트 확인` starts an explicit background GitHub query; only a small corner status indicates progress. Search, details and independent local edits remain usable. Results update the relevant entries without resetting forms, selection or scroll. Query failure retains the previous catalog and offers retry. Update discovery, download, profile activation and publication remain separate operations. Source errors appear near the relevant source or resource, instead of a general source-notice disclosure.

Profile authoring reads a host-only whitelist of saved connected-account metadata and Azrael model-cache observations. The optional `Provider 지정` checkbox controls provider, model and reasoning settings together. Unchecked omits all three overrides and the account restriction; checked inserts the dropdowns inline between the checkbox and the following form fields, without an enclosing card. A connected account and available model are required when enabled; reasoning is optional. The account scope filters models and each model supplies its supported efforts/default. Deleted or explicitly reauthentication-required accounts are excluded. Stable account scope IDs remain distinct from native modelProvider; saved profiles retain the native provider and separate providerAccount identity. Cache observations do not establish a fresh per-account entitlement or installed-engine activation. Inheriting runtime model settings for profiles without overrides requires separate native-adapter acceptance.

An account-selection recovery state makes all OpenAI account scopes unselected; it does not hide otherwise connected accounts or their verified cached model inventory. Per-account removal/reauthentication markers and malformed metadata still exclude unusable observations. Read-only discovery neither selects another account nor grants execution eligibility; runtime account admission remains authoritative.

Profiles are the activation unit. Several profiles can be stored, with exactly one active profile per project. Local and downloaded package-provided profiles appear as templates in the profile list. Editing or duplicating a template creates a separate personal profile; explicit activation of a template creates a personal copy and activates it. Packages without profiles supply resources for profile creation. Dragging a stored profile to the current project's active slot or using its accessible activation control selects that profile. The composer uses one `저장` action independently of activation. Changing one project's selection does not change another. Unassigned conversations use Azrael's default settings.

The target Azrael adapter captures project identity, active-profile revision and pinned component digests when a user request is accepted. A profile change affects subsequent requests for that project. Already accepted, queued and running requests, including their internal model steps, keep the captured snapshot. Native authority and global/user/project instruction ownership remain independent; profile switching replaces only that profile's contribution. Skills and long references stay on demand. Failed activation preserves the previous active selection. Provider handoff, compaction and replay require the same snapshot before integrated activation can be accepted.

The browser adapter writes only to an owned development sandbox. It can read explicitly selected libraries and the maintained baseline. Sandbox profile selection and captured-request preview do not activate an installed Azrael conversation. The host owns filesystem and GitHub credentials; a loopback HTTP transport validates host, origin and session token. The browser receives no GitHub credential. The same domain and UI modules are intended for the later Webview adapter, while live engine application remains a separate acceptance gate. Preservation feature: `ui.instruction-settings`.

Existing conversations created by the legacy library's fixed-profile command retain their original profile and admission path. Project profiles apply to ordinary and new conversations, without mixing with those legacy snapshots. The separately maintained browser development tab keeps its sandbox and remains available after native integration; production state lives under `CODEX_HOME/azrael/instruction-workbench`.

### Profile composer

Status: `partial`. The standalone composer implements vertically arranged slots on the left and a categorized resource catalog on the right. Resources can be added by drag or an accessible click/keyboard alternative. Profile authoring selects resources directly rather than selecting a package for the profile. The Azrael harness identity/core instruction is always present, read-only and cannot be removed. Additional base instructions support multiple entries and explicit ordering. Skills and MCP selections represent activation sets rather than instruction ordering. Playbooks, references and agent roles retain their distinct resource meanings. Host materialization supports composer profiles through immutable snapshots; native selected-only skill/MCP enforcement and ordered instruction application are implemented in source but still require compilation and integration acceptance.

The default profile is read-only and uses the existing default configuration. Other profiles are editable. A custom profile activates only its selected optional skills and MCP connections; unselected items do not inherit activation from the default profile. Azrael-required capabilities remain independently available and are not removable through optional resource selection. An empty optional selection enables no optional items. Selecting a package resource does not install a server, grant permissions or provide credentials.

The composer has one `저장` action, which persists the profile without equipping it. Project activation is a separate action. Saving edits to an already active profile affects the project's subsequent admitted requests; accepted and running requests keep their captured configuration. Native source preserves the six core workflow skills and required runtime servers while restricting optional selections. Host and browser composer behavior is verified; native enforcement remains acceptance work.

Profiles support duplication into a separate editable personal profile, including duplication of the read-only default profile. Duplication preserves the selected configuration while keeping the source unchanged and does not activate the copy. Required Azrael core instructions remain fixed in copies. Duplicating MCP selections does not duplicate credentials or grant new permissions.

Configuration diagnostics identify affected slots and summarize problems on the profile list. Diagnostics cover missing selected resources, unavailable MCP connections, unsupported provider/model/reasoning selections and duplicate resource identities. Instruction text disagreement is not presented as a reliably detected configuration error. An invalid configuration can be saved for further editing but cannot be activated or replace a project's applied configuration. Saving invalid edits to an active profile preserves its last valid applied revision, with the saved and applied states visibly distinguished. A valid edit to an active profile replaces that applied revision for subsequent admissions. Validation is repeated at application and request admission; preserving an applied revision does not establish that its external MCP connections or credentials are still available, and failures do not silently switch to another profile or default configuration.
