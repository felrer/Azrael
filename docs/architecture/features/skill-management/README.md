## Personal skill management

### Agreed product contract

Status: `partial`. The source implements local resource editing/import, separate Apply/Publish review, repository connections, verified remote packages and interrupted-operation recovery. Windows offline protocol/host tests and isolated light/dark/narrow rendering pass. This evidence does not establish live GitHub or installed-host acceptance. The baseline release installer retains its existing ownership.

Azrael provides one management surface for personal skill sources, installation and sharing. A skill includes its `SKILL.md`, scripts, references, templates and other support files. Sharing applies to the complete skill folder rather than individual files.

Sharing supports both independently acquired instruction resources and task profiles that compose resources with model settings. A user can acquire a complete task profile or reuse an individual instruction resource. The detailed package schema, dependency resolution and task activation are specified by the draft composition contract above.

A shared task profile supplies a recommended model that the user can explicitly change when applying it. Application validates the effective model's provider/tool compatibility and required capabilities and records the actual selection. Model substitution is not automatic and does not silently change the shared profile.

Task profiles apply only to the selected new conversation. They do not set a project default or modify a running conversation. Each new conversation can select its own task profile; acquiring a profile without applying it does not activate its instructions.

Three sharing classes are supported: public, one fixed collaborator group and local only. Public and collaborator content use separate GitHub repositories. Repository access controls the fixed group; membership in the Azrael application repository does not automatically grant access to the collaborator skill repository. Local-only content is excluded from Git tracking by the application repository and from all publication inputs. The management directory may reside inside the local Azrael project, while each remote repository remains independent.

New and first-imported personal skills default to collaborator sharing. This selects their intended publication destination without transmitting content. Existing verified remote provenance is retained rather than treating an imported published skill as unpublished.

Save updates only the local management source. Apply separately updates the Azrael installation and takes effect in new conversations. Publish separately presents the destination and included changes before transmitting them to GitHub. Apply and publish are independent: publication does not install a skill, and installation does not publish it. Running conversations retain the existing instruction lifecycle.

Sharing-class changes preserve past Git commits and release assets while restricting subsequent publication to the new class. Entries retain a `Previously published` indication with their known destinations and versions. Collaborator publication is available to every user with actual write capability on the collaborator repository; Azrael does not impose a separate owner-only publication role.

Local-only means exclusion from skill-sharing repositories and publication. It does not define a new model-inference policy: normal use of a selected skill remains governed by the native prompt and provider context contracts.

### Source, data and installation structure

Status: `partial`. The local storage and publication boundaries below have source implementations. Remaining product extensions and installed acceptance are distinguished from those implementations in the [current work record](../../../../work/BA-01-instruction-skill-sharing/01-plan.md).

All installations default to a sibling of `CODEX_HOME` named `<CODEX_HOME>-instruction-library`; opening an authoring checkout does not switch personal storage. Existing project-local libraries remain usable by explicitly selecting their absolute management location. Explicit project source mode reads the maintained `instructions/` tree independently of this personal store; `azrael.instructions.libraryRoot` can select another absolute management location. Library and installation roots cannot overlap. Within Git repositories, the library requires both prospective registry and package paths to be ignored and rejects any already tracked library files. The baseline release builder reads the public `instructions/` tree and explicitly excludes its checkout-local `.private/` directory before reading file contents; personal library bytes are not added to application or baseline instruction packages. Release archives, document indexes and manifest inventories share this exclusion, and a component mapping into excluded private data is rejected. Git ignore alone is not a packaging boundary.

The maintained public library contains five default core skills plus optional internal visualization and ktcloud skills. Personal machine-bound skills such as the current SSH profile live under `instructions/.private/skills/` and are not public components. ktcloud code and instructions are public source, while its repository-local settings and session records live under `instructions/.private/ktcloud-ai-nexus/`. Installed distributions resolve private records under the isolated Azrael state root, with an explicit absolute override when selected. Authentication material retains its existing machine-local owner. No skill invokes the retired Vault-first manager as a prerequisite for authoring or discovery; optional acquisition and authoring retain their existing purpose-built workflows. Personal installation links may select these local sources without publishing them or changing permissions on the external source.

`scripts/instruction-library.cjs` owns `registry.json`, immutable `packages/<id>/<digest>.json`, managed installation receipts and local recovery state. Package identity survives editing; content digests include name, kind, sharing, files and profile, while installation/publication metadata remains local. GitHub connections are scoped to the management root. Publication journals in `operations/` retain the exact host-owned approved bytes and destination; webview operation tokens expose only reviewed summaries and previews.

Personal Apply uses the same `CODEX_HOME/azrael/instructions/writer.lock` as the baseline installer, in addition to its library lock. Different libraries cannot race over the same installation. A baseline journal blocks personal mutation. Recovery clears only the matching library's dead personal writer marker, and preserves another library's or the baseline owner's marker. Identical unmanaged files can be adopted through an explicit reviewed Apply; their original bytes are retained. Differing unmanaged or externally edited managed files stop Apply. Renaming or removing managed support files restores adopted originals and removes only unchanged files created by the library.

The existing `instructions/` remains the owner of the maintained baseline instruction bundle, global guidance and agent roles. Bringing its skills into the management surface retains their source ownership instead of creating competing editable copies. Managed baseline skills can reference their existing owning directories; the publisher still selects explicitly approved content. Personal additions, collaborator sources and local-only content must not be placed in the baseline release tree. The existing whole-tree baseline release builder requires a separate boundary review before combining it with personal publication.

Each library entry has an immutable `skillId`, editable display name, validated engine skill name, source location and provenance. A renamed skill keeps its identity; its old installation name is removed only by an explicit apply plan. The registry records desired sharing class separately from known published destinations. Local metadata records the current content digest, installed digest and receipt owner, and publication commit, release and manifest digest for each destination. Tokens and machine-specific paths are not publication metadata.

The proposed first personal-skill installation target is `CODEX_HOME/skills/<engineName>`, matching the current Azrael personal installation. The project directory owns authoring, while that installation is available to the user's Azrael conversations. The Apply preview names this scope; project-scoped skill activation is a separate explicit choice rather than inferred from the source location. Existing workspace playbooks remain supported by the baseline installer.

Installation state and publication state are separate comparisons. The UI can show `Installed; local changes; collaborator destination; not published`, or `Applied; publication failed`, without treating one operation's success as evidence for another. An imported installation without a managed receipt is shown as an existing unmanaged installation, even when its bytes match the source. Remote state that has not been checked is unknown, rather than current.

Scan the active Azrael personal skill locations for import candidates and offer an explicit directory picker for additional sources. System and plugin-managed skills remain provider-owned entries with source and update information; copying one creates a separately named personal derivative with retained provenance. Import previews the folder inventory and name conflicts, copies a personal source into the library or registers an eligible maintained source, and preserves the original installation. Duplicate names are not silently renamed or installed over another source. A skill name can have only one installation owner per destination.

Validate `SKILL.md` frontmatter and complete support-file inventory before apply or publish. Reject escaped paths, symlinks and case-colliding names; retain the existing platform path protections. Incomplete edits can be saved as invalid drafts, with apply and publish unavailable and specific errors shown. Importing or editing a skill does not execute its scripts.

Reuse the existing installer's staged writes, original-file receipts, content hashes, locks, conflict handling and recovery. Extend receipt ownership to stable source and skill IDs before managing overlapping destinations. A local application plan compares source, previous receipt and current installation. External installation edits stop application; the user can bring them into the source, compare them or explicitly replace them after review. Unrelated files remain protected. Undoing an installation restores preserved originals or removes unchanged managed files. Deleting a management source and uninstalling it are separate operations.

### GitHub connections and publication

Each connection records a stable source ID, repository identity, branch, expected visibility, account and available read/write capability. Public and collaborator connections must refer to different repositories. Connecting checks the actual repository visibility and access; changing a repository's visibility externally blocks incompatible publication until reviewed. The application does not silently create repositories, invite collaborators or change repository visibility. Initial repository setup is an explicit onboarding action.

Prefer the host's GitHub authentication session when available. A scoped token alternative uses VS Code SecretStorage if the installed host cannot supply a suitable session. Authentication-provider availability is verified in the actual Azrael package before choosing the supported route. Credentials stay in the host and credential owner, never in webview messages, source files, publication manifests or diagnostic logs. See [VS Code authentication and secret storage](https://code.visualstudio.com/api/references/vscode-api).

Read access permits remote browsing, download and local installation. Write operations require actual repository write capability. Every writer can publish under the agreed group policy. The UI reflects the actual GitHub permissions rather than claiming an access restriction from button visibility. Private repository visibility alone is not an application-enforced read-only grant.

Use GitHub APIs for remote source commits and release assets so ordinary browse and installation retain the existing no-Git requirement. A publication freezes the approved source bytes, target repository and sharing class, complete file list, base branch commit and release version. Changes made while publication runs remain newer local edits and are not added to that operation.

The outgoing repository tree combines the accepted remote base with only the selected skill changes. The release represents that complete resulting repository inventory, preserving unselected published skills and excluding unselected new local entries. It does not publish every locally edited skill merely because it has the same desired destination. Files outside the managed skill roots and generated release metadata are not edited by skill publication.

Build one commit from the approved changes and update the branch without force. A changed remote branch stops publication for review and a new comparison; remote work is not overwritten. GitHub supports non-forced reference updates and reports conflicts. See [Git reference updates](https://docs.github.com/en/rest/git/refs).

Publication has two visible milestones: source commit accepted and installable release published. `scripts/instruction-publisher.cjs` assembles a resource ZIP and manifest from a frozen filtered inventory, uploads a draft release and publishes it only after every expected asset is verified. Source-committed receipts immediately preserve the known sharing history even if asset publication fails; the operation separately records release completion. Reopening settings reconciles these receipts without a network request. Retrying inspects remote outcomes before creating another commit or release. The operation does not promise a transaction across GitHub commits and releases.

Resource repositories use immutable `packages/<id>/<digest>/package.json` and support files, with `index.json` recording current heads. A selected current profile can retain historical pinned dependencies in the same release. Tags are `azrael-resources-v<semver>` and assets are `azrael-resources-<semver>.zip` plus its manifest JSON. This resource protocol is separate from the existing `instructions-v<semver>` baseline protocol. Checksums, bounded extraction and package content digests are validated before import. Actual repository visibility and writer capability are checked; no repository creation, invitations or visibility changes occur automatically.

Public and collaborator repositories maintain independent instruction release versions. The cache key includes repository/source identity, version and manifest digest, rather than version alone. Pinning is per source; one installed destination still has one owner. Keep a single coordinated installation ledger or equivalent shared destination lock across sources, so separate stores cannot race to install the same name. Existing single-source receipts and immutable caches need a staged migration with provenance retained; the old layout is not simply opened by both new sources.

Private assets are fetched through the authenticated GitHub asset API. Credentials are attached only to the authenticated GitHub API origin and are not forwarded to redirected asset hosts. Public downloads can remain anonymous. See [GitHub release asset download](https://docs.github.com/en/rest/releases/assets).

The package, manifest, document previews and release notes contain only the approved destination's skill inventory. File names, private source paths and the complete local registry are excluded when not public. Local-only metadata never enters remote payloads. Logging records operation IDs and outcomes, avoiding private document bodies, credentials and publication previews. Backups and recovery snapshots containing private or local data stay local and are excluded from app/release artifacts.

### Scope changes, updates and recovery

Changing the desired class changes future publication selection. Applying a scope change does not erase known publication destinations. The publication preview identifies additions at the new destination and any removal from the current source tree at the previous destination. A move across repositories records both outcomes independently and resumes only unfinished steps after failure.

The history policy preserves old commits and release assets. Public-to-collaborator or shared-to-local transitions display `Previously published` with the known destinations and versions; they never claim previously published bytes have become confidential. New local-only changes are excluded from every publication. Scope changes do not delete historical releases or rewrite Git history, and copies already downloaded remain outside the application's custody.

Update checking is explicit. Opening the settings page restores local state and verified caches without automatically contacting GitHub. A downloaded update is not automatically applied. Compare local source, the last synchronized base and remote source: when both sides changed the same managed entry, require a comparison instead of silently replacing it. Pinned sources retain their selected version until unpinned. Offline save, comparison and local apply work without GitHub; publication remains pending until a requested retry.

Operations are serialized per library and installation destination. Host-side validation binds each approved action to its frozen input digest and account/repository identity. A changed source, target, permission or library revision requires a new plan. Cancellation before mutation discards preparation; after a remote commit, cancellation preserves the known remote result and records what remains. Interrupted local changes use a recovery journal; interrupted remote publication uses commit/tag/asset identifiers and confirms actual server state on explicit recovery. Recovery does not publish newer edits or widen the sharing class.

### Implemented task boundary and remaining acceptance

`scripts/task-profile-runtime.cjs` materializes the reviewed dependency snapshots beneath `CODEX_HOME/azrael/task-profiles/<digest>/`. Short profile instructions are additive developer context with package attribution; context support files become discoverable references and complete skill bodies stay on demand. Selected role files are declared through per-thread `agents.<name>` configuration. Native runtime identity, base instructions, existing project guidance and permission enforcement retain their owning paths.

The effective native skill configuration now supports absolute `skills.extra_roots`. The host supplies these in `thread/start` configuration rather than calling the global `skills/extraRoots/set` API. Resolved-root cache keys and the cwd cache guard keep task resources out of other conversations. Model/provider/reasoning and supported builtin harness combinations are checked against native discovery before activation, with no automatic model replacement. Roles require an enabled native multi-agent feature and a root model with advertised spawning capability. Native draft transfer, first-turn composition and cold resume are owned by `scripts/inject-task-profile.cjs` and `scripts/task-profile-runtime.cjs`; package digests and per-thread associations preserve the captured resources across later local edits. Project-panel transfers use an origin-bound one-use token. The first successful turn captures the reviewed model and reasoning settings even when native collaboration settings carry another model; ordinary later picker changes retain their native meaning.

The first source implementation uses an explicit import picker and JSON editing for profile composition. Installed/provider-managed source inventory and explicit maintained project/release source selection now have source implementations. Custom shared behavior-template content remains a product extension; its target paragraphs above do not claim implementation. Current task harness references support the builtin prompt/tool IDs; unknown custom IDs stop activation. Full integrated task lifecycle, live authenticated GitHub checks and the final installed package require their own acceptance evidence. Feature IDs `ui.instruction-settings` and `engine.task-profile-skills` bind the implementation owners and mandatory source/native checks in the preservation inventory.

### Resource discovery and project Playbooks

Status: `partial` in source. Resource discovery, project Playbook delivery and version comparison have Windows backend, offline host and isolated rendered UI evidence. The [work record](../../../../work/CM-01-instruction-library-experience/01-plan.md) records verification; packaged installation, live connected repositories and Linux/macOS acceptance remain separate.

The instruction documents page provides one searchable catalog of the user's local library, Azrael-provided and installed resources, and resources from connected public and collaborator repositories. Search does not extend to unconnected external repositories. Categories select resource kinds rather than user-defined topics. Users can browse cards or a vertical text list and inspect a resource before acquiring it. Installed or provider-owned resources retain their original ownership; listing a resource does not create an editable personal copy, install it, activate it or publish it. Existing source-separated caches, permissions and local-only publication exclusions remain applicable.

Resource details provide a destination-specific primary action, such as downloading to the selected project or installing into Azrael. The action prepares verified resource content and shows the destination and file changes for review. Confirmation continues through acquisition and installation without requiring the user to find a separate import action. A secondary action adds the resource to the personal library without installing it. Preparation may populate a verified cache for preview; personal library registration and destination writes remain governed by the confirmed action. Acquisition and destination installation retain separate outcomes, so a successful acquisition followed by a failed write remains available for retry and is not shown as installed. Existing ownership conflicts and local edit protections still stop destination changes. Acquisition and installation do not publish the resource or activate it in an existing conversation.

Playbooks have a distinct resource kind in the catalog and default to local-only sharing when created. Their project destination is `docs/playbooks/<resource-id>/PLAYBOOK.md`, with support files inside the same directory. Leading metadata uses `azrael_playbook_id` and `azrael_playbook_version`. A Playbook document carries a stable document ID and version in leading metadata. For the explicitly selected local project, the UI compares the actual destination document's ID and version with the selected library resource: an absent file is not downloaded, a matching ID/version is downloaded, a matching ID with another version has a version difference, and missing/unreadable identity or version information requires checking. An unrelated document at the destination is a conflict rather than a downloaded copy. This status does not compare body content or prove that instructions are active. Update writes retain existing protection for local edits and unmanaged files. Resource versions are distinct from repository release versions.

A newly authored Playbook starts at version `0.1.0`. Saving a valid change to its distributable document content or support files automatically increments the patch component, for example from `0.1.0` to `0.1.1`. Saving unchanged content does not increment the version. Invalid drafts remain saveable under the existing draft rules but do not create a new downloadable version. Changing display-only or sharing metadata does not by itself change the document version. Acquiring an existing Playbook preserves its declared document ID and version. A newer library version does not automatically replace project files: the project shows a version difference until an explicitly reviewed update succeeds. This document version is independent of repository publication versions.

The catalog behavior is shared across local Windows x64, glibc Linux x64 and macOS ARM64 hosts. Platform paths, case sensitivity and credential ownership retain their existing contracts; remote workspace support is a separate scope.

The default catalog is a full-width vertical text list, with an optional card view. Search and resource-kind selection remain visible; source, sharing and destination-state filters are available through a filter control. Entries show title, short description, kind, source, version and destination-specific state. Selecting an entry opens a separate full-width detail screen containing the content preview and its destination-specific primary action. Returning restores the search, filters, selected entry and scroll position. Wide and narrow layouts use the same list-to-detail navigation. Editing, publication, library-only acquisition and technical metadata are secondary detail actions rather than permanently expanded forms in the catalog.

Version controls expand inside each list entry and are also available in detail. Choose a comparison base (a saved version or actual installed/project files) and an available version to inspect changed files with added and removed lines. Selecting or comparing versions does not install them. The primary action installs the exact selected snapshot after its destination preview; long content remains readable in detail. Personal history and connected release history retain immutable digests. Installed/provider resources remain read-only until explicitly acquired; matching managed installations are attached to their existing personal entry, while independent sources remain separately attributed.
