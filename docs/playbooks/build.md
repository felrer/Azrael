# Build and Reinstall Playbook

Applicability: Use when packaging Azrael engine, bridge or account module changes, or installing, updating or rolling back a local development distribution. [Development operations](../ops/development.md#build) owns execution commands.

Apply the [testing skill](../../instructions/skills/testing/SKILL.md) for common test selection, assertions, execution evidence and suite maintenance. This playbook retains Azrael's build inputs, caches, prerequisite gates, check selectors and exact-package acceptance.

When uploading a verified local build to GitHub Releases, also apply the [app release procedure](../ops/app-release.md).
Keep the distribution version, tag and file hashes consistent; do not overwrite files in an already published version.
Public macOS ARM64 distribution follows the [Mac distribution policy](../ops/app-release.md#macos-distribution-without-a-developer-id-certificate). Publish after obtaining a valid ad-hoc signature, an unnotarized-app notice and acceptance of the actual final package, without Developer ID or Apple notarization. This policy also applies to future Mac distributions and does not require obtaining a certificate first.

## Artifacts and Build Scope

- Apply the common [build-input rules](../../instructions/skills/implementation/references/build-inputs.md) for frozen inputs, app version and retry identity. These rules apply across Windows, Linux and macOS under the [multi-platform contract](../architecture/multi-platform.md); operational probes retain their stated platform scope.

- Full product/distribution generation requires an explicit user build instruction; focused compilation required for authorized verification may run within that scope.
- Store distribution executables in project `artifacts/releases/<name>/`, VSIX files in `artifacts/vsix/<name>/`, logs in `artifacts/logs/<name>/`, and isolated verification state in `artifacts/verification/`. Exclude all of `artifacts/` from Git.
- Copy account module source to `artifacts/build/<name>/companion/`, then install and build from its lockfile. Do not remove `node_modules` from the source directory or terminate user processes because the running extension holds native DLLs. Clean up build working folders immediately in the same task after verification and handoff. Retain only tool paths referenced by active installations or running processes; record retention reasons and removal conditions.
- Select an absolute Cargo cache and its execution owner before compilation. Reuse the engine source's (`-SourceRoot`) ignored `codex-rs/target/` only when compatible and available; its default location is not permission to contend with another task. Coordinate one producer per physical target directory, reusing its completed preparation or waiting before launching another Cargo process. Use `-EngineTargetDirectory` for a separate cache only when its preparation, duplicate compilation and storage cost are justified. Preserve exact package, feature, target, profile and toolchain semantics when grouping Rust checks; do not union features or replace distinct checks to obtain a warm cache. Reuse only currently used TypeScript `dist/` and `node_modules/`. At completion, review alternate Rust targets, test-only and worktree caches through their owners; delete verified unused generated groups or record protection and a concrete revisit condition. Do not generate distributions on the desktop or in external work-document folders.
- Product compilation requires an exactly bound compatible engine, bridge and code-mode host bundle. Pin the host from an installed compatible Codex with its source path and SHA-256; when upstream Windows `rusty_v8` assets cannot be obtained, do not label it as built from source. Current engine provenance covers the complete source tree; general test-only equivalence is not implemented.
- Keep build and verification caches, temporary preparation and frozen source copies inside the active workspace's `artifacts/` tree. Pin tool-specific cache and temporary-directory settings there before execution. Do not relocate them outside the workspace to solve path limits; use a short, owned verification directory inside the workspace. Existing installed tools and explicitly requested user-profile installation destinations retain their own roles.
- Fixtures intended to represent empty projects must establish their own project boundary and isolated home when stored below the checkout. Use the existing discovery configuration or an owned test repository so ancestor `AGENTS.md` and project settings do not enter test requests. Verify the actual fixture behavior with a focused check before expensive regression compilation; a workspace-local temporary path alone does not establish isolation.
- Engine reuse requires `azrael-engine-build.json` to match selected tracked, untracked and deleted source contents, major build environment inputs, and engine, bridge and code-mode host hashes. Git HEAD alone is insufficient; bundles without receipts require rebuilding. Recheck selected inputs before isolated deployment. The full product source audit remains mandatory even if narrower owner keys are implemented later; filenames alone never establish equivalence.

## Build Preflight and Artifact Dependencies

Apply the common [build-input and result-reuse rules](../../instructions/skills/implementation/references/build-inputs.md#후속-소비자와-산출물-재사용) before expensive execution. Including all current changes does not itself select `-FullRegression`. Final package identity and all six fresh-state host stages remain mandatory for installation.

Gate each expensive consumer on its required prerequisites using the [operational probes](../ops/development.md#consolidated-build-preflight) as inputs become available. Check actual dependency loads, package closure/exports, executable interfaces and owned output paths where consumed. Start ready independent work; later-produced prerequisites gate their consumers when ready.

Cargo verification enforces its executable prerequisite gate through the shared helper and the declared `selected-tests-v1` bundle contract; see [Cargo preflight operations](../ops/development.md#pipeline-verification-and-retry). Do not bypass the helper to accept a zero-test or failed prerequisite result.

Native result reuse and force-execution options follow the [operational contract](../ops/development.md#native-verification-result-reuse) and its linked Cargo evidence owner. Whole-engine fingerprints remain binding until a narrower complete contract is implemented and tested. Keep full-gate integrity checks and failed receipts.

Routine source selection keeps product behavior and small cache-safety cases. The pinned transform/cache matrix selects the closed asset-target union for known injector edits and exact known current pinned asset edits; common owners, pins, incomplete dependencies, direct test edits and exhaustive scope retain the complete matrix. Legacy pinned-link compatibility and aggregate preservation cache checks follow their registered related owners. Implementation source-text, AST-shape and fixed patch-count assertions are excluded from the source regression contract; actual execution, output, error, ownership and cache-integrity checks remain. Runner-selection regression likewise follows its own owner changes. The shared owner is `scripts/source-test-policy.cjs`; selection reports and preservation receipts record omitted cases and reasons. Use the [exhaustive operations](../ops/development.md#source-test-scope) for the complete source/tool matrix. These are conditional test exclusions, not evidence that excluded cases passed. Direct test changes and policy-owner changes retain the affected complete cases.

Select engine verification by functional bundle in the existing inventory. Use changed bundle owners or an explicit model-selected bundle scope; unresolved impact requires a scope decision rather than automatically selecting every engine check. Full regression explicitly selects all bundles. Run necessary actual tests without a deployment-wide preliminary type-check sweep. Preserve all six final host stages. A full deployment may defer the namespace-cache-owner source file to its mandatory UI preservation gate; source-only and changed-only runs keep that file when selected.

| Changed boundary | Early check before the long engine build | Later acceptance |
| --- | --- | --- |
| Windows engine replacement, PTY or process launch | The focused Windows PTY native preflight, including inherited Ctrl-C and detached-host cases | Selected engine preservation plus final host stages |
| Native dependencies and external runtimes | Actual `node-pty` load, selected Bun/Node availability and pinned code-mode host identity; acquire required V8 assets when applicable | Actual native and bundled-runtime checks |
| Host/UI/account packaging | Pinned pristine UI, lockfile/tool availability and affected registered source checks | Preparation preservation and the exact final VSIX host stages |

[Development operations](../ops/development.md#windows-native-preflight) owns the focused command. Run it explicitly before deployment when its row applies; the deployment runner does not automatically schedule this additional narrow preflight. Its preparation compile may warm the compatible Cargo target. A debug preflight does not establish a release-profile pass.

## From Generation to Installation

Azrael installation and updates install one independent host, including the account and usage module, into the ordinary VS Code profile. The internal account module VSIX is a build input and is not installed separately. Preserve original Codex files, registration and settings; install and pin only Azrael-owned extensions. Verify independent activation of the local VSIX and concurrent activation with original Codex before applying it; do not forcibly terminate working windows. [Operational documentation](../ops/development.md#prepare-verify-and-install) owns commands and recovery.

1. Read guidance and owners for the changed area and determine necessary verification scope. Reuse existing sufficient evidence.
2. Generate a newly named distribution with the operational build command only under an explicit user build instruction. Preserve failed outputs and apply the common retry procedure through existing owner keys.
3. Capture the distribution identity from `build-info.json` for the completion report. `latest.json` identifies only the last successful packaging location, not completed verification or installation.
4. Prepare the host package with `PrepareOnly`, then run the six host verification stages with fresh fixture state. This stage does not install user extensions or make actual model calls. For feature changes, also run the operational checks for the relevant area.
5. Install by specifying the exact verified package. Check the installation receipt and preservation of original Codex and settings; do not close running windows.
6. During the same task, review superseded distributions, rollback copies and VSIX packages through the [distribution cleanup procedure](../ops/development.md#legacy-release-cleanup); preview before deleting. Delete their complete generated groups once active installation, process, shortcut, work and handoff consumers have released them. A previous-version label or a failed replacement build does not justify retaining an otherwise unused copy.

## Updates, Recovery and Cleanup

When the changed installation or behavior needs the user's normal-operation check, follow the common [User confirmation and cleanup procedure](../../instructions/skills/implementation/references/artifact-lifecycle.md#user-confirmation-and-cleanup). Announce only necessary check/recovery material, including backups, rollback copies and required cloned environments, with exact paths/groups, purpose, known size and deletion after confirmation. Keep cleanup pending until the announced check is resolved; delete unrelated temporary output immediately. After clear confirmation, verify the replacement, release satisfied recovery references through their owners and finish ordinary cleanup without another cleanup request. Preserve current installations, required version evidence and existing owner/permission protections.

The UI source check result cache in `artifacts/cache/verification-results/` retains only the current input key for each check. When inputs change, delete the previous key before running its replacement check; do not store failures. Automatically clean up checks removed from the manifest and old schemas too. Clean up entries protected by an active lease immediately after completion; report retention reasons for path or ownership verification failures or abandoned leases, and bypass the cache. This cleanup is separate from distributions and user data. The six additional behavioral checks in UI source schema2 follow the same retention, lease and fail-closed contract. Reuse requires identical complete source inputs and actual project TypeScript; run the common cache-owner/fixture guard and final six host stages.

Also clean packaging stages from interrupted deployments with `clean-verification-artifacts.ps1`. Explicitly specify a diagnosed `artifacts/deployments/{deploy,manual}-<name>/package/stage-<32-lowercase-hex-digits>` path as `-FixtureRoot`, preview with `-IncludeDiagnosedFixtures`, then apply. Do not select it through automatic discovery; retain stages belonging to installed deployments or referenced by running processes or protected paths.

- Do not overwrite running distributions or forcibly terminate processes. Apply a verified independent extension build by reloading existing windows after the user finishes ongoing work.
- Retain logins, conversations and settings in existing `~/.azrael-ex`; do not treat them as build artifacts or clean them up. Existing CLI tooling owns Devin CLI login; additional managed accounts use the separate store in [provider account operations](../ops/provider-accounts.md).
- If an update fails, correct the failure and build a replacement; keeping an older rollback version is not required. Future releases that change state schemas require a separate compatibility review.
- On successful verification, retain only required result summaries, exit codes and package identifiers in the owning log location; immediately remove verification extensions, VS Code profiles, copied plugins, skills, packages and fixtures in the same task. Remove failed fixtures immediately after diagnosis and handoff too. Protect ongoing verification, running-process references and unresolved failures needed for reproduction while resolving cleanup. Before task completion, obtain explicit user approval for any remaining cleanup-scope material, with exact paths, reasons and release/review conditions under the installed `implementation` skill; pending approval keeps cleanup unresolved. Builds automatically clean only registered, reproducible caches after lock and path checks. Distributions, source snapshots and user data are excluded from automatic cache cleanup. Delete verification fixtures through the separate completion cleanup path after preserving required results. Do not move large fixtures or package copies into log folders for retention.
- Determine active installation references from actual extension registration and runtime settings, not `latest.json` alone. Clean up unprotected distributions and VSIX files before handing off a new distribution, recording a reason and removal condition for every retained path. Separately verify installation ownership and references for separate installation roots such as `%LOCALAPPDATA%/azrael-ex/releases`. Retain only small identifying receipts and results; do not move distribution binaries into log folders.

## Work and Version Ownership of Generated Artifacts

Retain Cargo dependency-based compilation and per-asset/per-check keys under the common reuse rules. Module logs retire with their content-key entry. Current module and verification owners collect superseded unused keys on selection; publication failure does not restore them. Protected consumers retain their entries. Target: collect superseded payload, dedicated logs and temporary outputs through the owning group as soon as replacement work or the last consumer completes, without another legacy-cleanup request. Publication and last-consumer release are not yet universal collection events; keep current owner guards and report this gap.

At completion, review obsolete version groups and use the [coordinated cleanup procedure](../ops/development.md#legacy-release-cleanup) with `-IncludeModuleCaches` when selecting their deletion. The procedure removes each unprotected version's payload and raw logs before collecting module keys whose final consumers have gone; cache owners keep their own leases and path/process/installation checks. Protect failed, unknown or required consumers; record the reason and revisit condition, and obtain explicit user retention approval for cleanup-scope leftovers before task completion. A protection or defer record alone is not approval. `-SkipCacheCleanup` requires completing the deferred cleanup/review before handoff, or explicit user approval for the exact retained cleanup-scope entries; a recorded reason alone is not a retention policy. Do not keep duplicated raw logs or snapshots after their purpose has ended, and verify actual remaining paths in the combined report.

For already registered groups, use the [management-tool workflow](../ops/project-maintenance.md#registered-group-cleanup) first. The tool performs its implemented pre-deletion checks; the model decides scope and delete/defer from its current results. Do not repeat covered ownership, content or reference checks through a separate recursive inventory, hash pass or re-registration. Use the coordinated scripts and cache owners for operations outside native coverage, and target additional investigation to unregistered paths, conflicts, reported uncertainty or uncovered installation/runtime references. Initial legacy adoption and migration inventory does not repeat for unchanged registered groups.

Before generation, connect payloads, input snapshots, working directories, logs, verification reports, packages and distribution evidence to the same owning group under [Artifact lifecycle and migration](artifact-lifecycle.md). Producers retaining existing paths must also create an `artifact-lifecycle` record first and reconcile membership and state after actual termination. Do not delete unregistered legacy files until their full ownership and references are known. Migration to a new structure follows inventory and mapping, changes to future writers, a small pilot, reader reference switching and verification, then model-directed deletion or deferral of old paths.

Distinguish retention of raw work logs from retention of version acceptance evidence. Preserve evidence needed by a version with that version so it can be read independently, switch references, then clean up unnecessary raw logs with their work group. Do not retain related logs, manifests or checksums separately forever after deleting a version payload. If current use, an active run, handoff or shared-consumer reference protects even one member, defer the entire group. For partial deletion, record why the remainder was not attempted and report actual remaining items. Keep existing cache owners' reuse, locking and safe bounded eviction contracts with those owners; do not disguise version evidence as cache.

## Inputs and Caches for Repeated Builds and Verification

New Windows builds select the shared Cargo compilation owner by default. `-CargoCacheProjectRoot <absolute-project-root>` lets a frozen execution workspace use its established owning project's `artifacts/cache/cargo/` tree; `-EngineTargetDirectory` alone retains explicitly selected legacy targets. A supplied shared owner and target must agree. The same selected target and shared owner pass to preservation checks. Keep one producer per physical target and retain unresolved leases; cache eviction remains a separate reviewed action. Do not delete the last useful compatible target merely to reduce storage while measuring repeated-build performance.

Engine provenance verification pins the physical root and directory identity within one validation context and rechecks them at stage boundaries and completion. Check physical path containment and contents for each file; reject replacing the root even with identical contents. The four mandatory source checks for `engine.source-provenance` preserve these boundaries and lexical/escape checks.

Repeated runs with the same pinned inputs use selected bytes and final fingerprints of tracked, untracked, deleted and initialized nested repositories recorded by [capture-project-inputs.cjs](../../scripts/capture-project-inputs.cjs). Apply selected bytes to independently prepared Git metadata and verify the final snapshot's hash, file count and byte count. Each file is selected during its own read interval; this does not constitute an atomic snapshot of the entire repository. Preserve before-and-after source-read file and parent identity checks, each parent's `lstat`, link and path boundaries, and exclusive output creation checks. Resolve actual paths with `fs.realpathSync.native` and check the physical root once per parent check. Regular-file parent inspection occurs at its read boundaries; deleted paths and nested repositories are inspected during selection. Destination creation and its before-read identity use one root-to-leaf inspection for that file; inspections are never cached across files. By default, read files up to 128KiB through an open handle into a Buffer and copy with `wx`; copy larger files through streams. `smallFileMaxBytes` is an integer from 0..1MiB; 0 forces streaming. Apply file modes individually and parent directory modes once each after checking observed identity. Compute Git blob IDs from the guarded copy bytes using the repository's SHA-1 or SHA-256 format. Query existing blobs in a batch and write only missing unique objects through Git's `fast-import` blob stream, validating the read bytes, file identity and returned IDs; the importer receives no commit/ref commands. Rebuild the selected index without a preliminary working-tree refresh. The final independent SHA-256 snapshot remains mandatory. Distinguish inventory/copy/Git/finalHash times, buffered/streamed file counts and Git reused-file/written-object counts in the capture receipt. Deployment preparation also records both captures, Git preparation, engine checks and immutable inventory time. A capture's complete final snapshot may serve the immediately following immutable snapshot when no override was applied; changed inputs and overrides still require validation. Guard verification for this optimization is currently limited to Windows x64 Node 26.7; assess other OSes and full input-copy performance separately through verification in those environments and with those inputs.

`deploy-azrael.ps1 -WindowControlTargetDirectory <absolute-path>` passes cache selection to the Window Control-owned builder. Do not change independent native owners' output contracts through global `CARGO_BUILD_TARGET`. Include selected input preparation and final package and host verification in repeated-run total elapsed time; distinguish already prepared pinned-input/cache cost from execution without caches. Do not reduce mandatory verification scope or failure conditions to claim a performance target pass.

Retain the registered source check list for the selected scope; select Node source test concurrency with `deploy-azrael.ps1 -SourceTestConcurrency 8` or `test-project.cjs --test-concurrency 8`. The default is 4 and the allowed range is 1–16. Select Cargo jobs separately with its supported configuration after checking actual available memory, CPU, disk pressure and cache locks. Do not start a duplicate compile waiting on the same cache. Compare total elapsed time, failures and memory impact rather than summed overlapping stage times. Record native-test compilation, test execution and resource/lock waits separately where the owning tool exposes them; mark missing subdivisions as unmeasured. More detailed timing or evidence reuse needs an implementation change, not a claim that editing this playbook accelerates the runner.

After build success and the post-build input identity check, ongoing source regression can overlap package preparation and engine verification. Monitor source failures while waiting for the build too; source, engine and preparation must all pass before proceeding to account probe, final host verification and installation. If any prerequisite fails, cancel the remaining work owned by that run. Record fixture verification of the reordered sequence separately from actual full-run time savings.

For repeated Cargo test filters, reuse completed preparation through the owning preservation run when its frozen source and compilation identity match. Treat reuse recommendations as decision support; select fresh preparation or advice-only mode when useful. Keep each filter's nonzero listing and actual Cargo execution. A preparation hit skips repeated type checking and does not reuse a passing test result. Preserve preparation receipts with the run's logs and cleanup group. Record measured phase durations separately from unmeasured compiler/link/resource costs; a smaller command count alone is not a measured end-to-end speedup. See [Cargo preparation operations](../ops/development.md#consolidated-build-preflight).
