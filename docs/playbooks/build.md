# Build and Reinstall Playbook

Applicability: Use when packaging Azrael engine, bridge or account module changes, or installing, updating or rolling back a local development distribution. [Development operations](../ops/development.md#build) owns execution commands.

Apply the [testing skill](../../instructions/skills/testing/SKILL.md) for common test selection, assertions, execution evidence and suite maintenance. This playbook retains Azrael's build inputs, caches, prerequisite gates, check selectors and exact-package acceptance.

When uploading a verified local build to GitHub Releases, also apply the [app release procedure](../ops/app-release.md).
Keep the distribution version, tag and file hashes consistent; do not overwrite files in an already published version.
Public macOS ARM64 distribution follows the [Mac distribution policy](../ops/app-release.md#macos-distribution-without-a-developer-id-certificate). Publish after obtaining a valid ad-hoc signature, an unnotarized-app notice and acceptance of the actual final package, without Developer ID or Apple notarization. This policy also applies to future Mac distributions and does not require obtaining a certificate first.

## Artifacts and Build Scope

- New Azrael builds select committed source only, as defined in [committed build inputs](../architecture/upstream-preservation.md#committed-build-inputs). Resolve the exact SHA before preparation and retain it through retries; uncommitted work and later commits are excluded. This project policy specializes the common selected-uncommitted-input default.

- Apply the common [build-input rules](../../instructions/skills/implementation/references/build-inputs.md) for frozen inputs, app version and retry identity. These rules apply across Windows, Linux and macOS under the [multi-platform contract](../architecture/multi-platform.md); operational probes retain their stated platform scope.

- Full product/distribution generation requires an explicit user build instruction; focused compilation required for authorized verification may run within that scope.
- Store distribution executables in project `artifacts/releases/<name>/`, VSIX files in `artifacts/vsix/<name>/`, logs in `artifacts/logs/<name>/`, and isolated verification state in `artifacts/verification/`. Exclude all of `artifacts/` from Git.
- Copy account module source to `artifacts/build/<name>/companion/`, then install and build from its lockfile. Do not remove `node_modules` from the source directory or terminate user processes because the running extension holds native DLLs. Clean up build working folders immediately in the same task after verification and handoff. Retain only tool paths referenced by active installations or running processes; record retention reasons and removal conditions.
- Select an absolute Cargo cache and its execution owner before compilation. Reuse the engine source's (`-SourceRoot`) ignored `codex-rs/target/` only when compatible and available; its default location is not permission to contend with another task. Coordinate one producer per physical target directory, reusing its completed preparation or waiting before launching another Cargo process. Use `-EngineTargetDirectory` for a separate cache only when its preparation, duplicate compilation and storage cost are justified. Preserve exact package, feature, target, profile and toolchain semantics when grouping Rust checks; do not union features or replace distinct checks to obtain a warm cache. Reuse only currently used TypeScript `dist/` and `node_modules/`. At completion, review alternate Rust targets, test-only and worktree caches through their owners; delete verified unused generated groups or record protection and a concrete revisit condition. Do not generate distributions on the desktop or in external work-document folders.
- Product compilation requires an exactly bound compatible engine, bridge and code-mode host bundle. Build the host from the selected engine source by default. An explicitly imported compatible host retains its source path and SHA-256; when matching Windows `rusty_v8` assets cannot be obtained, fail the source build or explicitly select an imported host, and do not label an import as built from source. Windows packaging, including reused bundles, must pass the isolated engine/host IPC check: completed text and native tool delegation, plus the existing running-cell and final-close checks. Current engine provenance covers the complete source tree; general test-only equivalence is not implemented.
- Keep build and verification caches, temporary preparation and frozen source copies inside the active workspace's `artifacts/` tree. Pin tool-specific cache and temporary-directory settings there before execution, then verify the effective paths using the consuming tool with the actual child environment. Setting parent environment variables or creating directories alone does not establish that the tool uses them. Follow the [operational preparation procedure](../ops/development.md#pipeline-verification-and-retry). Do not relocate them outside the workspace to solve path limits; use a short, owned verification directory inside the workspace. Existing installed tools and explicitly requested user-profile installation destinations retain their own roles.
- Fixtures intended to represent empty projects must establish their own project boundary and isolated home when stored below the checkout. Use the existing discovery configuration or an owned test repository so ancestor `AGENTS.md` and project settings do not enter test requests. Verify the actual fixture behavior with a focused check before expensive regression compilation; a workspace-local temporary path alone does not establish isolation.
- Engine reuse requires `azrael-engine-build.json` to match selected tracked, untracked and deleted source contents, major build environment inputs, and engine, bridge and code-mode host hashes. Git HEAD alone is insufficient; bundles without receipts require rebuilding. Recheck selected inputs before isolated deployment. The full product source audit remains mandatory even if narrower owner keys are implemented later; filenames alone never establish equivalence.

In the Windows local-NTFS integrated build, `engine-provenance.py --source-state <attempt-file> --source-generation <generation>` performs the full imported-source audit on first use of each physical source root. Later consumers in that attempt enumerate input names/identities and inspect file size, LastWriteTime and Windows ChangeTime without rereading source contents. Identical observations reuse that attempt's source snapshot; changed inputs require full validation and still reject a bundle built from different sources. Generation, target, validator/platform-policy bytes and build environment bind reuse. Source root replacement requires fresh validation. Linked/shared files, unsupported filesystems/platforms, missing/corrupt state and unavailable metadata cannot grant reuse. This is ordinary-change detection, not an atomic snapshot or protection against deliberately suppressed metadata updates. Binary hashes, host/profile/receipt checks and final package acceptance remain independent and always run. Standalone calls without state retain the original full validation; the state is not reused between build attempts. The owning feature is `engine.source-provenance`.

## Build Preflight and Artifact Dependencies

### Resuming a recorded pipeline

Use the same frozen work identity with the producer's explicit `-Resume` or `--resume`. The shared stage state selects reusable successes by consumed input identity, successful dependencies and current output hashes; a terminal failure retries its affected path. Do not assemble new handoff receipts merely to continue the same recorded work. Existing legacy runs without stage state retain their provenance-based reuse entry points.

Keep writer exclusion and unresolved execution protection. Running/unknown records and standalone installer crash leases require owner recovery; they are not passing results. Final package and current installation checks remain required. Stage state, attempt logs and generated output belong to the existing work/version group, so cleanup uses one owner review for that complete group. Resume neither releases consumers nor authorizes artifact deletion. See [pipeline state](../architecture/upstream-preservation.md#pipeline-state-and-retry) and [operations](../ops/development.md#automated-build-verification-and-installation).

Apply the common [build-input and result-reuse rules](../../instructions/skills/implementation/references/build-inputs.md#후속-소비자와-산출물-재사용) before expensive execution. Including all current changes does not itself select `-FullRegression`. Final package identity and the selected fresh-state host stages remain mandatory for installation. Final acceptance uses inventory/install/coexistence activation without repeating the full namespace source suite or requiring cached TypeScript. Standalone activation is required for host/installation dependency changes, unknown scope and full/exhaustive runs; callers may explicitly request it.

Gate each expensive consumer on its required prerequisites using the [operational probes](../ops/development.md#consolidated-build-preflight) as inputs become available. Check actual dependency loads, package closure/exports, executable interfaces and owned output paths where consumed. Start ready independent work; later-produced prerequisites gate their consumers when ready.

Prepare source-check tool dependencies in the actual frozen execution workspace before its first check, including fixture discovery. Fixture discovery must include selected extension tests and the actual current/standalone partition, not just root source tests. Source-preflight child environment applies to every selected command, including extension tests. Do not assume dependencies installed in the original checkout are available in its copy, or that a later deployment dependency stage prepares earlier consumers. Use the selected workspace's lockfile and verify actual module loading through the consumer's resolution path. Prepare the selected pinned UI and external runtime fixtures through existing owners and readiness checks; see the [operational preparation procedure](../ops/development.md#pipeline-verification-and-retry).

Cargo verification uses the shared helper and declared `selected-tests-v2` contract: the selected `cargo test` compiles and executes once, and acceptance requires an observed successful terminal result with at least one passing test. Separate broad `cargo check --tests` and filtered list passes are no longer default prerequisites. Explicit preparation is not passing-test evidence. See [Cargo operations](../ops/development.md#pipeline-verification-and-retry); zero-test, all-ignored, failed and unknown executions remain rejected. Windows PTY/PID checks still compile the exact selected libtest with `--no-run` and run it outside Cargo's Windows Job; that compilation replaces a separate preliminary `cargo check`. Executable identity, nonzero selection and actual direct execution remain required.

Native result reuse and force-execution options follow the [operational contract](../ops/development.md#native-verification-result-reuse) and its linked Cargo evidence owner. Whole-engine fingerprints remain binding until a narrower complete contract is implemented and tested. Keep full-gate integrity checks and failed receipts.

Routine build selection retains direct checks for repeated work omissions: selected inputs, fixture isolation, argument/context forwarding, package inclusion and runtime compatibility. The shared-engine fixture gate covers checker startup/IPC interpretation, Cargo invocation, selected environment/fixture readiness and owner auditing; cache matrices, resource summaries, recipe expansion and compilation-policy tools follow their changed owners or explicit verification scope instead of every shared-engine build. Instruction service coverage retains generated-package selected application and protection of locally modified files; UI copy, preview/list transitions and general error-state matrices are not retained there. Diagnostic snapshot JSON/storage-shape verification is one-off when that boundary changes; the bounded shutdown timeout check remains. These intentional reductions do not claim equivalent automated coverage. Checker resource arithmetic, fixed timeout arithmetic, version-parser input matrices and fixture-server response/state matrices are not retained source checks; actual binary identity and engine/host IPC acceptance remain required. Cargo storage corruption and failed-publication checks belong to the shared evidence store; the Cargo adapter retains its storage connection and forced invalidation check. Registered Cargo eligibility and representative key-binding checks replace the all-groups input-mutation matrix. Recipe checks retain registration/audit, target/feature/platform exceptions and child environment forwarding rather than duplicating ordinary feature filter lists and fixed inventory counts. The pinned transform/cache matrix selects the closed asset-target union for known injector edits and exact known current pinned asset edits; common owners, pins, incomplete dependencies, direct test edits and exhaustive scope retain the complete matrix. Legacy pinned-link compatibility and aggregate preservation cache checks follow their registered related owners. Implementation source-text, AST-shape and fixed patch-count assertions are excluded from the source regression contract; actual execution, output, error, ownership and cache-integrity checks remain. Runner-selection regression likewise follows its own owner changes. The shared owner is `scripts/source-test-policy.cjs`; selection reports and preservation receipts record omitted cases and reasons. Use the [exhaustive operations](../ops/development.md#source-test-scope) for the complete source/tool matrix. These are conditional test exclusions, not evidence that excluded cases passed. Direct test changes and policy-owner changes retain the affected complete cases.

Select engine verification by functional bundle in the existing inventory. Use changed bundle owners or an explicit model-selected bundle scope; unresolved impact requires a scope decision rather than automatically selecting every engine check. The explicit `cache-lifetime` engine verification profile selects the maintenance library, maintenance core handler, Windows owned cleanup and stable Cargo source checks. Its source checks retain their separate changed-owner selection; omitted native checks are reported as unselected, not passed. Other functionality and upstream preservation remain selectable when affected or through explicit full regression. Windows cleanup excludes metrics, module-build and deployment-flow checks from its native cleanup scope; their own registrations remain available. Run necessary actual tests without a deployment-wide preliminary type-check sweep. Exact-package identity and every selected fresh-state host/install stage remain mandatory. A full deployment may defer the namespace-cache-owner source file to its mandatory UI preservation gate; source-only and changed-only runs keep that file when selected.

| Changed boundary | Early check before the long engine build | Later acceptance |
| --- | --- | --- |
| Windows engine replacement, PTY or process launch | The focused Windows PTY native preflight, including inherited Ctrl-C and detached-host cases | Selected engine preservation plus final host stages |
| Native dependencies and external runtimes | Actual `node-pty` load, selected Bun/Node availability and pinned code-mode host identity; acquire required V8 assets when applicable | Actual native and bundled-runtime checks |
| Host/UI/account packaging | Pinned pristine UI, lockfile/tool availability and affected registered source checks | Preparation preservation and the exact final VSIX host stages |

[Development operations](../ops/development.md#windows-native-preflight) owns the focused command. Run it explicitly before deployment when its row applies; the deployment runner does not automatically schedule this additional narrow preflight. Its preparation compile may warm the compatible Cargo target. A debug preflight does not establish a release-profile pass.

## From Generation to Installation

Azrael installation and updates install one independent host, including the account and usage module, into the ordinary VS Code profile. The internal account module VSIX is a build input and is not installed separately. Preserve original Codex files, registration and settings; install and pin only Azrael-owned extensions. Verify concurrent activation with original Codex before applying it, and independent activation when selected by the host/dependency change scope; do not forcibly terminate working windows. [Operational documentation](../ops/development.md#prepare-verify-and-install) owns commands and recovery.

1. Read guidance and owners for the changed area and determine necessary verification scope. Reuse existing sufficient evidence.
2. Generate a newly named distribution with the operational build command only under an explicit user build instruction. Preserve failed outputs and apply the common retry procedure through existing owner keys.
3. Capture the distribution identity from `build-info.json` for the completion report. `latest.json` identifies only the last successful packaging location, not completed verification or installation.
4. Prepare the host package with `PrepareOnly`, then run the selected host verification stages with fresh fixture state. This stage does not install user extensions or make actual model calls. For feature changes, also run the operational checks for the relevant area.
5. Install by specifying the exact verified package. Check the installation receipt and preservation of original Codex and settings; do not close running windows.
6. During the same task, review superseded distributions, rollback copies and VSIX packages through the [distribution cleanup procedure](../ops/development.md#legacy-release-cleanup); preview before deleting. Delete their complete generated groups once active installation, process, shortcut, work and handoff consumers have released them. A previous-version label or a failed replacement build does not justify retaining an otherwise unused copy.

## Updates, Recovery and Cleanup

When the changed installation or behavior needs the user's normal-operation check, follow the common [User confirmation and cleanup procedure](../../instructions/skills/implementation/references/artifact-lifecycle.md#user-confirmation-and-cleanup). Announce only necessary check/recovery material, including backups, rollback copies and required cloned environments, with exact paths/groups, purpose, known size and deletion after confirmation. Keep cleanup pending until the announced check is resolved; delete unrelated temporary output immediately. After clear confirmation, verify the replacement, release satisfied recovery references through their owners and finish ordinary cleanup without another cleanup request. Preserve current installations, required version evidence and existing owner/permission protections.

The UI source check result cache in `artifacts/cache/verification-results/` retains only the current input key for each check. When inputs change, delete the previous key before running its replacement check; do not store failures. Automatically clean up checks removed from the manifest and old schemas too. Clean up entries protected by an active lease immediately after completion; report retention reasons for path or ownership verification failures or abandoned leases, and bypass the cache. This cleanup is separate from distributions and user data. The six additional behavioral checks in UI source schema2 follow the same retention, lease and fail-closed contract. Reuse requires identical complete source inputs and actual project TypeScript; run the common cache-owner/fixture guard and selected final host stages.

Also clean packaging stages from interrupted deployments with `clean-verification-artifacts.ps1`. Explicitly specify a diagnosed `artifacts/deployments/{deploy,manual}-<name>/package/stage-<32-lowercase-hex-digits>` path as `-FixtureRoot`, preview with `-IncludeDiagnosedFixtures`, then apply. Do not select it through automatic discovery; retain stages belonging to installed deployments or referenced by running processes or protected paths.

- Do not overwrite running distributions or forcibly terminate processes. Apply a verified independent extension build by reloading existing windows after the user finishes ongoing work.
- Retain logins, conversations and settings in existing `~/.azrael-ex`; do not treat them as build artifacts or clean them up. Existing CLI tooling owns Devin CLI login; additional managed accounts use the separate store in [provider account operations](../ops/provider-accounts.md).
- If an update fails, correct the failure and build a replacement; keeping an older rollback version is not required. Future releases that change state schemas require a separate compatibility review.
- On successful verification, retain only required result summaries, exit codes and package identifiers in the owning log location; immediately remove verification extensions, VS Code profiles, copied plugins, skills, packages and fixtures in the same task. Remove failed fixtures immediately after diagnosis and handoff too. Protect ongoing verification, running-process references and unresolved failures needed for reproduction while resolving cleanup. Before task completion, obtain explicit user approval for any remaining cleanup-scope material, with exact paths, reasons and release/review conditions under the installed `implementation` skill; pending approval keeps cleanup unresolved. Builds automatically clean only registered, reproducible caches after lock and path checks. Distributions, source snapshots and user data are excluded from automatic cache cleanup. Delete verification fixtures through the separate completion cleanup path after preserving required results. Do not move large fixtures or package copies into log folders for retention.
- Determine active installation references from actual extension registration and runtime settings, not `latest.json` alone. Clean up unprotected distributions and VSIX files before handing off a new distribution, recording a reason and removal condition for every retained path. Separately verify installation ownership and references for separate installation roots such as `%LOCALAPPDATA%/azrael-ex/releases`. Retain only small identifying receipts and results; do not move distribution binaries into log folders.

## Work and Version Ownership of Generated Artifacts

Retain Cargo dependency-based compilation and per-asset/per-check keys under the common reuse rules. Module logs retire with their content-key entry. Current module and verification owners collect superseded unused keys on selection; publication failure does not restore them. Protected consumers retain their entries. Target: collect superseded payload, dedicated logs and temporary outputs through the owning group as soon as replacement work or the last consumer completes, without another legacy-cleanup request. Publication and last-consumer release are not yet universal collection events; keep current owner guards and report this gap.

At completion, review obsolete version groups and use the [coordinated cleanup procedure](../ops/development.md#legacy-release-cleanup) with `-IncludeModuleCaches` when selecting their deletion. The procedure removes each unprotected version's payload and raw logs before collecting module keys whose final consumers have gone; cache owners keep their own leases and path/process/installation checks. Protect failed, unknown or required consumers; record the reason and revisit condition, and obtain explicit user retention approval for cleanup-scope leftovers before task completion. A protection or defer record alone is not approval. `-SkipCacheCleanup` requires completing the deferred cleanup/review before handoff, or explicit user approval for the exact retained cleanup-scope entries; a recorded reason alone is not a retention policy. Do not keep duplicated raw logs or snapshots after their purpose has ended, and verify actual remaining paths in the combined report.

For already registered groups, use the [management-tool workflow](../ops/project-maintenance.md#registered-group-cleanup) first. The tool performs its implemented pre-deletion checks; the model decides scope and delete/defer from its current results. Do not repeat covered ownership, content or reference checks through a separate recursive inventory, hash pass or re-registration. Use the coordinated scripts and cache owners for operations outside native coverage, and target additional investigation to unregistered paths, conflicts, reported uncertainty or uncovered installation/runtime references. Initial legacy adoption and migration inventory does not repeat for unchanged registered groups.

Before generation, connect payloads, input snapshots, working directories, logs, verification reports, packages and distribution evidence to the same owning group under [Artifact lifecycle and migration](artifact-lifecycle.md). Producers retaining existing paths must also create an `artifact-lifecycle` record first and reconcile membership and state after actual termination. Do not delete unregistered legacy files until their full ownership and references are known. Migration to a new structure follows inventory and mapping, changes to future writers, a small pilot, reader reference switching and verification, then model-directed deletion or deferral of old paths.

Distinguish retention of raw work logs from retention of version acceptance evidence. Preserve evidence needed by a version with that version so it can be read independently, switch references, then clean up unnecessary raw logs with their work group. Do not retain related logs, manifests or checksums separately forever after deleting a version payload. If current use, an active run, handoff or shared-consumer reference protects even one member, defer the entire group. For partial deletion, record why the remainder was not attempted and report actual remaining items. Keep existing cache owners' reuse, locking and safe bounded eviction contracts with those owners; do not disguise version evidence as cache.

## Inputs and Caches for Repeated Builds and Verification

Select the narrowest existing preparation path: unchanged read-only checks use `reuseDeploymentInputs`; new production inputs use `prepareDeploymentWorkspace` with a pinned commit (omitting `sourceCommit` selects HEAD once). Fixes must be committed and select a new input identity. Prepared-host packaging uses its existing declared closure. Preserve active source/manifest and cache ownership; a new input identity does not require discarding warm caches.

Full preparation reuses the successful imported-engine preflight as its before-copy provenance observation when the selected provenance/import/platform-policy tools are unchanged, rather than scanning the same source again immediately before copying. If the frozen tool bytes differ (including reviewed overrides), use the frozen validator for a fresh before-copy observation. Pin the engine source directory's physical identity before preflight and recheck it after preflight, before freeze validation and after the source's final validation. Continue independently validating the frozen engine and working engine, comparing the original source after copying, and checking complete project fingerprints. This reuse widens the checked interval; it does not introduce a persistent hash cache or permit reusing a previous run's provenance.

Existing schema-2 (`script-delta`) manifests retain read-only verification and reuse with their original dependencies. New `sourceInputs`/`projectOverrides` preparation is rejected because arbitrary overlays are not committed source. See [committed preparation](../ops/development.md#script-corrections-on-a-verified-baseline).

Before expensive producers, `test-project.cjs --check-fixtures` checks the selected suites' pinned UI closure, instruction fixture project/ancestor boundaries and Windows stable-Cargo linker path. This proves prerequisite readiness only; caller ownership and actual source, native and host tests remain separate.

When no explicit legacy engine target is selected, Windows build/deploy chooses the shared Cargo owner in this order: `CargoCacheProjectRoot`, explicitly supplied `ModuleCacheProjectRoot`, then the execution project. Thus an already selected persistent module owner also anchors Cargo storage for frozen execution copies; a dedicated Cargo owner still takes precedence. This selects storage, not permission to reuse an unverified bundle or migrate a legacy target.

The Windows release producer enables content-aware stable source preparation for managed shared Cargo targets. The physical target lease covers synchronization and the whole Cargo invocation. Supported imported engine inputs are copied into the shared entry's `source/engine`; unchanged files retain their identity and timestamps. Full selected-source validation and post-execution equality checks remain mandatory. A failed source observation preserves Cargo's actual exit separately and prevents successful cache publication. Explicit legacy targets keep their existing physical location and frozen-source execution; this change does not migrate or discard warm targets.

On Windows, filesystem IO supports the native extended-path namespace while ownership and root comparisons keep canonical physical identities. Stable Cargo execution keeps an ordinary child cwd when it fits below MAX_PATH; using the extended namespace unnecessarily can change Cargo path-dependency identity and make an unchanged lockfile fail `--locked`. Longer child paths retain the existing extended-path launch. The existing importer supplies provenance's canonical/IO separation. Tool-specific output limits still apply: test compilation plans a feasible owned output path before invoking MSVC, independently of long-file source validation. No namespace adapter changes the selected source, target ownership or integrity checks.

Stable execution is deliberately restricted to reviewed build scripts, contained dependency/build paths and equivalent effective Cargo/toolchain context. Unsupported or path-sensitive contexts run from the original frozen source and record the fallback reason. Changed script/configuration bytes require review before stable execution can cover them. Generic Cargo verification does not opt into source relocation. The implementation and recurring checks are owned by `engine.shared-engine` in the feature inventory and the Cargo target/source helpers.

New Windows builds select the shared Cargo compilation owner by default. `-CargoCacheProjectRoot <absolute-project-root>` lets a frozen execution workspace use its established owning project's `artifacts/cache/cargo/` tree; `-EngineTargetDirectory` alone retains explicitly selected legacy targets. A supplied shared owner and target must agree. The same selected target and shared owner pass to preservation checks. Keep one producer per physical target and retain unresolved leases; cache eviction remains a separate reviewed action. Do not delete the last useful compatible target merely to reduce storage while measuring repeated-build performance.

Engine provenance verification pins the physical root and directory identity within one validation context and rechecks them at stage boundaries and completion. Check physical path containment and contents for each file; reject replacing the root even with identical contents. The four mandatory source checks for `engine.source-provenance` preserve these boundaries and lexical/escape checks.

New production source is materialized from exact Git objects by `committed-project-inputs.cjs`, with committed gitlink SHAs and raw file bytes independent of checkout filters, dirty files and later commits. `captureProject` and `snapshotProject` retain live-tree semantics for explicit verification callers; they do not define the new production selection. `copyVerifiedProject` copies the verified immutable inventory into the working tree. Copy completion is preparation only; the existing complete fingerprint/provenance checks remain required before consumption and final acceptance.

`deploy-azrael.ps1 -WindowControlTargetDirectory <absolute-path>` passes cache selection to the Window Control-owned builder. Do not change independent native owners' output contracts through global `CARGO_BUILD_TARGET`. Include selected input preparation and final package and host verification in repeated-run total elapsed time; distinguish already prepared pinned-input/cache cost from execution without caches. Do not reduce mandatory verification scope or failure conditions to claim a performance target pass.

Read-only downstream consumers can explicitly select a successfully frozen deployment input with `reuseDeploymentInputs` using its original manifest SHA-256 and project fingerprint. The existing immutable input and its manifest owner remain referenced; reuse copies no source or Git metadata and does not require the earlier working copy. Full inventory, source/engine fingerprints and physical identities are still checked. Verification of an old reference proves content identity, not execution authority: each new consumer must acquire its own owner references. Writable compilation continues to use the existing working-copy preparation.

For an existing verified release and prepared host, `preparePackagingWorkspace` captures only the reviewed packaging script/license/verifier closure from that baseline, plus explicit hash-bound packaging overrides. It creates a new packaging identity without claiming an overridden full project is unchanged. Engine Rust sources and Git objects are not copied. The compact group retains dependencies on the full input and its verification evidence. Each consumer run prepares a fresh compact input, holds execution references, and calls the copied `prepare-app-release.ps1` with `-PackagingInputManifest` and `-PackagingInputSha256`. Fixed mode requires explicit release and prepared-host paths, the copied configuration, and matching whole-engine provenance; it cannot fall back to host preparation. Pre/post input verification and final ZIP/selected-host acceptance remain mandatory. See [operational usage](../ops/development.md#read-only-input-reuse). Current acceptance is tracked in the [input preparation work](../../work/EC-01-unused-file-archive/04-plan.md).

Retain the registered source check list for the selected scope; select Node source test concurrency with `deploy-azrael.ps1 -SourceTestConcurrency 8` or `test-project.cjs --test-concurrency 8`. The default is 4 and the allowed range is 1–16. Deployment applies this selection to preservation source checks too. Direct `feature-preservation.cjs` configuration accepts optional `sourceTestConcurrency` in the same range; omission retains Node's default. This controls test files while keeping separate processes, independently of `sourceConcurrency` for invocation groups. Deployment exposes invocation-group concurrency as `-SourceCheckConcurrency` (default 4, range 1–4), passed to both source preflight and engine preservation; select 1 for serial invocation groups without changing the check list, Node file concurrency or timeouts. Receipts and source handoff retain the selected value. Select Cargo jobs separately with its supported configuration after checking actual available memory, CPU, disk pressure and cache locks. Do not start a duplicate compile waiting on the same cache. Compare total elapsed time, failures and memory impact rather than summed overlapping stage times. Record native-test compilation, test execution and resource/lock waits separately where the owning tool exposes them; mark missing subdivisions as unmeasured. More detailed timing or evidence reuse needs an implementation change, not a claim that editing this playbook accelerates the runner.

After build success and the post-build input identity check, ongoing source regression can overlap package preparation and engine verification. Monitor source failures while waiting for the build too; source, engine and preparation must all pass before proceeding to account probe, final host verification and installation. If any prerequisite fails, cancel the remaining work owned by that run. Record fixture verification of the reordered sequence separately from actual full-run time savings.

For repeated Cargo test filters, reuse completed preparation through the owning preservation run when its frozen source and compilation identity match. Treat reuse recommendations as decision support; select fresh preparation or advice-only mode when useful. Keep each filter's nonzero listing and actual Cargo execution. A preparation hit skips repeated type checking and does not reuse a passing test result. Preserve preparation receipts with the run's logs and cleanup group. Record measured phase durations separately from unmeasured compiler/link/resource costs; a smaller command count alone is not a measured end-to-end speedup.
