# Build and Reinstall Playbook

Applicability: Use when packaging Azrael engine, bridge or account module changes, or installing, updating or rolling back a local development distribution. [Development operations](../ops/development.md#build) owns execution commands.

When uploading a verified local build to GitHub Releases, also apply the [app release procedure](../ops/app-release.md).
Keep the distribution version, tag and file hashes consistent; do not overwrite files in an already published version.
Public macOS ARM64 distribution follows the [Mac distribution policy](../ops/app-release.md#macos-distribution-without-a-developer-id-certificate). Publish after obtaining a valid ad-hoc signature, an unnotarized-app notice and acceptance of the actual final package, without Developer ID or Apple notarization. This policy also applies to future Mac distributions and does not require obtaining a certificate first.

<a id="테스트와-관리-도구의-경계"></a>
## Boundaries Between Tests and Management Tools

Separate build invocations from test invocations, and preparation compilation from actual check results. Built-in project maintenance connects registered commands and generation history to existing cache and cleanup owners. Retention periods and capacity budgets are conditions for model review, not automatic deletion times. Preserve backups, pinned inputs, warm measurement targets and active references; recheck protection immediately before deletion even after the model's decision. Follow [project maintenance operations](../ops/project-maintenance.md).

## Artifacts and Build Scope

- Apply the common [build-input rules](../../instructions/skills/implementation/references/build-inputs.md) for frozen inputs, app version and retry identity. These rules apply across Windows, Linux and macOS under the [multi-platform contract](../architecture/multi-platform.md); operational probes retain their stated platform scope.

- Full product/distribution generation requires an explicit user build instruction; focused compilation required for authorized verification may run within that scope.
- Store distribution executables in project `artifacts/releases/<name>/`, VSIX files in `artifacts/vsix/<name>/`, logs in `artifacts/logs/<name>/`, and isolated verification state in `artifacts/verification/`. Exclude all of `artifacts/` from Git.
- Copy account module source to `artifacts/build/<name>/companion/`, then install and build from its lockfile. Do not remove `node_modules` from the source directory or terminate user processes because the running extension holds native DLLs. Clean up build working folders immediately in the same task after verification and handoff. Retain only tool paths referenced by the current or immediately previous installation and paths referenced by running processes; record retention reasons and removal conditions.
- Select an absolute Cargo cache and its execution owner before compilation. Reuse the engine source's (`-SourceRoot`) ignored `codex-rs/target/` only when compatible and available; its default location is not permission to contend with another task. Coordinate one producer per physical target directory, reusing its completed preparation or waiting before launching another Cargo process. Use `-EngineTargetDirectory` for a separate cache only when its preparation, duplicate compilation and storage cost are justified. Preserve exact package, feature, target, profile and toolchain semantics when grouping Rust checks; do not union features or replace distinct checks to obtain a warm cache. Reuse only currently used TypeScript `dist/` and `node_modules/`. At completion, review alternate Rust targets, test-only and worktree caches through their owners; delete verified unused generated groups or record protection and a concrete revisit condition. Do not generate distributions on the desktop or in external work-document folders.
- Changes to product compilation inputs require affected rebuilds and an exactly bound compatible engine, bridge and code-mode host bundle. Pin the host from an installed compatible Codex with its source path and SHA-256; when upstream Windows `rusty_v8` assets cannot be obtained, do not label it as built from source. Account-module, launcher, documentation and path changes may reuse verified components only through existing owner fingerprints. Current engine provenance covers the complete source tree; general test-only equivalence is not implemented.
- Keep build and verification caches, temporary preparation and frozen source copies inside the active workspace's `artifacts/` tree. Pin tool-specific cache and temporary-directory settings there before execution. Do not relocate them outside the workspace to solve path limits; use a short, owned verification directory inside the workspace. Existing installed tools and explicitly requested user-profile installation destinations retain their own roles.
- Fixtures intended to represent empty projects must establish their own project boundary and isolated home when stored below the checkout. Use the existing discovery configuration or an owned test repository so ancestor `AGENTS.md` and project settings do not enter test requests. Verify the actual fixture behavior with a focused check before expensive regression compilation; a workspace-local temporary path alone does not establish isolation.
- Do not report reused binaries as newly built from current source. Build command success and feature verification are separate.
- Engine reuse requires `azrael-engine-build.json` to match selected tracked, untracked and deleted source contents, major build environment inputs, and engine, bridge and code-mode host hashes. Git HEAD alone is insufficient; bundles without receipts require rebuilding. Recheck selected inputs before isolated deployment. The full product source audit remains mandatory even if narrower owner keys are implemented later; filenames alone never establish equivalence.

## Build Error Fixes and Platform Impact

When changing source or configuration during a build, apply the common [scope and reporting rules for build error fixes](../../instructions/skills/implementation/references/build-inputs.md#빌드-오류-수정의-범위와-변경-보고). Resolve a platform-specific error at that platform's boundary and preserve existing behavior on other platforms. For example, do not remove a common CSS Windows spacing patch to fix Linux fallback-font spacing, or change conversation filtering on all platforms to fix Linux history display. If a common fix is needed, check impact and relevant regression verification under the [multi-platform contract](../architecture/multi-platform.md). If behavior changes on another platform are unavoidable, explain the impact and alternatives and obtain separate user instructions before applying them.

## Build Preflight and Artifact Dependencies

Apply the common [build-input and result-reuse rules](../../instructions/skills/implementation/references/build-inputs.md#후속-소비자와-산출물-재사용) before expensive execution. Record input selection separately from check selection: including all current changes does not itself select `-FullRegression`. Select affected registered checks plus mandatory acceptance by default; broaden coverage for unknown behavior, ABI or dependency impact, broad contract changes or insufficient evidence. A content-identical relocation or new artifact identifier alone does not require full coverage. Record the reason in the current work plan. Final package identity and all six fresh-state host stages remain mandatory for installation.

Gate each expensive consumer on its required prerequisites using the [operational probes](../ops/development.md#consolidated-build-preflight) as inputs become available. Check actual dependency loads, package closure/exports, executable interfaces and owned output paths where consumed. Reuse unchanged probe results and start ready independent work; later-produced prerequisites gate their consumers when ready. Keep compatible physical source, cache, SDK and temporary paths stable across retries. A new run identifier alone requires neither a new source folder/cache nor rebuilding unchanged components.

Cargo verification enforces its executable prerequisite gate through the shared helper and the declared `selected-tests-v1` bundle contract; see [Cargo preflight operations](../ops/development.md#pipeline-verification-and-retry). Do not bypass the helper to accept a zero-test or failed prerequisite result. This gate supplements the other preflight boundaries above; it does not establish final package acceptance.

Reuse is automatic by default: cache owners compute validity. Before heavy execution, record their per-component/check reuse, rebuild or rerun outcomes and concrete input, environment or key differences on misses in the existing report. Follow the common reuse rules and current owner keys: whole-engine fingerprints remain binding until a narrower complete contract is implemented and tested. Keep full-gate integrity checks, failed receipts and exact reused passing evidence. `-FullRegression` selects coverage while permitting valid receipt reuse; it does not force execution.

Routine source selection keeps product behavior and small cache-safety cases while running the registered expensive cache matrices, legacy pinned-link compatibility and pinned branding counts only for related changes. Runner-selection regression likewise follows its own owner changes. The shared owner is `scripts/source-test-policy.cjs`; selection reports and preservation receipts record omitted cases and reasons. Use the [exhaustive operations](../ops/development.md#source-test-scope) for the complete source/tool matrix. These are conditional test exclusions, not evidence that excluded cases passed. Direct test changes and policy-owner changes retain the affected complete cases.

Full engine regression retains both auto-compaction library contracts and the separate token-budget integration feature. Focused deployment includes the large integration harness for related engine/session/context/dependency or verification-policy changes. Preserve all six final host stages. A full deployment may defer only the namespace-cache-owner source file to its mandatory UI preservation gate; source-only and changed-only runs keep that file when selected. Do not infer cross-stage equivalence for other files from a filename intersection.

| Changed boundary | Early check before the long engine build | Later acceptance |
| --- | --- | --- |
| Windows engine replacement, PTY or process launch | The focused Windows PTY native preflight, including inherited Ctrl-C and detached-host cases | Selected engine preservation plus final host stages |
| Native dependencies and external runtimes | Actual `node-pty` load, selected Bun/Node availability and pinned code-mode host identity; acquire required V8 assets when applicable | Actual native and bundled-runtime checks |
| Host/UI/account packaging | Pinned pristine UI, lockfile/tool availability and affected registered source checks | Preparation preservation and the exact final VSIX host stages |

[Development operations](../ops/development.md#windows-native-preflight) owns the focused command. Run it explicitly before deployment when its row applies; the deployment runner does not automatically schedule this additional narrow preflight. Its preparation compile may warm the compatible Cargo target, but its result does not replace the complete registered engine check or final-package acceptance. A debug preflight does not establish a release-profile pass.

## From Generation to Installation

Azrael installation and updates install one independent host, including the account and usage module, into the ordinary VS Code profile. The internal account module VSIX is a build input and is not installed separately. Preserve original Codex files, registration and settings; install and pin only Azrael-owned extensions. Verify independent activation of the local VSIX and concurrent activation with original Codex before applying it; do not forcibly terminate working windows. [Operational documentation](../ops/development.md#prepare-verify-and-install) owns commands and recovery.

1. Read guidance and owners for the changed area and determine necessary verification scope. Reuse existing sufficient evidence.
2. Generate a newly named distribution with the operational build command only under an explicit user build instruction. Preserve failed outputs and apply the common retry procedure through existing owner keys.
3. Record the distribution name, engine, bridge and VSIX hashes from `build-info.json`, build and verification exit codes, and log locations in the work plan. Do not put them in operational documentation. `latest.json` identifies only the last successful packaging location, not completed verification or installation.
4. Prepare the host package with `PrepareOnly`, then run the six host verification stages with fresh fixture state. This stage does not install user extensions or make actual model calls. For feature changes, also run the operational checks for the relevant area.
5. Install by specifying the exact verified package. Check the installation receipt and preservation of original Codex and settings; do not close running windows.
6. After confirming successful verification and installation of the new version, clean up legacy distributions and VSIX packages in the same task. Under the [distribution cleanup procedure](../ops/development.md#legacy-release-cleanup), protect the actual installed runtime, immediately previous verified rollback copy, latest selected copy, ongoing work, processes and shortcut references; preview before deleting. Do not delete rollback copies based on a failed new version or one whose installation is unconfirmed.

## Updates, Recovery and Cleanup

The UI source check result cache in `artifacts/cache/verification-results/` retains only the current input key for each check. When inputs change, delete the previous key before running its replacement check; do not store failures. Automatically clean up checks removed from the manifest and old schemas too. Clean up entries protected by an active lease immediately after completion; report retention reasons for path or ownership verification failures or abandoned leases, and bypass the cache. This cleanup is separate from distributions and user data. The six additional behavioral checks in UI source schema2 follow the same retention, lease and fail-closed contract. Reuse requires identical complete source inputs and actual project TypeScript; run the common cache-owner/fixture guard and final six host stages.

Native verification result reuse follows the [operational contract](../ops/development.md#native-verification-result-reuse) and its linked Cargo evidence owner. `-FullRegression` selects complete coverage while automatically reusing valid receipts; `-ForceNativeVerification` forces selected native/Cargo checks to execute. Combine them for fully forced native verification. Preserve provenance and final-package binding, and run all six pre-installation host stages with fresh state against the exact package every time. Build/package generation and installation acceptance remain separate.

Also clean packaging stages from interrupted deployments with `clean-verification-artifacts.ps1`. Explicitly specify a diagnosed `artifacts/deployments/{deploy,manual}-<name>/package/stage-<32-lowercase-hex-digits>` path as `-FixtureRoot`, preview with `-IncludeDiagnosedFixtures`, then apply. Do not select it through automatic discovery; retain stages belonging to installed deployments or referenced by running processes or protected paths.

- Do not overwrite running distributions or forcibly terminate processes. Replace with a verified independent extension build of the current app version, and apply it by reloading existing windows after the user finishes ongoing work.
- Retain logins, conversations and settings in existing `~/.azrael-ex`; do not treat them as build artifacts or clean them up. Existing CLI tooling owns Devin CLI login; additional managed accounts use the separate store in [provider account operations](../ops/provider-accounts.md).
- If an update fails, reinstall by specifying the immediately previous verified distribution path and restore shortcuts. This restores executable selection; future releases that change state schemas require a separate compatibility review.
- Retain the distribution currently in use and the immediately previous verified one. Clean up older distributions after confirming that no running engine, bridge or shortcut references them. On successful verification, retain only required result summaries, exit codes and package identifiers in the owning log location; immediately remove verification extensions, VS Code profiles, copied plugins, skills, packages and fixtures in the same task. Remove failed fixtures immediately after diagnosis and handoff too. Temporarily retain only ongoing verification, running-process references and unresolved failures needed for reproduction, with retention reasons and removal conditions recorded. Builds automatically clean only registered, reproducible caches after lock and path checks. Distributions, source snapshots and user data are excluded from automatic cache cleanup. Delete verification fixtures through the separate completion cleanup path after preserving required results. Do not move large fixtures or package copies into log folders for retention.
- Preserve the current installation, immediately previous verified copy, and distributions referenced by running engines or shortcuts. Determine the installed copy from actual extension registration and runtime settings, not `latest.json` alone. Clean up unprotected distributions and VSIX files before handing off a new distribution, recording a reason and removal condition for every retained path. Separately verify installation ownership and references for separate installation roots such as `%LOCALAPPDATA%/azrael-ex/releases`. Retain only small identifying receipts and results; do not move distribution binaries into log folders.

## Work and Version Ownership of Generated Artifacts

Cache owners determine reuse from actual dependency keys; retain Cargo dependency-based compilation and per-asset/per-check keys. Module logs retire with their content-key entry. Current module and verification owners collect superseded unused keys on selection; publication failure does not restore them. Protected consumers retain their entries. Target: collect superseded payload, dedicated logs and temporary outputs through the owning group as soon as replacement work or the last consumer completes, without another legacy-cleanup request. Publication and last-consumer release are not yet universal collection events; keep current owner guards and report this gap.

At completion, review obsolete version groups and use the [coordinated cleanup procedure](../ops/development.md#legacy-release-cleanup) with `-IncludeModuleCaches` when selecting their deletion. The procedure removes each unprotected version's payload and raw logs before collecting module keys whose final consumers have gone; cache owners keep their own leases and path/process/installation checks. Preserve failed, unknown or required consumers with an explicit reason and revisit condition. `-SkipCacheCleanup` is a temporary bypass requiring a recorded reason and a later cleanup/review before handoff; it is not a retention policy. Do not keep duplicated raw logs or snapshots after their purpose has ended, and verify actual remaining paths in the combined report.

For already registered groups, use the [management-tool workflow](../ops/project-maintenance.md#registered-group-cleanup) first. The tool performs its implemented pre-deletion checks; the model decides scope and delete/defer from its current results. Do not repeat covered ownership, content or reference checks through a separate recursive inventory, hash pass or re-registration. Use the coordinated scripts and cache owners for operations outside native coverage, and target additional investigation to unregistered paths, conflicts, reported uncertainty or uncovered installation/runtime references. Initial legacy adoption and migration inventory does not repeat for unchanged registered groups.

Before generation, connect payloads, input snapshots, working directories, logs, verification reports, packages and distribution evidence to the same owning group under [Artifact lifecycle and migration](artifact-lifecycle.md). Producers retaining existing paths must also create an `artifact-lifecycle` record first and reconcile membership and state after actual termination. Do not delete unregistered legacy files until their full ownership and references are known. Migration to a new structure follows inventory and mapping, changes to future writers, a small pilot, reader reference switching and verification, then model-directed deletion or deferral of old paths.

Distinguish retention of raw work logs from retention of version acceptance evidence. Preserve evidence needed by a version with that version so it can be read independently, switch references, then clean up unnecessary raw logs with their work group. Do not retain related logs, manifests or checksums separately forever after deleting a version payload. If current use, the immediately previous recovery copy, an active run, handoff or shared-consumer reference protects even one member, defer the entire group. For partial deletion, record why the remainder was not attempted and report actual remaining items. Keep existing cache owners' reuse, locking and safe bounded eviction contracts with those owners; do not disguise version evidence as cache.

## Completion Report

Record changes, actual build and verification scope and exit codes, distribution paths, reuse, installation status and remaining constraints in the work plan and report them to the user. If installation state changes, update [current state](../ops/development.md#current-state) in operational documentation. Maintain changed commands in that single operational owner; this playbook references it.

If engine systems, features, permissions, data handling or UI design change during a build, explain to the user what changed, why and how, before and after the change, under the common change reporting rules. Include removal or replacement of existing patches, platform-specific impact, actual verification environments and unverified scope, and restoration or follow-up results. Do not report only build and installation success while omitting product behavior changes. If product behavior did not change, report that fact and the scope checked.

## Inputs and Caches for Repeated Builds and Verification

Engine provenance verification pins the physical root and directory identity within one validation context and rechecks them at stage boundaries and completion. Check physical path containment and contents for each file; reject replacing the root even with identical contents. The four mandatory source checks for `engine.source-provenance` preserve these boundaries and lexical/escape checks. A single sequential comparison with identical inputs took 28.563→17.450 seconds; host activity and filesystem cache effects remain, so do not extrapolate this to total build time savings.

Repeated runs with the same pinned inputs use selected bytes and final fingerprints of tracked, untracked, deleted and initialized nested repositories recorded by [capture-project-inputs.cjs](../../scripts/capture-project-inputs.cjs). Apply selected bytes to independently prepared Git metadata and verify the final snapshot's hash, file count and byte count. Each file is selected during its own read interval; this does not constitute an atomic snapshot of the entire repository. Preserve before-and-after source-read file and parent identity checks, each parent's `lstat`, link and path boundaries, and exclusive output creation checks. Resolve actual paths with `fs.realpathSync.native` and check the physical root once per parent check. By default, read files up to 128KiB through an open handle into a Buffer and copy with `wx`; copy larger files through streams. `smallFileMaxBytes` is an integer from 0..1MiB; 0 forces streaming. Apply file modes individually and parent directory modes once each after checking observed identity. Distinguish inventory/copy/Git/finalHash times and file counts by copy path in the capture receipt. Guard verification for this optimization is currently limited to Windows x64 Node 26.7; assess other OSes and full input-copy performance separately through verification in those environments and with those inputs.

`deploy-azrael.ps1 -WindowControlTargetDirectory <absolute-path>` passes cache selection to the Window Control-owned builder. Do not change independent native owners' output contracts through global `CARGO_BUILD_TARGET`. Include selected input preparation and final package and host verification in repeated-run total elapsed time; distinguish already prepared pinned-input/cache cost from execution without caches. Do not reduce mandatory verification scope or failure conditions to claim a performance target pass.

Retain the registered source check list for the selected scope; select Node source test concurrency with `deploy-azrael.ps1 -SourceTestConcurrency 8` or `test-project.cjs --test-concurrency 8`. The default is 4 and the allowed range is 1–16. Select Cargo jobs separately with its supported configuration after checking actual available memory, CPU, disk pressure and cache locks. Do not start a duplicate compile waiting on the same cache. Compare total elapsed time, failures and memory impact rather than summed overlapping stage times. Record native-test compilation, test execution and resource/lock waits separately where the owning tool exposes them; mark missing subdivisions as unmeasured. More detailed timing or evidence reuse needs an implementation change, not a claim that editing this playbook accelerates the runner.

After build success and the post-build input identity check, ongoing source regression can overlap package preparation and engine verification. Monitor source failures while waiting for the build too; source, engine and preparation must all pass before proceeding to account probe, final host verification and installation. If any prerequisite fails, cancel the remaining work owned by that run. Record fixture verification of the reordered sequence separately from actual full-run time savings.
