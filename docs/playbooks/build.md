# 빌드·재설치 Playbook

적용 범위: Azrael 엔진·브리지·계정 모듈 변경을 패키징하거나, 로컬 개발 배포본을 설치·업데이트·롤백할 때 사용한다. 실행 명령의 소유자는 [개발 운영 문서](../ops/development.md#build)다.

## 산출물과 빌드 범위

- 배포 실행파일은 프로젝트 `artifacts/releases/<이름>/`, VSIX는 `artifacts/vsix/<이름>/`, 로그는 `artifacts/logs/<이름>/`, 격리 검증 상태는 `artifacts/verification/`에 저장한다. 전체 `artifacts/`는 Git에서 제외한다.
- 계정 모듈은 `artifacts/build/<이름>/companion/`에 소스를 복사한 뒤 lockfile로 설치·빌드한다. 실행 중인 확장이 점유한 네이티브 DLL 때문에 소스 디렉터리의 `node_modules`를 제거하거나 사용자 프로세스를 종료하지 않는다. 빌드 작업 폴더는 검증과 인계가 끝나면 같은 작업에서 즉시 정리한다. 현재/직전 설치본의 도구 경로와 실행 중인 프로세스가 참조하는 경로만 보존하고, 보존 사유와 제거 조건을 기록한다.
- Rust 중간 산출물은 기본적으로 엔진 소스(`-SourceRoot`)의 무시된 `codex-rs/target/` 캐시를 재사용한다. 다른 작업이 사용하는 캐시를 변경하지 않고 스냅샷을 빌드하려면 `-EngineTargetDirectory`로 전용 절대 캐시 경로를 지정한다. 현재 사용하는 TypeScript의 `dist/`와 `node_modules/`만 재사용한다. 대체 Rust 타깃, 테스트 전용 캐시와 worktree에서 옮긴 보존 캐시는 작업 완료 시 사용 여부를 검사하여 사용하지 않는 경로를 즉시 삭제한다. 버전 마커가 없다는 이유로 알려진 Cargo 캐시를 계속 보관하지 않는다. 배포본을 바탕화면이나 외부 작업 문서 폴더에 만들지 않는다.
- 엔진 변경은 엔진과 브리지를 같은 빌드에서 생성하고, 설치된 호환 Codex의 code-mode host를 원본 경로·SHA-256과 함께 고정해 같은 번들로 만든다. Windows용 upstream `rusty_v8` 자산을 받을 수 없는 상태에서는 host를 소스 빌드한 것으로 표시하지 않는다. 계정 모듈만 바꾸면 검증된 배포본의 엔진 번들을 명시적으로 재사용한다. 런처·문서·경로 변경의 검증에는 기존 검증된 엔진 번들과 VSIX를 재사용할 수 있다.
- 재사용한 바이너리를 현재 소스에서 새로 빌드했다고 보고하지 않는다. 빌드 명령 성공과 기능 검증 통과는 별개다.
- 엔진 재사용은 `azrael-engine-build.json`의 소스 지문과 현재 소스가 일치하고 엔진·브리지·code-mode host 해시가 일치할 때만 허용한다. Git HEAD만 비교하지 않는다. 추적 파일의 실제 내용, 미추적·삭제 파일과 주요 빌드 환경을 함께 비교한다. 기록이 없는 이전 엔진은 새로 빌드한다. 빌드 도중 소스가 바뀌면 패키징하지 않고 다시 빌드한다. 격리 배포 직전에도 같은 검사를 수행한다.

## 생성에서 설치까지

azrael 설치·업데이트는 계정·사용량 모듈을 포함한 독립 호스트 하나를 일반 VS Code 프로필에 설치하는 방식이다. 내부 계정 모듈 VSIX는 빌드 입력이며 별도로 설치하지 않는다. 원본 Codex 파일·등록 정보·설정은 보존하며 azrael 소유 확장만 설치·고정한다. 로컬 VSIX의 독립 활성화와 원본 Codex와의 동시 활성화를 검증한 뒤 적용하고, 작업 중인 창은 강제 종료하지 않는다. 명령과 복구는 [운영 문서](../ops/development.md#prepare-verify-and-install)가 소유한다.

1. 변경 소유 영역과 적용 지침을 읽고 필요한 검증 범위를 결정한다. 기존 충분한 근거를 재사용한다. 이 작업에서는 테스트를 별도 에이전트에 맡기며, root는 구현·통합·최종 판단을 맡는다.
2. 운영 문서의 빌드 명령으로 새 이름의 배포본을 생성한다. 실패하면 로그의 최초 원인을 확인한다. 실패한 폴더를 덮어쓰지 말고 수정 후 새 이름으로 재시도한다.
3. 배포본 이름, `build-info.json`의 엔진·브리지·VSIX 해시, 빌드·검증 종료 코드와 로그 위치는 작업 계획 문서에 기록한다. 운영 문서에는 쓰지 않는다. `latest.json`은 마지막 패키징 성공 위치일 뿐 검증·설치 완료 표시는 아니다.
4. `PrepareOnly`로 호스트 패키지를 준비하고, 새 fixture 상태로 호스트 검증 6단계를 실행한다. 이 단계는 사용자 확장 설치나 실제 모델 호출을 하지 않는다. 기능 변경은 운영 문서의 해당 영역 검사까지 수행한다.
5. 검증한 바로 그 패키지를 지정해 설치한다. 설치 영수증과 원본 Codex·설정 보존 결과를 확인하며, 실행 중인 창은 종료하지 않는다.

## 업데이트·복구·정리

- 실행 중인 배포본을 덮어쓰거나 프로세스를 강제 종료하지 않는다. 새 버전의 독립 확장을 설치하고, 사용자가 진행 중인 작업을 마친 뒤 기존 창을 다시 로드해 적용한다.
- 로그인·대화·설정은 기존 `~/.azrael-ex`에 유지하며 빌드 산출물로 취급하거나 청소하지 않는다. Devin CLI 로그인은 기존 CLI가 소유하며, 추가 관리형 계정은 [provider 계정 운영 문서](../ops/provider-accounts.md)의 별도 저장소를 사용한다.
- 업데이트 문제가 생기면 직전 검증된 배포 경로를 지정해 재설치하고 바로가기를 되돌린다. 이 방법은 실행파일 선택을 복구하며, 향후 상태 스키마가 바뀌는 릴리스는 별도의 호환성 검토가 필요하다.
- 현재 사용 중인 배포본과 직전 검증본은 보관한다. 오래된 배포본은 실행 중인 엔진/브리지와 바로가기 참조가 없음을 확인한 뒤 정리한다. 검증 성공 시 필수 결과 요약·종료 코드·패키지 식별 정보만 로그 소유 경로에 보존하고 검증용 확장, VS Code 프로필, 복사된 플러그인·스킬·패키지와 fixture를 같은 작업에서 즉시 제거한다. 실패 fixture도 원인 분석과 인계가 끝나면 즉시 제거한다. 진행 중인 검증, 실행 중인 프로세스의 참조, 재현에 필요한 미해결 실패만 보존 사유와 제거 조건을 기록하여 일시 보존한다. 빌드는 잠금과 경로 검사를 거쳐 재생성 가능한 등록 캐시만 자동 정리한다. 배포본·소스 스냅샷·사용자 데이터는 캐시 자동 정리 대상이 아니다. 검증 fixture는 별도의 완료 정리 경로에서 필수 결과를 보존한 뒤 삭제한다. 로그 폴더에 큰 fixture나 패키지 복사본을 옮겨 보관하지 않는다.
- 현재 설치본, 직전 검증본, 실행 중인 엔진이나 바로가기가 참조하는 배포본은 보존한다. 그 밖의 배포본과 `%LOCALAPPDATA%/azrael-ex/releases`의 과거 배포본은 참조가 없음을 확인한 뒤 제거할 수 있다.

## 완료 보고

변경 내용, 실제 빌드/검증 범위와 종료 코드, 배포 경로, 재사용 여부, 설치 여부와 남은 제약을 작업 계획 문서에 남기고 사용자에게 보고한다. 설치 상태가 바뀌면 운영 문서의 [현재 상태](../ops/development.md#current-state)를 갱신한다. 바뀐 명령은 운영 문서 한 곳에서 유지하고 이 playbook은 그 문서를 참조한다.
