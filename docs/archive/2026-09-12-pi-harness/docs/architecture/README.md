# Architecture

설계 문서는 제품별로 분리한다. azrael-ex의 변경이 Pi Harness Workbench 기준선을 암묵적으로 바꾸지 않게 하기 위한 경계다.

## 문서 범위

이 분류에는 목표 구조, 경계, 인터페이스, 동작 모델, 제약, 품질 속성 및 설계 결정을 기록한다.

구현 순서, 작업 목록, 담당자, 일정, 진행 상태, 마이그레이션 단계 같은 실행 계획은 저장하지 않는다. 구현 계획은 이 저장소 밖의 별도 계획 저장소에서 관리하며 `docs/implementation/` 트리를 만들지 않는다.

## 구성 원칙

- 이 README는 설계 전체를 담는 문서가 아니라 설계 문서의 지도와 읽기 순서를 제공하는 라우터로 유지한다.
- 이 프로젝트의 최상위 설계 경계는 독립적으로 이해하고 변경할 수 있는 제품이다. 각 제품의 문서는 해당 하위 디렉터리에 둔다.
- 각 제품 안에서는 서로 다른 설계 관점을 한 문서에 섞지 않는다. 필요할 때 개요와 맥락, 정적 구조, 주요 런타임 흐름, 배포 구조, 도메인·데이터·보안·신뢰성 같은 횡단 관심사, 설계 결정으로 나눈다.
- 독자, 책임 주체, 변경 주기, 추상화 수준이 다르거나 한 문서가 독립적으로 검토될 수 있으면 파일을 분할한다. 내용이 짧고 함께 변경된다면 불필요한 디렉터리와 파일을 만들지 않는다.
- 코드 위치 안내는 `docs/maps/`, 실행 가능한 개발·배포·장애 대응 절차는 `docs/ops/`에 두고 설계 문서와 중복하지 않는다.
- 실제 문서가 생길 때만 파일과 하위 디렉터리를 만들고, 이 README에서는 현재 존재하는 문서만 연결한다.

## 구조 선택 기준

새 설계 문서 집합을 만들기 전에 현재 시스템의 규모, 설계 대상, 독자를 확인하고 이미 검증된 문서화 체계에서 필요한 부분만 선택한다.

- [C4 모델](https://c4model.com/diagrams)은 시스템 맥락, 컨테이너, 컴포넌트처럼 추상화 수준을 나누어 정적 구조를 설명할 때 참고한다. 모든 수준을 의무적으로 만들지는 않는다.
- [arc42](https://docs.arc42.org/home/)는 맥락과 범위, 솔루션 전략, 빌딩 블록, 런타임, 배포, 횡단 관심사, 품질 요구사항과 위험을 구분할 때 참고한다.
- 중요한 선택의 맥락과 결과는 [Architecture Decision Record](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)로 한 결정씩 기록하고, 변경되거나 대체된 기록도 상태와 후속 문서 링크를 남겨 보존한다.

프레임워크의 전체 목차를 기계적으로 복제하지 않는다. 현재의 제품별 설계 체계를 유지하고 필요한 관점만 그 안에 추가한다.

## 제품별 설계

- [Pi Harness Workbench](pi-harness/README.md): 공개 Pi SDK를 격리 process와 durable state 경계 뒤에서 사용하는 Electron harness
- [azrael-ex](azrael-ex/README.md): immutable workspace/session binding을 사용하는 VS Code extension, Webview UX, process model, 안정성 계약과 1차 release 경계

## 문서 권위 규칙

각 제품 디렉터리는 해당 제품에만 규범적이다. 제품 사이의 링크는 배경 또는 명시적으로 채택한 계약을 가리키며, 연결된 제품의 모든 결정을 자동으로 상속하지 않는다. 공통 runtime 동작은 사용하는 제품의 system design에 다시 명시된 뒤에만 구현 계약이 된다.
