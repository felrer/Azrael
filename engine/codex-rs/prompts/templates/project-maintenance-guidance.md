Project maintenance capability version 1 is available only for the tools and actions listed below. Use a local project root containing project-maintenance.json or a previously registered project_id; these selectors are mutually exclusive. project_inventory projects lists this isolated engine's registered projects. register_project requires an explicit project_root and records the validated configuration ID and canonical root under this engine's codex_home; unregister_project requires project_id and removes only alias metadata. Registering the same ID at another root requires explicit unregister and re-register. Every ID lookup rechecks the actual configuration ID and current filesystem permissions. Remote projects are unsupported. Current filesystem permissions, execution approvals, sandbox rules and tool restrictions still apply.

Use project_inventory to list configured test/build bundles and register owned generated items, including caches and backups; define or update bundles in project-maintenance.json. Unregistered tests remain retained; names and age do not establish ownership or permission to delete. project_tests and project_build support plan, run, status and recover. Select explicit bundle IDs. Review the plan's argv, cwd, environment, prerequisites and guards before running. Tests may prepare their required compilation; product builds require explicit build selection. Preserve mandatory checks and existing cache receipt rules.

Run executes ordered steps through the existing command boundary and rechecks declared inputs and configuration before and after each step. This checks declared input scope; existing producer procedures still own immutable source preparation. Changed inputs prevent a passing receipt even when the observed command exit is zero; bounded execution_output preserves that observed exit separately. Inspect execution_outputs and actual exit_code values separately from successful tool dispatch. A yielded session, missing terminal evidence, tool error, cancellation or unknown status is not a passing command. Keep session IDs and use status for native observation where available. A run with unknown steps blocks dependent work; status does not invent completion. Do not duplicate a producer whose lifecycle remains unresolved. A trusted producer_completed receipt allows a fresh attempt while preserving the original unknown result.

After abrupt engine loss, use recover only after independently verifying that the exact owned producer and its process tree have stopped. Mere PID absence is insufficient. Supply run_id and request {producer_stopped_verified:true,reason,evidence_ref} documenting that verification. Recovery refuses sessions still owned by the current execution manager and releases only unresolved producer protection. It preserves unknown/interrupted results and nullable exits; it cannot report success or accept an invented exit code. Then plan or run a fresh attempt using current inputs.

For artifact cleanup, start with project_inventory's existing group records and use project_cleanup_review and project_cleanup_apply as the primary operational path. Rely on their implemented identity, membership, ownership, reference, permission and protection checks instead of duplicating them with shell inventories or recursive hashing. Update changed group metadata through supported registration, then obtain fresh review tokens; unchanged groups do not need re-registration. A changed group invalidates prior deletion approval. Direct investigation is for unregistered paths, conflicting evidence, tool-reported uncertainty or concrete checks outside tool coverage, such as installation/runtime references not represented in the registry. Preserve existing owner procedures for unsupported operations. During a slow call, identify the stage and await its actual outcome; do not launch a duplicate scan or producer. These instructions do not bypass the tool's internal validation or claim it avoids recursive scans.

After executing a one-off bundle, review results, fix failures and rerun as needed. Use project_cleanup_review for current identities, references, protection and evidence. Choose delete or defer for each reviewed item, with a reason; defer also needs a concrete reconsideration condition. Keep material still needed for diagnosis, active work, receipts or recovery. Passing tests, elapsed time and exceeded budgets never authorize automatic deletion. Retiring retained tests requires evidence that the protected contract is replaced, obsolete or sufficiently duplicated.

Use project_cleanup_apply only for explicit decisions on exact reviewed identities. The tool rechecks protection, ownership and current references. Inspect actual per-item deletion results and remaining paths; a completed call is not proof that cleanup succeeded. ReadOnly/Hidden normalization applies only to verified owned generated items selected for deletion. Do not change System attributes, ACLs or ownership, force deletion, or bypass failed ordinary deletion. Model decisions use existing task authority and do not require repeated user confirmation unless scope or permissions actually change.

Keep payload, logs, reports, snapshots and backups attributable to one work/run, version or shared group before execution. Register a complete lifecycle with project_inventory request {group:{id,kind:'work'|'run'|'version',owner,version,membership_complete,provenance_ref,membership_source,members:[item]}}. Member paths must be disjoint; project-specific producers may project nested files to owned roots. membership_source is an optional contained metadata file or small directory: changed, missing or unreadable membership evidence blocks deletion until full re-registration. It is protected control evidence, outside the deleted group. Native registration measures existing members; producers separately record planned outputs before creating them, then reconcile actual outputs, failures and references before registration. Do not claim an incomplete producer record is deletable.

Review request {group_ids:[id]} or any member ID to expand the whole group. Every live member needs the same delete/defer fate; protection, active use, uncertainty or inbound consumers on any member protects the group. Inspect all expanded members and tokens. Deletion attempts payload before logs/evidence and stops the affected group on failure, preserving unattempted evidence and truthful partial state. Before discarding task logs required by a retained version, preserve independently readable verification in that version and switch references. Shared data has one owner and explicit consumer references; age and labels never establish safe cleanup. Reconcile producer metadata only after verified absence and released references, without leaving an unlimited history of empty groups.
