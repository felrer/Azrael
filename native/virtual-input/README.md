# Virtual input native prototype

Source-stage prototype for **local Windows x64, MSVC C++17, Windows 10/11 interactive desktops**. It is separate from the physical Windows mouse/keyboard. Only fresh owned Win32 `EDIT` fixtures with an explicit Common Controls v6 manifest and InitCommonControlsEx are in the initial acceptance scope: A uses single-line EDIT, B/C use multiline EDIT. Build and runtime verification are required; source availability does not establish compatibility with user applications. Modern Notepad, Chromium/Electron, IME/dead-key composition, Raw Input, DirectInput, elevated/protected applications, other CPU architectures and other OSes have no acceptance claim. Independent simultaneous physical typing remains unverified.

## Build and check

No dependency installation, package download or network access occurs during CMake builds. Source inputs include pinned MinHook 1.3.4 and nlohmann/json 3.11.3 (see [notices](THIRD_PARTY_NOTICES.md) and [per-file provenance](vendor/provenance.json)). Use the owning project build/artifact procedures to prepare immutable inputs and select output ownership **before** invoking these commands:

```powershell
& '<VS18>/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe' -S '<frozen>/native/virtual-input' -B '<owned-build>' -G 'Visual Studio 18 2026' -A x64
& '<cmake>' --build '<owned-build>' --config Release --target azrael-virtual-input azrael-virtual-input-selftest
& '<owned-build>/Release/azrael-virtual-input-selftest.exe'
```

VS18 on the development host is `C:/Program Files/Microsoft Visual Studio/18/Community`. Targets produce broker `azrael-virtual-input.exe`, fixed sibling `azrael-virtual-input-hook.dll`, owned fixture `azrael-virtual-input-fixture.exe`, and `azrael-virtual-input-selftest.exe`. The selftest has no arguments; success is exit 0 plus `PASS: ...`, failure is exit 1 plus `FAIL: ...`. It needs an unlocked interactive desktop and ordinary medium-integrity, non-elevated execution. Do not physically move the cursor during this check. It creates its own fixture, and uses only that fresh PID/HWND for injection. The fixture exits through its own graceful quit message; no process is force-killed. Failure to close it reports the remaining PID.

The maintained selftest prevents future edits from accidentally replacing virtual delivery with physical input, raising/activating the target, accepting a stale binding, leaking held states between roots, or acknowledging detach before actual hook removal. Each owned fixture process has roots A/B on one GUI thread and C on another. The test delivers to A, then verifies detach/module absence before sequential attachment to B, C and A again; unbound sibling contents must remain unchanged. Child HWND attachment and attempts to route focus/capture outside the bound root are rejected. It checks real EDIT contents, Unicode UTF-16 delivery, virtual cursor/key getters, mouse focus, Ctrl+A/backspace on v6 single-line A, Home+Shift+End/backspace on A and multiline B/C, printable key translation, held-state releases and module absence after detach. Each selection must cover exactly the expected content before backspace leaves an empty EDIT. Ctrl+A failures report selection positions and target-observed modifier/key/character information rather than weakening that expectation. A second fresh, uninjected owned fixture process is a Z-order sentinel: actual OS foreground and the two processes' A roots' relative top-level Z order must remain unchanged through attach, virtual mouse/key/text input and detach. While the injected target reports virtual F8 held, the broker's physical GetAsyncKeyState high bit, another GUI thread's getter and the uninjected fixture's getter must remain clear. No fixture is activated by the test, and no physical input is injected. It also checks stale/foreign identities and unknown fields. Physical F8 presses, mouse movement or foreground switching during the check cause failure. This verifies absence of physical-state/activation effects during a stationary test; actual simultaneous human typing/mouse motion and general application coexistence are separate unverified scenarios.

The prior unmanifested legacy multiline EDIT received Ctrl+A keydown, character 1, both Ctrl state getters and backspace, yet did not select text. That observation does not establish a general input-hook failure or Ctrl+A support across EDIT versions. The explicit fixture variants distinguish standard control behavior from delivery/state failures. Product input contains no EM_SETSEL/semantic selection fallback. Microsoft documents the [manifest and common-controls initialization requirements](https://learn.microsoft.com/en-us/windows/win32/controls/about-edit-controls) for visual-style EDIT controls; exact shortcut acceptance still comes from the executed fixture checks.

## JSON-lines protocol

Each stdin line is one UTF-8 object with exactly `id`, `method`, `params`. Output is `{id,result}` or `{id,error:{code,message,mutationOutcome}}`. IDs are string, integer or null. Empty params are `{}`. Unknown fields/methods, malformed UTF-8, duplicate JSON keys, invalid identities/ranges and lines over 65536 bytes are rejected. No UI or other stdout diagnostics are emitted. EOF performs detach; unresolved cleanup exits 2 and reports on stderr.

```json
{"id":1,"method":"attach","params":{"window":{"hwnd":"0x12345","pid":1234,"processCreated":"0x01d0000000000000","executable":"C:\\absolute\\approved.exe"}}}
{"id":2,"method":"input","params":{"kind":"mouse","action":"move","x":24,"y":28}}
{"id":3,"method":"input","params":{"kind":"mouse","action":"down","button":"left"}}
{"id":4,"method":"input","params":{"kind":"mouse","action":"up","button":"left"}}
{"id":5,"method":"input","params":{"kind":"key","virtualKey":65,"action":"down"}}
{"id":6,"method":"input","params":{"kind":"key","virtualKey":65,"action":"up"}}
{"id":7,"method":"input","params":{"kind":"text","text":"mousemux test 123 한글 🙂"}}
{"id":8,"method":"status","params":{}}
{"id":9,"method":"detach","params":{}}
{"id":10,"method":"shutdown","params":{}}
```

`processCreated` is the unsigned hexadecimal Win32 `GetProcessTimes` creation `FILETIME`, not a timestamp string. HWND must be a nonzero hexadecimal string. Attach uses the **fixed sibling DLL only** and allows one current attachment per broker. The host must obtain explicit approval and supply its exact existing target binding; this broker does not perform UI approval itself.

Mouse coordinates are **physical client pixels of the bound top-level HWND**, independent of its screen position. Both x/y are required for move and must be paired when supplied for down/up/wheel; omitted coordinates use the virtual position. Range is 0..32767 and inside the current client rectangle. Buttons are `left`, `right`, `middle`. Wheel action requires signed nonzero `delta` in -32768..32767, with Win32 wheel units (typically 120 per notch). Keys use virtualKey 1..255 and down/up. Text is at most 2047 UTF-16 code units per command, valid UTF-8 without embedded NUL; the DLL sends each UTF-16 unit as WM_CHAR. Keydown uses current target keyboard layout and ToUnicodeEx to generate WM_CHAR/WM_SYSCHAR; modifiers retain their control-character/shortcut semantics. Layout, dead-key and IME generality remains unverified.

Status returns `attached`, physical-client and screen `position`, `heldKeys`, `heldButtons`, exact bound `window` identity and current physical `client` geometry. During a disabled ambiguous session it returns `attached:false`, `cleanupPending:true`, `mutationOutcome:"unknown"`. This is not confirmation that a DLL has unloaded. A successful detach returns `unloaded:true` only after module enumeration confirms absence.

## Delivery and containment

The native broker/DLL private packet ABI is version 2; mixed old/new binaries are rejected. `status` and input replies include `deliveryDiagnostics`: the last successfully delivered message's HWND, current HWND class, message number, result and cumulative count. The class is sampled when reporting and can be empty if that window has since disappeared. These fields diagnose routing only: `applicationEffectVerified` remains false even when a WndProc returns zero or message delivery completes. They do not prove a control handled the input. Installed hosts are unchanged until a separately verified runtime is deployed.

The broker checks HWND/PID/creation/executable, same user and interactive session, ordinary medium integrity with no elevation/UIAccess, native x64 and no process protection. These are rechecked before input/status. System/security/authentication/terminal/Codex/Azrael host executable names are excluded. This is a bounded deny list, not comprehensive identification of every third-party sensitive application; host approval of the exact process and binding remain required. Multiple visible top-level siblings in that process are permitted. Exactly one root is bound at a time: changing roots, including between GUI threads, requires verified detach/unload followed by a fresh identity-checked attach. Message delivery, logical SetFocus and SetCapture remain restricted to the current root's own GUI-thread descendants. Hidden/message-only windows are not input recipients.

APIs without an HWND argument cannot distinguish which same-thread sibling caused a call. Cursor/key/foreground/active/focus/capture getters therefore expose the current attachment's virtual state to **the entire bound GUI thread**, including sibling window callbacks. A same-thread sibling's GetForegroundWindow sees the currently bound root; it does not see itself as foreground merely because it called the getter. Other GUI threads call the original APIs. Allowing siblings under process approval does not claim per-window isolation of these getters, simultaneous root control, or general multiwindow application compatibility.

An unnamed mapping and unnamed request/ack events are duplicated into the target alongside a SYNCHRONIZE-only handle to the owning broker. A POD config is passed to the remote exported initializer after LoadLibraryW. There is no named/public IPC endpoint and no arbitrary caller-selected DLL path. The DLL sends bounded synchronous messages to the exact top-level window or its hit-tested descendants on the approved GUI thread. It rejects coordinates outside the client and foreign-thread children. Logical focus/capture, cursor and 256-key states are private. MinHook detours affect callers on the approved GUI thread only; other threads call originals. A minimal nonactivating, transparent neutral native arrow marks the virtual position and is bounded to the client. It refreshes on operations and is removed on detach; it does not track moving windows while idle.

No SendInput, global SetCursorPos, actual foreground/focus changes, clipboard, UIA Value write, shell, elevation or SeDebugPrivilege is used. The SetCursorPos hook changes only the private point on the target thread. Applications that bypass these APIs are outside initial acceptance.

## Lifetime and error outcomes

Attach success follows hook readiness. Each finite command has a sequence acknowledgement and a 2.5-second DLL delivery budget. Message or remote-thread timeouts are not retried. `mutationOutcome:"unknown"` requires callers to stop/reconcile; it never means input failed without effects. `none` denotes a precondition/rejection path without an unconfirmed message delivery; a virtual-state precondition rejection may still update private transient state, and callers should use status or detach rather than assuming state rollback.

Normal detach releases held keys/buttons where safely deliverable, clears all private state, destroys the overlay, disables/removes hooks, closes target duplicated handles/views, and unloads through FreeLibraryAndExitThread. Before freeing detours it checks callback activity and suspended-thread instruction pointers to avoid unloading a callback epilogue. The broker independently polls actual module absence. Failure to establish quiescence retains the DLL, reports cleanup incomplete and never claims unload.

Controller death stops new deliveries, including checks between text units, and starts worker cleanup. On an ambiguous broker-side timeout the broker deliberately does not overwrite a potentially in-flight shared packet; further input is disabled. EOF/shutdown failure exits the controller so the process handle signals worker cleanup. **There is no confirmation channel after controller death**; retained callbacks or a hung target may prevent unload, and a timed-out LoadLibraryW can leave its remote path allocation or loaded module without a started worker. These are explicitly unresolved cleanup outcomes, never reported as success. The prototype does not kill the target to hide them. Target death releases OS resources. Broker and target termination during timeout/cleanup and concurrent physical typing still require focused runtime verification beyond the ordinary fixture happy path.
